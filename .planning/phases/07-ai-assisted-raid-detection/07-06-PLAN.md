<objective>
The raid path's own text checks. A new watcher at handler group 2 (between the commands at 0 and `/aispam` at 3) picks, cheapest first, the texts of members who joined in the last 24 hours that a cheap rule finds suspicious: a link, a forward, or a text the sender just repeated (D-01). It excludes everyone D-02 names, hands nothing to AI when `/aispam` will judge the text anyway (D-03), and puts the rest into a new bounded raid AI pool with its own workers and drain (D-18), where a raid-only TypeSafe check reports a spam verdict to plan 07-01's counter. The watcher itself costs one cached settings read and one Redis script call and always continues the update; nothing on this path deletes, restricts, bans or posts.

Task 1 is the text candidates end to end. Task 2 makes `/aispam` and the raid path share one verdict, keeps the feature inert without Redis, and keeps the raid-only breaker silent. Task 3 bounds the pool, moves the lockdown start off the worker, and adds the shutdown drain.

NEVER start PostgreSQL by any means (no su, sudo, setpriv, initdb, pg_ctl, docker). This plan adds no PostgreSQL-only guarantee.

Purpose: ROADMAP Phase 7 criteria 1 and 3, RAID-04 (text half), RAID-05, D-01, D-02, D-03, D-06, D-07, D-15, D-18, D-19.
Output: `alita/modules/raid_ai.go`, the group-2 registration, the drain and its registration in `main.go`, tests, AGENTS.md rules.
</objective>

## Phase Goal

**As a** group admin, **I want to** have AI flag borderline spam text and images, **so that** subtler raids still trigger a lockdown.

**This slice:** link spam from fresh accounts is judged by AI even in a group that never enabled `/aispam`, and a burst of it locks the group, while ordinary members are never sent to AI and nothing waits on it.

## Decisions taken here (Claude's discretion, recorded)

- Handler group 2 (`raidAIGroup = 2`, unused today, research Pattern 1): commands end the update at 0, so a command the bot handles is never judged; group 3 (`checkAISpam`) runs right after with the same carve-outs. Registered in `LoadLockdown` beside the flood watchers, value receiver on `moduleStruct`, `defer error_handling.RecoverFromPanic("raidAIWatcher", "Lockdown")`, `ext.ContinueGroups` on every path.
- Watcher order (cheapest first, copying `raidFloodCountUpdate`): supergroup; `raidFloodSenderCounts` (sender_chat, automatic forward, service IDs, the bot); the item: a text candidate is a message with `Text` set (captions belong to the image path of plan 07-08); a provider is configured for it (`raidAITextConfigured()`: `config.AppConfig.EnableAISpam && config.AppConfig.TypeSafeAPIKey != ""`); `raidRedis()`; `raidSettingsLookup` under `raidSettingsTimeout` with `AIEnabled`; `aispamWillJudge(chat.Id)` (the gates at the top of `checkAISpam`: the TypeSafe config, `aispam.IsAISpamEnabled` and `!aispamBreakerPaused`); the candidate script; the rule; then `aispamCarvedOut` (pending captcha, cached admin, approved), which costs more and so runs only for candidates; then the enqueue.
- Candidate script `raidAICandidateScript` (research Pattern 4): KEYS the `:joined` set and `alita:raid:{<chat>}:ar:<user>`; returns (new, repeated); records the hash only for a new member; the list keeps the newest 5 hashes (`raidAIRepeatHistory`) with a 1 hour TTL (`raidAIRepeatTTL`). The hash is `raidAITextHash`: lower-case, whitespace collapsed and trimmed, at least 10 runes (`raidAIRepeatMinRunes`, so "ok" never repeats), then the first 8 bytes of SHA-256 in hex. No raw text is stored anywhere (D-15).
- Rule: new AND (`len(aispamLinkDomains(msg, text)) > 0` OR `msg.ForwardOrigin != nil` OR repeated).
- `raidAIConfigured()` is `raidAITextConfigured() || raidAIImageConfigured()` with `raidAIImageConfigured()` = `config.AppConfig.GeminiAPIKey != ""`; plan 07-07's "not set up" notice reads it, and plan 07-08's image candidates use the image half.
- Pool (D-18): `raidAIQueueCapacity = 128`, `raidAIWorkerCount = 4`, started once; `raidAIJobs` and `raidAIFires` are `raidPostTracker` counters, never a `sync.WaitGroup` (its doc in raid_trigger.go explains why a bounded drain cannot use one); the in-flight count is taken before the draining flag is read, like `aispamEnqueue`; a full queue or a draining pool sheds the job and counts it. The pool context is behind a mutex-guarded accessor `raidAIContext()`, so the drain can cancel every HTTP call at once. `raidAIProcess` is a package variable (default `raidAIProcessJob`) only so a test can install a gated processor. `/aispam`'s queue and behaviour stay unchanged.
- Raid-only text job (`raidAIProcessText`): `aispamBreakerPaused` refuses (counted as shed, no request); the state is `aispamTask{...}.state(nil, 1)`, so no sender history is read or written; `aispamJevDecide` with a context from the pool context; an error counts as failed and calls `aispamBreakerRecordFailure` ignoring its tripped return, so no breaker notice is ever posted from the raid path; a success calls `aispamBreakerRecordSuccess`; `aispamIsDelete` decides spam (D-04). Only chat, user and message IDs are logged.
- `raidAIRecordVerdict` (plan 07-01) now starts `raidFire` through `raidAIFireAsync(b, chat, trig)`, a goroutine counted in `raidAIFires` that starts with `defer error_handling.RecoverFromPanic("raidAIFire", "Lockdown")`, so neither an `/aispam` worker nor a raid AI worker waits up to `raidFireTimeout`; the 60 s latch bounds how many exist.
- Drain: `StopRaidAI()` sets draining, cancels the pool context first (a check cut off is no verdict, the safe side), then waits at most `raidAIStopWait = 1 * time.Second` (a variable for tests) for the jobs and the fires; `RegisterRaidAIDrain(m)` registers it with `raidAIStopWait + shutdownDrainGrace`; `main.go` calls it right after `RegisterRaidPostsDrain`, so LIFO runs it after `DrainAISpamChecks` (whose verdicts can start fires) and before `StopRaidPosts` (a fire can start a post) and the database close. Worst case this adds 2 s to the drains in front of `StopStaffActions` in webhook mode, which AGENTS.md records honestly; idle drains return at once. A fire still running after the wait is cut off with the process and leaves at worst an unconfirmed row that the lockdown worker settles.
- Stats (D-15): `raidAIChecked` (provider answers that carried a verdict, like /aispam's checked), `raidAISpam`, `raidAIKept`, `raidAIShed` (queue full, draining or breaker paused), `raidAIFailed` (`atomic.Int64`) and `GetRaidAIStats() RaidAIStats`; plans 07-08 and 07-09 add their own counters, plan 07-10 shows them.
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`.
