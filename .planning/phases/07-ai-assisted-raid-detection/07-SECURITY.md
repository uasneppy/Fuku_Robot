# Phase 7 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Group members to `/aispam` and to the raid AI watcher | Anyone in a group can post text or media that an AI judges; the verdicts now drive a counter that can start a lockdown |
| New members to the image path | A fresh account chooses the media the bot fetches and forwards to Google, and so decides how many calls the owner pays for |
| Replicas to Redis and PostgreSQL | Several replicas report verdicts and may fire at the same moment; the database decides |
| Environment to process | The owner's Gemini key enters through the environment and must never come back out in a log, an error or a metric |
| Bot to Google (`generativelanguage.googleapis.com`) | The request carries the owner's key and a member's image; the answer is untrusted model output |
| Image content to the model | Text inside an image can try to steer the model |
| Bot to Telegram file storage | The download URL embeds the bot token |
| Bot to TypeSafe | Raid-only checks send a new member's suspicious text to TypeSafe in chats that never ran `/aispam` |
| AI providers to the bot | Every answer, failure and silence of TypeSafe and Gemini is untrusted; a slow provider must not hold a worker, a start or the shutdown |
| Cache to code | A settings value cached by the previous build is decoded into the new struct |
| Group members to `/autolockdown ai` | Anyone can type it; only a live creator or restricting admin may change the AI trigger |
| Owner's shell to the spike tool, and the tool to Google | The key enters through the environment; sample images and the key leave the machine during a run |
| Owner and developers to `/stats` | Only the owner and developers can read the AI counters |
| Docs, help text and AGENTS.md to admins and later phases | Admins decide whether to keep the AI trigger, and Phase 9's settings menu builds on the rules, from what they say |
| Test suite to the network | No test may reach a real provider |
| Process to shutdown | In-flight checks and lockdown starts must end inside the 60 s budget |

## Observations

Not register threats. None blocks the phase, and no production code was changed by this audit. The SUMMARY files raised no threat flag (07-02 to 07-14 each say "None"; 07-01 has no Threat Flags section); O-1 is the one unregistered item found by this audit.

- **O-1, WARNING (unregistered), no volume cap on the raid-only TypeSafe calls.** The Gemini path has the 20, 150 and 500 hourly budgets (T-07-33), but a raid-only text check (`raidAIProcessText`, `raid_ai.go:552-597`) has no hourly cap and no verdict cache: every candidate text (a new member's link, forward or repeated text, when `/aispam` will not judge it) is one TypeSafe call. It is bounded only by the 4 workers and the 128-job queue (`:56`, `:58`; a full queue sheds), the candidate rule and the carve-outs, so a sustained flood of link texts from fresh accounts across the owner's groups can spend up to the pool's throughput for as long as it lasts (roughly 14 000 calls an hour at a 1 s latency; TypeSafe pricing is not in the repository). The per-chat breaker counts failures, not volume. The impact is cost and shed checks, not a lock or a leak, and D-20 names Gemini only, so this is not a failed mitigation. Optional hardening: an hourly per-account and per-chat counter for text jobs, the same `raidAIBudgetTake` shape. Severity below the `high` block threshold; not counted in `threats_open`.
- **O-2, update-path lookup bound.** `aispamCarvedOut` (`aispam.go:238`) runs on the update path at group 2 for a candidate: a captcha-pending read and the cached admin and approval lookups, which on an admin-cache miss make a `getChatAdministrators` call bounded by the bot client's default timeout, not by a dedicated bound (the flood watcher bounds its own admin lookup in `antiflood.go`). It is reached only for a new member's suspicious text, or any new member's media when a Gemini key and `ENABLE_AISPAM` are set, and it is the same lookup `/aispam` makes at group 3. It delays that one update only; the dispatcher runs updates in parallel. Same family as Phase 6 O-1.
- **O-3, dot-only model names.** `ValidModel` accepts `.` and `..` (`client.go:53`), and `PathEscape` leaves dots alone, so `GetModel` with `..` (no suffix) requests `/v1beta/models/..`, a dot segment. The value is operator-set (`GEMINI_MODEL`, or the spike's `-model`), no slash can be added and the host is fixed, so it cannot redirect the key. `Classify` appends `:generateContent` to the same segment. Optional hardening: refuse a name made only of dots.
- **O-4, retry doubles the requests.** `exec` retries a 429 or 5xx once when the wait is at most 2 s (`client.go:205-223`), so one reserved budget unit can make two HTTP requests: at most 1 000 requests an hour fleet-wide at the 500 cap. Still bounded.
- **O-5, stale AI snapshot after a failed script.** The `:aispammers` snapshot script deletes the key first and writes only recent joiners (`raid_ai_count.go:211-226`), but if its call fails (Redis error) at a second AI lockdown that starts within 15 minutes of the first snapshot, the alert can list the earlier burst's accounts. The TTL bounds it and the ban run still decides each account live. Same as Phase 6 O-5.
- **O-6, wording.** The help sentence "AI never deletes or bans" (`locales/en.yml:2833`) is about the trigger; `/aispam` does delete the messages it judges, as its own page says. `lockdown_auto_ai_unavailable` ("AI checks are not set up on this bot") also shows when `ENABLE_AISPAM=false` with keys set, which reads as unconfigured rather than switched off; it errs toward telling the admin nothing is checked.
- **O-7, small log and policy notes.** A deprecated-model warning logs the model id from Google's answer, unbounded but capped by the 1 MiB body and logged once per process through the hook (`raid_ai_image.go:423-440`). The TypeSafe HTTP client (`aispam_jev.go`, unchanged `/aispam` code reused by the raid text path) uses Go's default redirect policy, which drops the `Authorization` header on a cross-host redirect; its endpoint is a code constant. The 8-byte hashes of new members' texts (1 h, per account) could confirm a guessed common phrase to someone with Redis access, who already holds more.
- **O-8, a crafted failure pauses one chat's image trigger.** Five images that make Gemini answer unusably (`MAX_TOKENS`, unreadable JSON) count as five failures and pause that chat's image checks for 5 minutes (`raid_ai_breaker.go:101-145`). Each costs the attacker one of its 20 hourly units. The join and flood triggers are untouched, and a paused check only lowers the count.
- **O-9, default-on data flow.** The AI trigger is on by default for every group (`raiddetection.Defaults`, `repository.go:44-54`) and, with `TYPESAFE_API_KEY` set and `ENABLE_AISPAM` true (the default), a new member's suspicious text goes to TypeSafe in chats that never ran `/aispam`. It is disclosed in the help text, `sample.env:105-113`, the aispam page and `AGENTS.md`, and the owner has three switches (TR-07-01); it is a decision, not a gap.
- **O-10, tests the audit could not run.** The PostgreSQL halves are CI-only (`make test-postgres-integrity`): `TestRaidDetectionSettings` against the real migration CHECK `chk_chat_raid_detection_ai`, the migration chain applying `20261029120000`, `TestStartLockdownOneActivePerChat` and `TestBeginAlert`. T-07-04 and T-07-15 rest on them for the database half. The deferred live checks of `07-VERIFICATION.md` (a real Gemini call, a real burst, two replicas, native-speaker review) are not security evidence and were not run.
