<objective>
The raid AI pool's lifecycle, split out of plan 07-06 to keep each plan small. A lockdown start asked for by an AI verdict moves onto its own tracked, recovered goroutine, so no worker ever waits on it; the pool gets a cancellable context that every AI call derives from; and a shutdown drain, `StopRaidAI`, cancels in-flight checks first and then waits at most a second for jobs and starts, registered in `main.go` right after `RegisterRaidPostsDrain`. Tests pin the pool's bounds, its panic recovery and the drain.

Task 1 is the lockdown start off the worker. Task 2 is the bounded pool's tests, the pool context and the drain with its registration.

## Phase Goal

**As a** group admin, **I want to** have AI flag borderline spam text and images, **so that** subtler raids still trigger a lockdown.

**This slice:** the AI checks can never hold a message, a worker or the bot's shutdown, whatever the providers do.

## Decisions taken here (Claude's discretion, recorded)

- Async start: `raidAIRecordVerdict` (plan 07-01) starts `raidFire` through `raidAIFireAsync(b *gotgbot.Bot, chat gotgbot.Chat, trig raidTrigger)`, a goroutine counted in `raidAIFires` (a `raidPostTracker`, never a `sync.WaitGroup`) that starts with `defer error_handling.RecoverFromPanic("raidAIFire", "Lockdown")`, copying `raidPostAsync`. `raidFire` keeps its own bounded context (`raidFireTimeout`); the 60 s latch bounds how many starts exist.
- Pool context: `raidAIContext()` returns the pool's context from a mutex-guarded holder created with the workers; `raidAIProcessText` (and plan 07-08's image job) derive their call context from it, so cancelling it aborts every HTTP call at once.
- Drain: `StopRaidAI() bool` sets `raidAIDraining`, cancels the pool context first (a check cut off is no verdict, the safe side), then waits at most `raidAIStopWait = 1 * time.Second` (a variable for tests) for `raidAIJobs` and `raidAIFires` to go idle, logging one warning when the wait runs out; queued jobs are dropped as no verdict. A start still running after the wait is cut off with the process and leaves at worst an unconfirmed row that the lockdown worker settles.
- Registration: `RegisterRaidAIDrain(m *shutdown.Manager)` registers it with `raidAIStopWait + shutdownDrainGrace` and the log line "[Shutdown] Draining raid AI checks..."; `main.go` calls it right after `modules.RegisterRaidPostsDrain(shutdownManager)`. Shutdown is LIFO, so it runs after `DrainAISpamChecks` (whose verdicts can start lockdowns) and before `StopRaidPosts` (a start can post a notice) and the database close.
- Budget: in webhook mode the drains before `StopStaffActions` already add up to exactly the 60 s budget minus its 31 s, so in the worst case, when every earlier drain runs to its limit, the staff drain can now be cut up to 2 s short; idle drains return at once. AGENTS.md records this honestly.
- A test helper in raid_ai_pool_test.go restores the pool after a drain (clears the draining flag and renews the pool context) so later tests in the binary keep a working pool.
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools ./alita/modules .` and `gofmt -l` stand in for `make lint`.
