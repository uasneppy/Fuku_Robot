## Planner assumptions (flagged)

- The lookup pacer is Interval 100 ms, MaxRetries 1 (the smallest the pacer accepts: it replaces a value of 0 or less with 3), MaxWait 5 s (research S-04; Claude's discretion, D-09). After a 429 the pacer records the full `retry_after` as the shared block and, for a `retry_after` over MaxWait, returns `ratelimit.ErrRateLimited` at once, so a block longer than 5 s sheds every lookup of every replica with no Telegram request and no waiting. The options live in a package variable so a test can build a second pacer over the same keys. Alternative for the owner (research Open Question 5): 200 ms.
- `ErrRateLimited` wraps its cause with `%v`, not `%w`, so a shed 429 can never satisfy a Telegram-error classifier: a shed is unknown, never inert (verified in `telegram_pacer.go`).
- The flight context derives from `memberReqContext()`, not from the caller, so a 3 s page open or the 4 s join budget never cancels a lookup that jobs share, and a lookup of the join entry or a press (which are not jobs) still ends at shutdown (D-11). A flight goroutine ends within `memberReqLookupFlightTimeout` or at once on `StopMemberReqJobs`; it is one goroutine per distinct key in flight, not a pool (D-10).
- The flight function's first deferred statement is the repo's panic recovery, and its zero return is `memberReqUnknown`, so a recovered panic needs no named result. A test calls `memberReqFlight` with a panicking function.
- The cache read happens outside the flight (cheap, and a `Fresh` caller never takes a cached value); the flight wraps the paced call and the cache write, so by the time the flight deregisters the positive key exists and a job that starts a moment later hits the cache.
- `Fresh` bypasses the read cache, writes a positive on a positive answer and deletes a stale positive key on a definite breach, so a member who removed their photo within 30 minutes is not shown as fixed by "I fixed it" and not waved through by the watcher afterwards (research S-04). The channel rule's `Classify` flag is added with its first reader in plan 14-04.
- A body of `null` decodes to a nil pointer with a nil error in gotgbot: nil is unknown and is never dereferenced. A breach needs `TotalCount == 0` and an empty `Photos` slice together (a count above zero or a non-empty list is a pass).
- `memberReqPhotoRule` and the layer around it have no production caller until plan 14-05 puts the rule in the table and plan 14-06 folds it into the executor; each function is called by a test of this plan, and the SUMMARY says so (the brief's rule against an unused helper).
- Logs carry chat, user IDs and `memberReqErrText` only: never a file ID, a name, a title or Telegram's description (D-18). The photo lookup sends Telegram only the user ID.
- Execution rules are `executor-brief-13.md`'s (sequential single writer, root-pin guard, commit trailers, lint stand-in, requirement bookkeeping); read "of 14" in its STATE.md rule as "of 12".
- Test hygiene (CI runs all of `fuku/modules` in one PostgreSQL database in source order): every member comes from `uniqueLinkOwnerID()`, every chat and channel from `uniqueModuleChatID()`; `memberReqCleanup` deletes the `fuku:memberreq:*` keys that contain a chat ID (register a channel ID as a chat ID so `sub:` and `lc:` keys go), and `photo:<user>` holds only a user ID, so `mreqLookupCleanup` deletes `fuku:memberreq:photo:<user>` for every minted user. Singleflight and the lookup pacer are package globals: a test that holds a flight open releases it in `t.Cleanup`, restores the pacer with `withFastLookupPacer`, and a test that calls `StopMemberReqJobs` calls `restoreMemberReqRunner(t)`. No test uses `t.Parallel` with `withMemberReqLive`, and no test assumes concurrent writers on SQLite.
