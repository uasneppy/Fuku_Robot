# Phase 14 - UI Design Contract

> Visual and interaction contract for the profile-photo rule and the channel-subscription rule. It covers the two new
> cells and rule screens of the Member requirements page, the "cannot work here" lines (MREQ-10), the refusal of a
> punishing channel rule in a group with no linked channel, the two new phrases in the group notice and in the "I fixed
> it" answers, every new callback with its worst-case size, every new string with its key and ceiling, and the checks
> that prove it.
> Generated by gsd-ui-researcher; to be verified by gsd-ui-checker.
> Upstream: 14-CONTEXT.md D-01..D-20 (locked, not reopened), REQUIREMENTS MREQ-10, MREQ-11, MREQ-12 and PLAT-06, ROADMAP
> Phase 14, the APPROVED Phase 13 contract (`13-UI-SPEC.md`, whose structure, section order, check list and string-table
> style this file copies), AGENTS.md (Handlers, Callbacks `settings|v1` and `mreq|v1`, Permissions, Data, Subsystem
> traps) and the code of `settings_mreq.go`, `memberreq_rules.go`, `memberreq_notice.go`, `memberreq_fixed.go`,
> `locales/en.yml` (`settings_mreq_*`, `settings_btn_mreq_*`, `mreq_*`) and `fuku/i18n/settings_locale_test.go` and
> `memberreq_locale_test.go`.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard, on the same two
surfaces as Phase 13: the settings menu (private, or opened in the group, edited in place) and the group (the notice and
its edit). This contract **extends** the Phase 13 contract. **Anything not restated here is unchanged and applies to the
two new rules**: the message anatomy, text styling, the press pipeline (`settingsPress.verify`, owner gate at step 4b, one
answer per press), the rule screen's shape, the two-tap card (`settings_card.go`), the rights (`settingsRightAdmin` to open,
`settingsRightRestrict` to choose), the notice anatomy, the "I fixed it" order, the "never name the Staff Group" rule
(D-21, D-32 of the settings menu; D-16 of Phase 13) and the Phase 11 to 13 limit tables.

## Interaction Contract

### 1. The seven-cell grid and the rule codes (MREQ-11, MREQ-12; D-13, D-14)

| Property | Contract |
|----------|----------|
| Rule table | two rows appended after Chinese: photo (`Code` `ph`, `Bit` 32, `memberreq.RulePhoto`, columns `photo_action`) and channel (`Code` `ch`, `Bit` 64, `memberreq.RuleChannel`, `channel_action`). They need a lookup, so they carry no pure `Broken` func; their cell, line, desc and phrase keys sit in the same row type |
| Codes | `ph` and `ch` are two-letter `t` values like `ln un ru ar zh`. They clash with no control of page `m` (`ln un ru ar zh j d`), no page action (`mo`, `my`) and no core action code. `registerSettingsPage` still panics on a duplicate |
| Controls | `ph` and `ch` are rule controls exactly like the five: `st` only (`Actions: ["st"]`), `Validate` = `v` one digit 0..4, right `settingsRightRestrict` |
| Page actions | `mo` and `my` unchanged; `mo` accepts `t=ph` and `t=ch` (`settingsMreqOpenFields` reads the table) |
| Cells | `settings_btn_mreq_photo` = `{state} Profile photo` (rendered 15), `settings_btn_mreq_channel` = `{state} Channel` (rendered 9); `{state}` is the punishment icon |
| Main | unchanged: `Off` when every rule is Off, else `{n} on` with n now 1 to 7; database only, no Telegram call, never a cannot-work flag |
| Rolling deploy | a replica on Phase 13 code answers a `t=ph` or `t=ch` press as `common_callback_invalid_request` (its table has five rules); accepted, like the other rolling-deploy caveats |

### 2. What opening a screen costs (D-15, D-08, D-06, D-09)

Every Telegram call below goes through the new lookup pacer (`fuku:memberreq:lkp:pace:*`, D-09), never `memberReqPacer`, and
the whole status read of one draw is bounded by **3 seconds** (`settingsMreqHereTimeout`, the owner-state lookup's bound).
A call the pacer sheds, a timeout, a 429, a 5xx, a transport error and any other answer that is not a definite status are all
**unknown** (the one exception, amendment M13: the bot's own `getChatMember(channel, bot)` failing with an error that
`cache.IsBotGoneError` recognises, code 400 or 403, is the `notadmin` status): the
screen draws `❔`, never an error text, never a refusal, never the cannot-cut-open edit.

| Draw | Telegram calls | Redis | Notes |
|------|----------------|-------|-------|
| Main grid entry and Main state | 0 | 0 | unchanged, DB only |
| Page, channel rule Off | 0 | 0 | nothing to flag on an Off rule |
| Page, basic group (type read from the chat object the press already holds) | 0 | 0 | the basic-group line only, and only while some rule is not Off |
| Page, supergroup, channel rule not Off, cache hit "none" | 0 | 1 `GET fuku:memberreq:lc:<chat>` | shows `settings_mreq_here_nolink` |
| Page, same, cache hit "linked" | 1 `getChatMember(channel, bot)` | 1 `GET` | shows `notadmin` or nothing |
| Page, same, cache miss | 1 `getChat(group)`, then 1 `getChatMember(channel, bot)` only if linked | 1 `GET`, 1 `SET` (10 minutes) | at most **2** calls |
| Photo rule screen | 0 | 0 | the rule needs nothing from the bot |
| Channel rule screen, every draw | 1 fresh `getChat(group)` (refreshes the cache), then 1 `getChatMember(channel, bot)` only if linked | 1 `SET` | at most **2** calls; the cache is bypassed on read (D-06) |
| Confirm card for `ph` or `ch` | 0 | 0 | the link check of `ch` happens at the press, before the card (section 5) |

The linked channel is `getChat(group).LinkedChatId` only; it is never taken from callback data or from the update (D-06).
The page's cached read can show a stale "no linked channel" for up to 10 minutes after an owner links a channel; opening
the channel rule screen refreshes the cache (Assumption P14-A6). The planner may reuse the `getChat` answer a private press
already made instead of a second call, which only lowers the numbers above. The press is answered **empty first**, then the
status read runs, then the page or screen is edited (the Staff Group page's order), so the spinner never waits on Telegram.

### 3. "Cannot work here" (MREQ-10; D-15, D-08)

Three conditions plus the unknown status, each one line of words, never an identifier:

| Condition | Line (key) | Page body | Rule screen |
|-----------|------------|-----------|-------------|
| No linked channel (channel rule only) | `🚫 ` + `settings_mreq_here_nolink` (`{rule}` = the channel rule name) | only while the channel rule is **not Off** | always on the channel screen |
| The bot is not an administrator of the linked channel (channel rule only): a definite `getChatMember(channel, bot)` status that is not administrator or creator, or an error `cache.IsBotGoneError` recognises (400 or 403), amendment M13 | `🚫 ` + `settings_mreq_here_notadmin` | only while the channel rule is not Off | always on the channel screen |
| The group is a basic group (every rule) | `🚫 ` + `settings_mreq_here_basic` (rule-agnostic, one line, never one per rule) | only while **at least one** rule is not Off (with all Off, the all-off line already says nobody is checked) | on **every** rule screen, in its status slot |
| The status could not be read (channel rule only) | `❔ ` + `settings_mreq_here_unknown` (`{rule}`) | only while the channel rule is not Off | always on the channel screen |

Rules for the lines:

- **Page body vs screen.** The page lists a problem only for a rule that is not Off (an Off rule is not expected to work).
  A rule screen always shows the line that applies to its rule, because the screen exists to explain.
- **At most one line on the page today.** A basic group reads no channel status, so the basic line replaces the channel
  lines; in a supergroup only the channel rule can have a line. After Phase 15 the AI line adds a second.
- **Nothing is claimed that the code does not do.** The lines say "so nobody is checked": that is the fail-open behaviour of
  D-05 and D-07. The photo rule has no cannot-work line except the basic-group one.
- **"No linked channel" is a finding, not a certainty (spike S3).** If `getChat(group).LinkedChatId` is not returned to a bot
  that is not an administrator of the group, an empty answer cannot prove there is no link. The line therefore says what the
  bot **found** (`I found no linked channel for this group`), never that none exists, and the same text is the refusal
  alert of section 5. If S3 comes back negative the wording is changed in place to ask for bot administrator rights in the
  group (no key added); safety is unchanged because the failure is inert (Assumption P14-A15).
- **No identifier.** No line names the linked channel's title or ID, the Staff Group, or any member (D-18). The status
  lines are words, and the same text is shown whether the channel is public or private.
- **Unknown is a status, not an error.** A failed read draws the `❔` line and leaves every control usable.
- **Where "AI not configured" goes (Phase 15, MREQ-14).** A new `settings_mreq_here_ai` line appended to the same block on
  the page (only while the AI rule is not Off) and in the AI rule screen's status slot. It adds no row and changes none of
  the above. It is deliberately not written here.

### 4. Choosing a punishment for the new rules (D-04, D-14)

Phase 13 section 2 applies unchanged to `ph` and `ch`: five choices as `st` presses with the absolute `v`; Off and Warn write
at once through `applyMemberReqAction(ctx, chatID, rule, action)`, Kick, Ban and Mute draw the card and write nothing until
Yes; a press of the stored value (judged on a direct fresh database read) writes nothing and draws no card; a failed write
redraws the rule screen with `⚠️ common_settings_save_failed`. The photo screen's hint
(`settings_mreq_hint_photo`) recommends Warn or Mute and does **not** hide Kick or Ban: all five stay selectable.

### 5. Refusing a punishing value without a linked channel (D-05, D-08)

The channel screen draws only `[Off]` when the group has no linked channel, so a punishing press can reach the bot only from
a stale screen (the channel was unlinked after it was drawn), a stale card, or a forged callback. It is refused, with an
alert, by a **live check that runs after every existing step**:

| Order | Step (an `st` on `ch` with `v` 1..4, and the card's `my` on `ch`) |
|-------|-------------------------------------------------------------------|
| 1 to 5 | the whole press pipeline: strict decode, service identity, group-menu opener, live `getChatMember` of the presser, owner gate, right `settingsRightRestrict` (a Yes also checks `e`, and an expired Yes redraws the rule screen with `⚠️ settings_card_expired`, no link check) |
| 6 | the fresh same-value database read (a press of the stored value writes nothing, draws no card, makes no link check) |
| 7 | one fresh `getChat(group)` through the lookup pacer, bounded 3 s, which refreshes `fuku:memberreq:lc:<chat>` |

## Accessibility and phone-width notes

- State is never icon alone: both new cells have their word on a body line (`settings_mreq_line`), and every status line
  starts with an icon but carries the full sentence, so a screen reader or a reader who misses the icon loses nothing.

- The single `[Off]` of the Off-only screen is a normal-width button, the largest tap target on that screen.
- The one-line "A member can fix a hidden photo only in their own privacy settings" is the sentence the owner can quote to a
  member; it names no setting by its in-app label, because the label differs by Telegram client and language.
