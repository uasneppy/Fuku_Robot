<objective>
The tracer for Phase 3. A confirmed staff action leaves a durable audit record: one parent row with issuer, target, action, duration, reason and time, and one row per linked group with its outcome and the target's state before the action. The record is created at Confirm, each group's prior state is written before that group's Telegram write, results are written as groups finish, and one transaction finalizes it when the run ends.

The prior-state columns are a one-way door (D-02): rows written without them can never be restored correctly, so Task 1 asks the owner to confirm the exact column set before Task 2 writes the migration. Task 2 is the tracer: `/ban` from the Staff Group, end to end, through the migration, model, repository, Confirm and run. Task 3 covers every kind, the fail-closed paths, shutdown truthfulness, chat migration and the AGENTS.md rules.

Purpose: ROADMAP Phase 3 success criterion 2 (STAFF-10), and the record that the log posts, the history view and "Undo everywhere" all read.
Output: the migration, model, repository, record glue in the modules package, the test harness changes and the AGENTS.md rules.
</objective>

## Phase Goal

**As a** staff member, **I want to** log, list and undo every staff action, **so that** mistakes can be reversed and we stay accountable.

**This slice:** every confirmed staff action is recorded durably, with each group's outcome and the target's prior state there, and the record survives restarts.

## Decisions taken here (Claude's discretion, recorded)

- Two tables: `staff_actions` (one row per confirmed action, with the undo-claim columns D-09 needs) and `staff_action_groups` (one row per linked group, with prior state, outcome and per-group undo result). Per-group rows, not JSON, so results are written as groups finish and counted in SQL.
- The record is created at Confirm, after every check that can still abort the card. An action is never applied without a record (fail closed, research Open Question 1).
- The prior state is written before the Telegram write (write-ahead). A crash between the write call and the result write leaves that row pending with prior state set; it renders as interrupted and is not undoable (accepted residual hole, research A8).
- `summary_chat_id` is immutable; `staff_chat_id` follows `RekeyChat`. A message ID is only meaningful in the chat it was sent to (research Pitfall 5).
- Record writes use `db.DB` directly, never the run's context, which a shutdown cancels first.
- Test seams `staffCreateActionRecord` and `staffSavePrior` (package variables, the `staffUserLookup` precedent) let tests prove the fail-closed paths with real fixtures.

## Assumptions recorded

- No PostgreSQL server runs in this sandbox by default, but the PostgreSQL 16 binaries do. Task 3 starts a throwaway cluster as the `postgres` user and runs `TestRepositoryMigrationChain` against it (this command was run successfully during planning on the current migration set). CI runs the same test.
- Pending Phase 2 cards in Redis at deploy time get a record only if confirmed after deploy; actions confirmed before Phase 3 shipped have no record and so no Undo button (CONTEXT discretion item).
