<objective>
Post every applied staff action to the log channel of each group where it was applied. The post goes out right after the group's ✅ result, through the shared pacer, under the existing admin log category, and names the issuer and target without revealing the Staff Group.

To hang the post off each group's result, the run's coordinator becomes one engine driven by a spec: `startStaffRun(b, staffRunSpec)` keeps Phase 2's coordinator exactly (one writer, throttled edits, 429 hold, lock renewal, sweep, delivery) and takes the per-group work and the hooks as functions. Phase 2's `startStaffActionRun` becomes the first spec; plan 03-06's undo run is the second. Task 1 builds the engine and the post; Task 2 proves the failure, pacing, category, escaping and regression rules and updates AGENTS.md.

Purpose: ROADMAP Phase 3 success criterion 1 (STAFF-09), D-10 to D-12.
Output: the actionlog Destination seam, staff_log.go, the run engine, three locale keys in 7 locales, tests and the AGENTS.md rule.
</objective>

## Phase Goal

**As a** staff member, **I want to** log, list and undo every staff action, **so that** mistakes can be reversed and we stay accountable.

**This slice:** each linked group's own admins see in their log channel what the staff did there, by whom and why.

## Decisions taken here (Claude's discretion, recorded)

- The post is sent with `b.SendMessageWithContext` inside `staffPaced` with the 8 s call timeout, not through `actionlog.Log`, whose send is unpaced (D-12). `actionlog.Destination` is split out so the channel lookup, the category check and the header stay in one place.
- Labels ("Admin", "User", "via Staff Group") are localized in the linked group's own language (`staffChatTranslator(link.GroupChatID)`); hashtags are not localized, like every existing log hashtag. User text (names, reason) is spliced in after translation, never passed through the translator.
- Reason cap for posts: 300 runes, applied before escaping (Pitfall A). Phase 2 already caps the stored reason at 200 runes, so this is a second guard for rows read back later.
- A run cancelled by StopStaffActions skips the remaining posts, so a group applied just before a shutdown may have no post; accepted and written into AGENTS.md (research Open Question 4).
- The engine refactor lives here because this plan adds the third per-group hook (record result from 03-01, then the log post), and plan 03-06 needs the same engine for undo.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Staff Group to linked groups' log channels | Linked groups' admins, who may not be staff, read the post |
| Staff member input (reason, names) to HTML posts | Free text from staff and stored names is rendered as Telegram HTML |
| All replicas to Telegram's flood limits | Posts add one call per applied group to the shared budget |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-03-07 | Information disclosure | Staff Group identity leaking into linked groups' log channels | medium | mitigate | composeStaffActionLog never reads card.StaffChat; TestStaffActionLogPosts scans every post for the Staff Group title and ID |
| T-03-08 | Tampering | reason or names injecting HTML or overflowing a post | medium | mitigate | Reason cut to 300 runes then html.EscapeString; target via staffTargetDisplay (escaped, capped); issuer via MentionHtml (TestStaffActionLogReasonCapped) |
| T-03-09 | Denial of service | log posts exhausting the shared flood budget or stalling a run | medium | mitigate | Every post through staffPaced; MaxWait refusal fails fast; failures logged only (TestStaffActionLogPaced, TestStaffActionLogRateLimitedKeepsDone) |
| T-03-10 | Repudiation | a failed post hiding or falsifying an applied action | low | mitigate | Post sent after progress.set and the record write; its failure never changes the result (TestStaffActionLogFailureKeepsDone) |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs; go.mod and go.sum are unchanged |
