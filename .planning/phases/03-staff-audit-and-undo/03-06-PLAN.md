<objective>
The tracer for "Undo everywhere". A staff member presses Undo on a finished summary, confirms a card that replies to it, and the bot puts back, in each group where the action was applied and the presser is an admin with restrict rights, exactly the state the record says was there before. The result is its own summary message; the original summary gains an "Undone by" line and loses its button.

Undo is a second run through the same machinery, not a copy: the same Redis card model and Lua scripts (an undo card is `action=undo` with `undo_of` and `undo_kind`), the same per-target lock, the same run engine from plan 03-03, the same per-group check chain with the presser as actor, the same pacer and summary rules, and the decision table from plan 03-02. Task 1 is the end-to-end slice for a ban. Task 2 proves the button rules, the fallback message, the reply and original-edit edge cases, and the empty and ordering edges, and records the rules in AGENTS.md.

## Phase Goal

**As a** staff member, **I want to** log, list and undo every staff action, **so that** mistakes can be reversed and we stay accountable.

**This slice:** a staff member reverses a staff ban everywhere from its summary, with a Confirm tap and live per-group checks.

## Decisions taken here (Claude's discretion, recorded)

- The undo card is the reply message (D-08): Undo posts a new card replying to the original summary, and Confirm edits that card into the undo summary, exactly as a Phase 2 card turns into its summary.
- The undo card's Issuer is the presser, so the existing Lua compare-and-set gives "only the person who pressed Undo can confirm" for free, and the per-group chain checks `card.Issuer`, which is the presser.
- Rolling deploy (research Pitfall 9): undo cards use `action=undo` and new callback codes `ya`/`yc`/`yn`. A replica still on old code answers the new codes "expired", and an undo card fed to old code's decideStaffAction fails every group with no write. New code refuses an undo card at the staff action Confirm too.
- The claim (`UPDATE staff_actions SET undo_by ... WHERE id = ? AND undo_started_at IS NULL`, RowsAffected == 1) is the last check before the run starts; the original-summary edit after it is best effort. No `links_sig` comparison: every group is rechecked live anyway.
- Groups where the original was skipped or failed are counted in one header line instead of one ⏭ line each (D-03 leaves this to the planner): a 97-group Staff Group stays readable and nothing is hidden, because the count is shown and the detail view lists them.
- "Undo while the original run is still going" is impossible by construction: the button exists only on the final text, and Ask and Confirm both require finished_at.
- Undone groups are recorded on the original record's rows (undo_outcome, undo_reason, undo_detail); an undo cannot itself be undone, so no second record is made.

| Boundary | Description |
|----------|-------------|
| Any Telegram user to the Undo and undo Confirm buttons | Buttons can be pressed by anyone who sees them, replayed from stale clients, or forged with guessable record IDs |

| Replicas sharing Redis and PostgreSQL | Two replicas can handle two undo cards for one record at once; a rolling deploy runs old and new code together |
| Staff Group chat migration | Stored summary message IDs belong to the old chat |
