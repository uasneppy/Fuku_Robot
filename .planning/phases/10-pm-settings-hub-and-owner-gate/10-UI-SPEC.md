# Phase 10 - UI Design Contract

> Visual and interaction contract for the PM settings hub and the owner gate: the private group list, the
> two-column main menu, the Access page with its two-tap ON card, the gate refusals on every door, and every new
> string with its locale key. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Upstream: 10-CONTEXT.md D-01..D-20 (locked, not reopened), REQUIREMENTS MENU-09..MENU-15 and PLAT-05, ROADMAP
> Phase 10 and its cross-cutting constraints, the Phase 9 contract (`09-UI-SPEC.md`, approved 2026-10-30), AGENTS.md
> (Callbacks, Permissions, Data), and the code of `settings.go`, `settings_menu.go`, `settings_pages.go`,
> `settings_card.go`. Layout reference only: the owner's GroupHelp screenshots (PM group list: one plain full-width
> button per group; main menu: two-column grid of icon plus name). Fuku keeps its own pages and labels.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard. Template
sections that assume CSS, fonts, pixels or colour are replaced by their Telegram equivalent, exactly as Phase 9 did.
This contract EXTENDS the Phase 9 contract: anything not restated here (message anatomy, status icons, steppers,
two-tap cards, notices versus alerts, the one-answer-per-press rule, the "never name the Staff Group" rule) is
unchanged and applies to the new screens. Where this contract changes a Phase 9 rule it says so under "Changes to
Phase 9 rules".

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Telegram Bot API, gotgbot v2) |
| Preset | not applicable |
| Component library | none: `gotgbot.InlineKeyboardMarkup` rows of `InlineKeyboardButton` |
| Icon library | Unicode emoji only, not localized (same practice as Phase 9); every word around them is a locale key |
| Font | none: Telegram client fonts. Styling is limited to the HTML tags in "Text Styling" |

Project scan: no `components.json`, `tailwind.config.*`, `package.json`, `.tsx` or `.css` in the repo. Component
Inventory is omitted (`Tool: none`). Existing Telegram UI matched in style and wording: the Phase 9 settings pages
(`renderSettingsMain`, `settingsCompose`, `settingsCardRows`), the Staff panel's Prev/Next paging, and the command
refusal texts.

Telegram limits this contract is built inside:

| Limit | Value | Where it bites |
|-------|-------|----------------|
| Message text | 4096 characters after parsing; the bot caps its own HTML at 3800 UTF-16 units | the list page (8 short lines plus hint) and the Access page are far below it; a test renders the worst case in all 8 locales |
| Callback data | 64 bytes, through `fuku/utils/callbackcodec` only | table "Callback data"; worst case for this phase is 45 bytes, the existing Phase 9 maximum stays 53 |
| Buttons | at most 8 per row, 100 per message | the list holds at most 8 group rows plus one Prev/Next row plus Close; Main holds 2 per row |
| `answerCallbackQuery` alert text | 200 characters, plain text (no HTML) | every new alert key is held to 120 EN / 160 other |
| Button label | clients cut a label with an ellipsis: about 20 visible characters in a half-width (two-column) cell, about 40 on a full-width row | grid button at most 20 code points rendered; full-width button at most 40 rendered (rules in "Copywriting Contract") |

## Message Layout (replaces Spacing Scale)

Telegram has no pixel spacing. Spacing is blank lines, line breaks and keyboard rows. The Phase 9 anatomy stands
(header line, group line, one blank line, body, one blank line, footer; one blank line between blocks, a single
newline between facts; navigation row always last, Back left and Close right). This phase adds three things.

### The list page is the one page with no group line

The private group list manages no single group, so it has the header and no group line:

```
⚙️ Settings · Groups                  <- settings_header + settings_page_groups
<blank line>
<intro line>                          <- settings_list_intro
<blank line>
<hint paragraph>                      <- settings_list_hint
<blank line>
Page 2/3                              <- staff_panel_page, only with more than one page
<keyboard: one group per row, then Prev/Next, then Close>
```

### The Main page gets a status block (state leaves the buttons)

A two-column grid cell shows about 20 visible characters, so the Phase 9 label "page icon + name + state" no longer
fits (`👥 Staff Group · Not linked` is 27 characters before translation). Decision: a grid button is **icon plus name
only**, and each page's state moves to one line in a status block in the message body:

```
⚙️ Settings
Fuku Test Group  -1001234567890

Pick what to manage. A change made here is the same as the matching command.
Only Alex can use this menu.                   <- group menu only

👥 Staff Group: Linked                         <- status block: one line per page, in grid order
🔒 Lockdown: Not active
🧩 Captcha: On
🌊 Antiflood: Limit 5
🔑 Access: Owner only                          <- the live owner only, last line
```

| Rule | Contract |
|------|----------|
| Status line | `settings_main_state_line` with `{icon}` (the page's icon), `{page}` (the page name, `settings_page_*`) and `{state}` (the page's `MainState`). One blank line separates the hint block from the status block; no blank line inside it |
| Unknown state | a page whose `MainState` read failed keeps its line with `{state}` = `❔` (the Phase 9 unknown mark) |
| Privacy | the Staff Group line is only `Linked` / `Not linked` / `{count} linked` in a menu opened in the group and for a private menu of a non-creator (Phase 9 D-21, D-32); it never names the Staff Group |
| Order | the status lines follow the grid order (page `Order`, then `Key`), the Access line last |

### The Main grid

| Rule | Contract |
|------|----------|
| Columns | two buttons per row, filled left to right in page order. An odd page count leaves the last page alone on a full-width row |
| Label | `{icon} {page name}`, built from the same `settings_page_*` key as the page header. Icon plus space plus name is at most 20 code points in every language |
| Access entry | a `🔑 Access` button, shown only to the live owner of the group. It is never paired into the grid: it is always its own full-width row after the last grid row, so adding or hiding it never changes how the other pages pair. An admin who is allowed in sees the grid with no Access button and no Access status line |
| Last rows | private menu: `[ ⬅️ Groups \| ✖️ Close ]`. Group menu: `[ ✖️ Close ]` alone (Phase 9) |
| Future pages | Phases 11 to 19 register their pages and they join the grid by `Order`. This phase fixes the grid rule, not the page list |

Why Access is last and alone: it is the one page only the owner sees; keeping it out of the pairing means the
admin's grid and the owner's grid differ by one row and nothing else.

## Text Styling (replaces Typography)

Phase 9 styling stands: `<b>` on the word "Settings" in the header and on the group title, `<code>` on chat IDs,
`<b>` on a control's current value, no other tags, user text escaped and spliced in after translation, button labels
plain text. One addition:

| Role | Telegram markup | Used for |
|------|-----------------|----------|
| Command to send elsewhere | `<code>` | `/admincache` and `/settings` inside `settings_list_hint`. Plain `/admincache` would become a tappable command that sends itself to THIS private chat, where it does nothing useful; in `<code>` a tap copies it so the owner can paste it in the group |

Group titles in the list are button labels, so they are plain text: they are **not** HTML-escaped (an escape would
show `&amp;` on the button). D-01's "escaped and spliced in after translation" holds for every place a title appears in
message text (the Main and Access group line, as in Phase 9); a title on a button is cut and left plain, as
`staffButtonTitle` does for the Staff picker.

## Interaction Contract

### The doors and the gate (MENU-11, MENU-13, D-13, D-15, D-16, D-17)

**Definition (governs every "Telegram client error", "any 4xx" and "4xx" in this document):** a Telegram client error is a
4xx answer from Telegram **other than 429**. A 429 (rate limit) depends on load and not on the named chat, so it is grouped
with transport errors, timeouts, 5xx and unreadable answers as "a failure that is not a client error", and answers
`settings_check_failed` at every door. Wherever this document says "any 4xx", read "any 4xx except 429".

Every way in re-checks the person live with `getChatMember` against the group it affects (never the admin cache or
Redis), and the owner gate sits on top of that check. The gate's answer for a person whose live status is
`administrator` is decided by the owner-state read of step 4b below: in when "Admins can change settings" is on, or when
the group has no live owner (D-15); out when an owner exists and the switch is off; and out whenever either fact cannot
be established (R6, R7). A live `creator` is always in, on the member record the live check already fetched, with no
extra call.

| Door | Order of checks | A gated admin gets | Everyone else |
|------|-----------------|--------------------|---------------|
| `/settings` typed in a group | group only, live admin check (existing, unchanged), then the gate | a plain public reply to the command: `settings_refuse_owner_only`. No keyboard. It never mentions the switch, the Access page or the Staff Group | a non-admin gets the existing refusal of `requireLockdownAuthority`; the gate never runs for them, so the new text never reaches a member |
| Anonymous admin in a group | the existing `PromptAnonAdminProof` first; after the proof tap the tapper is the sender and is checked live, then gated as above (D-17) | the same `settings_refuse_owner_only` | the proof tap of a non-admin gets the existing refusal |
| `/start settings_<chat id>` in private | strict payload parse, live check, then the gate, then one `getChat` | a plain reply `settings_start_owner_only`, no keyboard, no menu | bad payload `settings_start_invalid`; not an admin (any non-admin status), or **any Telegram 4xx client error** at the live `getChatMember` (bot missing, group gone, chat not found, forbidden, bad request, any wording, whether or not `chat_status.IsBotMissingError` recognises its text), `settings_start_not_admin` (the same words a plain non-member gets, so the reply never tells anyone whether the bot is in a chat); a failure that is not a client error (transport error, timeout, 5xx, 429, unreadable answer) `settings_check_failed`. After the gate, the one `getChat`: a 4xx client error, or a chat that is not a `group` or `supergroup`, `settings_start_not_admin` as well (the neutral refusal); a failure that is not a client error `settings_check_failed`. The class rule (a 4xx answer, never its wording) **overrides Phase 9's phrase-based mapping for this door**, which sent the three `IsBotMissingError` phrases to `settings_start_not_admin` and every other wording to `settings_check_failed`, and sent a gone or non-group chat at `getChat` to `settings_cannot_open` |
| A button press (any menu, any page, Close included) | the Phase 9 steps 1 to 4, then the gate, then the control's right | an alert `settings_gate_owner_only`; the menu is left exactly as it is (D-10) | not an admin `settings_not_admin`; lookup error `settings_check_failed` |
| Pick from the private list (`pk`) | the press pipeline with the pick overrides below (`settings_pick_unavailable` replaces `settings_not_admin` and the cannot-open edit, and answers every Telegram client error (any 4xx) at `getChatMember` and `getChat`, whatever its wording) | the same alert `settings_gate_owner_only`, and the list stays | the pick rules below; `settings_check_failed` only for transport errors, timeouts, 5xx and 429 |

**The gate cannot decide.** On every door above, when the gate cannot establish the facts it needs (the switch cannot be
read, or the owner-state read of step 4b failed, timed out or returned an unusable answer) the person is refused with the
existing `settings_check_failed` and nothing else runs: a plain reply at the three message doors (group `/settings`,
anonymous re-entry, deep link), an alert at a press, an alert at a pick with the list left as drawn. It is never answered
with the gated-admin text (that would claim an owner exists) and never lets the person in (R6, R7). No new locale key.

Press pipeline, extended. Phase 9 steps 1 to 5 stand; the gate is step 4b:

1. Decode and structure, no I/O (adds action `pk` with exactly `a` and `c`, and the list namespace).
2. Service identity: `lockdown_alert_post_as_yourself`.
3. Group menu only: `query.From.Id` equals `u`, else `settings_not_your_menu`.
4. One live `getChatMember` of the presser in the group: creator or administrator, else `settings_not_admin`; a failed lookup `settings_check_failed`. (The `pk` action overrides both refusals, see the pick rules.)
4b. **Owner gate (new), the same function on every door.** It runs only after step 4 proved the presser is a creator or an administrator of that group (R1), and decides in this order:
    1. Creator: **in**, no further read, no extra call (the member record step 4 fetched is the proof).
    2. Administrator: read the switch (one database read, fresh: D-12; the read policy is plan-phase research's call, the contract is "the next press on any replica sees the change"). Unreadable: refuse with `settings_check_failed`. Switch **on**: **in**, no Telegram call.
    3. Administrator and switch **off**: the owner-state read below. Creator entry found who is not the presser: refuse with `settings_gate_owner_only` (alert) or the door's own gated text. Result usable and no creator entry: **in** (D-15, no live owner). Error, timeout or unusable result: refuse with `settings_check_failed`.
5. The control's right. New `settingsRightOwner` (live status creator, from the member record step 4 already fetched, no extra call): refusal alert `settings_access_owner_only`.
6. to 7. Apply, answer once, edit in place: unchanged.

#### The owner-state read (how "no live owner" is known; D-15, R6, R7)

A non-creator administrator's own member record does not show whether a creator exists, so the gate needs one extra
fact, and it pays for it only on the rare path.

| Property | Contract |
|----------|----------|
| Read | one live `getChatAdministrators` of the group, then a scan of the result for an entry whose status is `creator` |
| When it runs | only when the presser is a non-creator administrator AND the switch is off. A creator never makes it; an administrator in a group whose switch is on never makes it; a non-admin never reaches the gate. So only admins who are already being gated pay the call |
| Cost and bound | one Telegram call, bounded by a 3 s timeout (code constant, `settingsOwnerLookupTimeout`) that also bounds the press. Concurrent presses for one chat on one replica share one call in flight (a singleflight keyed by chat ID), so a burst of taps from several admins is one call, not many |
| Positive memo | an answer "an owner exists" (a creator entry that is not the presser) may be remembered per chat for at most 30 s in process memory (`settingsOwnerMemoTTL`), so an admin hammering a menu in a group that has an owner costs at most about two calls a minute per chat per replica. A memo can only keep an admin OUT, so a stale positive fails closed (an owner who just vanished keeps admins out for at most 30 s) |
| Never memoised | "no owner" (that answer lets a person in, so it is always read live), an error, a timeout and an unusable result. A group with no live owner therefore costs one call per gated press; that is the rare path of a rare path (switch off, no creator, an admin pressing) and the singleflight plus the 3 s timeout bound it. It is accepted |
| Creator is the presser | cannot happen on this path (a creator is step 4b.1); if the scan finds a creator entry whose user ID equals the presser's, the state is unusable and refuses |
| Unusable result | a result that does not contain the presser's own entry as an administrator (the presser was just proven an admin by step 4, so a list without them is stale or truncated) is unusable: refuse with `settings_check_failed`. An empty list is the same |
| Failure direction | unknown owner state ALWAYS refuses with `settings_check_failed`, never lets the admin in and never answers the gated-admin text (R6, R7) |
| Mechanism status | `getChatAdministrators` plus a creator scan is the mechanism this contract assumes. 10-CONTEXT.md lists "how a missing creator is recognised live without an extra Telegram call on every press" as an open item for plan-phase research, so the **outcomes** here (what is read, which way it fails, the refusal key, who pays) are binding and the **mechanism** may be refined there, provided the same outcomes hold |

Rules that hold for every refusal this phase adds (the checker's privacy dimension):

| # | Rule |
|---|------|
| R1 | A gate refusal is produced only after the presser's live status is proven to be creator or administrator of that group, so it tells no non-admin anything. It is never shown for a failed or unproven check. |
| R2 | No refusal, alert, notice, list text or hint contains a group title, a chat ID or the words "Staff Group", in any of the 8 languages. The refusals name no setting, switch or page (the in-menu alert says "the owner", never "Access"). |
| R3 | Where the presser is not proven an admin of the group named in the request (deep link, forged `c` in a pick), the answer is the same text and has the same effect whether the bot is in that chat or not, the chat is gone, or it is not a group. For the pick door this is spelled out in "The pick rules": every non-admin outcome and every Telegram client error (any 4xx, whatever its wording) at every step answers `settings_pick_unavailable`, the list stays, nothing is edited. For the deep link door the same class rule applies with its own text: every non-admin status and every Telegram 4xx at the `getChatMember` step answers `settings_start_not_admin`, and a 4xx or a non-group at the later `getChat` step answers it too; only failures that are not a client error (transport, timeout, 5xx, 429, unreadable answer) answer `settings_check_failed`, because none of them depends on the named chat. |
| R4 | The public group reply (`settings_refuse_owner_only`) never mentions the switch, the Access page or what an owner could do. |
| R5 | The empty-list text is one text for every user. It never changes with what the bot knows about the person. |
| R6 | When anything is unclear (unreadable switch, unknown right) the gate refuses. |
| R7 | An unknown owner state (the owner-state read failed, timed out or was unusable) refuses with `settings_check_failed`. It never lets the admin in (that would be fail-open) and never answers the gated-admin text (that would claim an owner exists). |

### The pick rules (private list, new action `pk`)

A pick is `settings|v1|a=pk&c=<group id>`: it goes through the whole press pipeline, so the live admin check, the
gate and the one `getChat` all run before anything is shown. On success the list message is **edited in place into
that group's Main page** (private menu, the opener's language, Groups button in the Back slot). The list message is
never deleted and never replaced by `settings_cannot_open`.

`c` is attacker-controlled (callback data is not authenticated), so a pick must not let anyone learn whether the bot is
in a chat. The pick therefore **overrides two Phase 9 mappings**: a non-admin presser gets `settings_pick_unavailable`
(not `settings_not_admin`), and every Telegram client error (any 4xx, a superset of the bot-missing errors) gets
`settings_pick_unavailable` (not the cannot-open edit). Order of
a `pk` press and what each step answers:

| Step | Condition | Answer | The list |
|------|-----------|--------|----------|
| 1 | `a` or `c` missing, extra key, `c` not a negative number | `common_callback_invalid_request` (before any I/O, no Telegram data involved) | stays as drawn |
| 2 | service identity | `lockdown_alert_post_as_yourself` | stays |
| 4 | the live `getChatMember` returns a status other than creator or administrator (member, restricted, left, kicked) | `settings_pick_unavailable` | stays |
| 4 | the live `getChatMember` returns a Telegram client error: any 4xx answer from Telegram (bad request, forbidden, chat not found, user not found, bot kicked, bot not a member, and any wording not listed here), whether or not `chat_status.IsBotMissingError` recognises its text | `settings_pick_unavailable` | stays |
| 4 | the live `getChatMember` fails without a Telegram client error: a transport error, a timeout, a 5xx, a 429 rate limit (it depends on load, not on the chat), or an answer that cannot be read | `settings_check_failed` | stays |
| 4b | the presser is a proven creator or administrator and the gate refuses (switch off with a live owner) | `settings_gate_owner_only` | stays |
| 4b | the presser is a proven administrator and the gate cannot decide (R7) | `settings_check_failed` | stays |
| after 4b | the one `getChat` returns a Telegram client error (any 4xx, same definition as step 4), or a chat whose type is not `group` or `supergroup` | `settings_pick_unavailable` | stays |
| after 4b | the one `getChat` fails without a Telegram client error (transport, timeout, 5xx, 429, unreadable answer) | `settings_check_failed` | stays |
| all pass | the gate lets the presser in and `getChat` shows a group or supergroup | the group's Main page replaces the list message | gone (it became the menu) |

Restated as the two rules the checker and the tests rely on:

- **Every Telegram client error (any 4xx answer) at step 4 and at the `getChat` step of a `pk` press returns
  `settings_pick_unavailable`, as does every non-admin status.** The mapping is by the error's class (a 4xx answer
  from Telegram), never by matching its wording: `chat_status.IsBotMissingError` recognises only three phrases ("bot
  was kicked", "bot is not a member", "chat not found"), and any real wording outside that set would otherwise be
  answered `settings_check_failed`, a difference that tells a forger whether the bot is in the chat (R3). Only
  failures that are not a Telegram client error (transport errors, timeouts, 5xx, 429 rate limits, unreadable answers)
  return `settings_check_failed`; none of those depends on the named chat. So a forged `c` naming a chat the bot is
  not in, a chat that is gone, a chat Telegram refuses in any wording, or a chat the bot is in where the presser is a
  plain member all produce the SAME alert text and the SAME effect: the alert, the list left exactly as drawn, no
  edit, no write, one answer.
- **A pick of a chat where the presser is a proven admin but the gate refuses (a row from before the switch was turned
  off) returns `settings_gate_owner_only`** and the list stays. That text is reachable only after step 4 proved the
  presser an admin of that chat (R1), so it discloses nothing to a non-admin; the bot's presence in that chat is
  already known to a person who administers it.

The rows are a hint (D-06): this is where a stale row is refused. The callback data is not authenticated by Telegram,
so `c` is treated as untrusted exactly as Phase 9 treats it; the pick adds no new trust.

### The list door

`/settings` typed in the bot's private chat sends the list as a new message (no reply quote; a private chat needs
none), in the user's language, built only from the bot's record for that user ID (a database read, no Telegram call).
It is shown even when the user has exactly one group (D-03). The list for a user is every group where the user is the
recorded owner, plus every group where the user is a recorded admin and the switch is on (or the group has no live
owner). Which rows exist is the repository's decision; this contract fixes how they look.

| Control | Contract |
|---------|----------|
| Row | one full-width button per group, the label is the group's title only (D-01). No icon, no role marker, no attention marker |
| Label | the stored title with line breaks and runs of spaces collapsed to one space, trimmed, cut at 32 runes with `…` appended when cut. An empty title shows the chat ID. Plain text (see Text Styling). 32 runes plus the ellipsis fits the full-width cell |
| Order | alphabetical by lower-cased title (code point order, not locale collation), ties by chat ID ascending (D-04). The order is stable between redraws |
| Duplicate titles | two groups can share a title and then their buttons look the same. Accepted (D-01 says title only): the pick opens a Main page whose group line shows the title and the chat ID, which is where the owner tells them apart |
| Page size | 8 rows per page (D-04) |
| Paging | one row after the groups. Page 1 of several: `[ Next ➡️ ]`. A middle page: `[ ⬅️ Prev \| Next ➡️ ]`. The last page: `[ ⬅️ Prev ]`. One page only: no paging row and no `Page` line. Buttons that would be dead are not drawn. The `Page {page}/{pages}` line sits above the keyboard (reused `staff_panel_page`) |
| Page value | the data carries the 1-based page number, at most 3 digits; a value past the last page is clamped to the last page; a value that is not a whole number of 1 to 3 digits is an invalid request (alert `common_callback_invalid_request`) |
| Navigation | `[ ✖️ Close ]` alone. This is what D-20 says once its recorded clarification (10-CONTEXT.md, D-20, 2026-11-04) is applied: "every page has Back" means every page of a group's menu, i.e. every page reached from that group's main menu. The list is the top level of the hub, not a page of any group, and has no parent to go back to (like the v1.0 main menu), so its navigation is Close only. Every page of a group's menu (Main, Staff Group, Lockdown, Captcha, Antiflood, Access) has a way back, and a private Main page's way back is `⬅️ Groups`, which returns to the list. Close deletes the message and, when the delete fails, edits it to `settings_closed` with no keyboard |
| Who can press | any press in the private chat; the list is rebuilt from the presser's own user ID (`query.From.Id`), never from the data, so a forwarded or replayed list button shows the presser their own groups, not the original user's |
| Returning | a private Main page's `[ ⬅️ Groups ]` redraws the list at page 1. The page the user came from is not remembered (accepted: the menu keeps no state) |

### Close and Back

Back always redraws the Main page; Cancel on a card returns to the page that asked. Close deletes the menu message.
On the Main page of a private menu the Back position holds `⬅️ Groups` (back to the list); on a group menu's Main
page Close stands alone. Every other page of a group's menu keeps `[ ⬅️ Back | ✖️ Close ]`, Access included, which is
D-20's "every page has Back" as clarified in 10-CONTEXT.md (every page of a group's menu). The private group list is the
top level of the hub, not a page of a group, so per that clarification its navigation is `[ ✖️ Close ]` alone, like the
v1.0 main menu (see the list's Navigation row). A gated admin's Close is
refused like any other press (step 4b): they can delete the message with Telegram's own delete.

### The Access switch (MENU-12, MENU-14, D-08 to D-11)

| Rule | Contract |
|------|----------|
| Who sees it | the live creator only: the Main button, the Main status line and the Access page are drawn only when the press's own member record (step 4) shows `creator`. No extra Telegram call. Everyone else, including an admin who is allowed in, sees nothing of it |
| Who can press it | the live creator only (`settingsRightOwner`, step 5). A forged press of an Access control by an allowed admin is refused with the alert `settings_access_owner_only` and changes nothing |
| OFF to ON | two taps (D-09): the toggle press draws the confirm card, Yes writes. The toggle press itself never writes ON |
| ON to OFF | one tap, writes at once (it only narrows access) |
| Card | the shared `settings_card.go` card: Yes carries the expiry minute `e` (unix minutes, five minutes ahead), expiry is lazy, no timer, no Redis key. An expired Yes redraws the Access page with `settings_card_expired` and writes nothing. Yes runs the whole press pipeline again, so the creator is re-checked live at Yes (and a presser who is no longer the creator gets `settings_access_owner_only` or `settings_not_admin`, nothing written) |
| Card buttons | the shared `settings_btn_yes` ("✅ Yes") and `settings_btn_no` ("❌ No") keys, kept as Phase 9 uses them. They are bare words on purpose: on a two-tap card the question text directly above them (`settings_access_confirm`) carries all the specificity ("Let the admins of this group change its settings?"), so Yes and No answer that question and a separate Access-specific label pair adds two keys for no gain |
| Asker | in a group menu only the opener can press anything (step 3), in a private menu only the person the private chat belongs to; so the asker needs no `u` of its own on the card |
| Wording audience | a group menu's text is readable by every member of the group, so no Access string addresses "you" or claims who can see the page: the Access strings speak of "the owner" and "admins" only, and are true read by anyone, in a group menu and in a private one |
| After a write | the Access page is redrawn from the apply function's returned value (not a re-read), showing the new state. No notice line on either flip, nothing is announced to the group, the Staff Group or the log channel (D-11) |
| Write failure | notice `⚠️ ` plus the existing `common_settings_save_failed` on the redrawn page, the stored state unchanged |
| Read failure | the Access page cannot read its row: the generic cannot-open edit (`settings_cannot_open_alert` plus `settings_cannot_open`), as Phase 9 D-11 |
| An open menu after OFF | the next press of an admin menu answers `settings_gate_owner_only` as an alert and edits nothing (D-10). The owner's menu is unaffected |
| No live owner | nobody is a creator, so nobody sees Access, and administrators are let in regardless (D-15, still a live `getChatMember` check on every press). How the gate knows there is no owner is the owner-state read in step 4b; if that read fails the admin is refused (R7), not let in |

One setting, one code path (D-19): the Access write is one apply function that holds the validation, the refusals,
the write and its `cache.DeleteCache`, and returns a typed result; the toggle, the Yes and any future command read
and write through it.

## Callback data (64-byte cap)

Built only with `encodeCallbackData` / `callbackcodec.Encode`, read only with `decodeCallbackData` (never `strings.Split`).
`settings|v1|` is 12 bytes. Worst case below: `c` = `-1001234567890` (14 characters with the sign), `u` = `1234567890`
(10 digits), `e` = `29800000` (8 digits), page `v` at most 3 digits. A test renders every new screen with these IDs and
fails on any omitted button (`Omitted` must stay 0).

New action codes (none clashes with `oh op bk cl tg st no ls ly ua uy lk pg`):

| Code | Meaning | Fields | Namespace |
|------|---------|--------|-----------|
| `pk` | pick a group from the private list; the list message becomes that group's Main page | `a`, `c` (private only) | `settings\|v1` |
| `ay` | Access Yes: write ON | `a`, the owner field (`c` in a private menu, `u` in a group menu, exactly one as the namespace requires), `e` | `settings\|v1` (a page action of the Access page, key `a`) |
| `lp` | list page `v` (Prev, Next, and the Groups button with `v=1`) | `a`, `v` | the list namespace |
| `cx` | close the list | `a` | the list namespace |

The Access page is registered as page key `a` (the existing keys are `s`, `l`, `c`, `f`) with control `s` (the switch).

The list namespace is the planner's call (research decision 16). **Recommended: a separate namespace** (for example
`shub`), because the list has no group and no opener, and `settings|v1` enforces "exactly one of `c` and `u`" before any
I/O, an invariant worth keeping untouched. The list buttons carry no group and no user ID (the list is rebuilt from
`query.From.Id`, and the namespace is accepted only on a message in a private chat). The bytes below assume a list
namespace prefix of at most 12 bytes (`shub|v1|` is 8).

| Button | Example data | Private bytes | Group bytes |
|--------|--------------|---------------|-------------|
| Pick a group | `settings\|v1\|a=pk&c=-1001234567890` | 33 | not used |
| Main grid button, Access open, Refresh | `settings\|v1\|a=op&c=-1001234567890&p=a` | 37 | 33 |
| Access toggle (ask ON or write OFF) | `settings\|v1\|a=tg&c=-1001234567890&p=a&t=s&v=1` | 45 | 41 |
| Access Yes (`a`, `c` or `u`, `e`) | `settings\|v1\|a=ay&c=-1001234567890&e=29800000` | 44 | 40 |
| Cancel the card | `settings\|v1\|a=no&c=-1001234567890&p=a` | 37 | 33 |
| Back, Close (existing) | `settings\|v1\|a=bk&c=-1001234567890` | 33 | 29 |
| List Prev, Next | `shub\|v1\|a=lp&v=999` | 18 | not used |
| Groups button (from Main) | `shub\|v1\|a=lp&v=1` | 16 | not used |
| Close the list | `shub\|v1\|a=cx` | 12 | not used |

Largest new button: 45 bytes (the private Access toggle), 19 bytes of headroom; the largest button of the whole menu
stays the Phase 9 private Turnstile choice at 53. A page value is capped at 3 digits, which is 7,992 groups; if a user
manages more, the last page is the limit (accepted). The Open in private button is still a URL, not callback data.

Rules: an encode that returns `""` is a bug; the renderer omits that button and logs at Error, and the worst-case test
fails. The pick and the list buttons must never carry a group's title, a user's name or the Staff Group (callback data
carries only numbers and codes).

### Per-locale length note

Measured on the 82 existing `settings_` keys of the repo's locale files (code points, translated divided by English,
strings longer than 8 characters): average ratio es 1.12, fr 1.12, pt 1.11, uk 1.10, ru 1.08, id 1.08, hi 1.01; the longest
single string reached 1.81 (uk), 1.70 (es), 1.67 (hi), 1.56 (fr, pt), 1.50 (id), 1.44 (ru), all on short labels. So:

| Language | What to expect | Strings to watch |
|----------|----------------|------------------|
| es, fr, pt | about 10 to 15 percent longer; fr and pt add articles and prepositions | `settings_btn_access_toggle` (state words "Activado" / "Désactivé" / "Desligado" are long; shorten the label part so the rendered button stays at most 40), `settings_access_confirm`, `settings_list_hint` |
| ru, uk | about 8 to 10 percent longer on sentences, but single words are long (Антифлуд, налаштування); the state words are short ("Вкл", "Увімк.") | the grid names (icon plus name at most 20), `settings_btn_access_toggle`: the literal rendering of the English ("Адміни можуть змінювати налаштування" is 36 characters before `: ` and the state, so about 47 with them) is over the 40 ceiling, so translate it shorter, for example "Адміни змінюють налаштування: ✅ Увімк." (38 characters rendered) |
| hi | the code-point count is close to English, but combining marks (matras) make the visible width about 20 percent wider than the count suggests; the existing hi locale mixes Devanagari with Latin transliteration | every label: check on a phone that a grid name and the toggle are not ellipsized |

Rule of thumb for the ceilings above: labels and short states "Other" is 1.5 times EN (the measured worst), sentences
1.4 times EN. For a button, the rendered limits (20 half-width, 40 full-width) are the real ones and override the
ratio, which is why `settings_btn_access_toggle` is held to 40 (not 1.5 times 36). Keep every alert at most 160
characters so a long translation still fits Telegram's 200.

## Notes for the planner (contract level)

- `settingsPage` needs a way to mark a page owner-only and anchored below the grid (a field such as `OwnerOnly`), and a
  main entry that can be hidden per press; the Access page is registered from its own file like any page (`registerSettingsPage`
  with page key `a`, control `s`, page action `ay`). The renderer change is `renderSettingsMain` (two columns, the status
  block, the Groups button, the Access row), which D-20 and CONTEXT list as changed code.
- Add `pk` to `settingsCheckFields` (exactly `a` and `c`, private message only) and to `dispatch`. At a pick the step-4
  non-admin status and every Telegram client error (a 4xx `gotgbot.TelegramError`, at `getChatMember` and at
  `getChat`, classified by status code and not by wording, so `IsBotMissingError`'s three phrases are a subset) answer
  `settings_pick_unavailable` and keep the list; it must not call `cannotOpen()` and must not use `settings_not_admin`
  for those cases. Only transport errors, timeouts, 5xx, 429 and unreadable answers answer `settings_check_failed`.
- The deep link handler (`settingsStartDeepLink`) classifies its two lookups like the pick does: a Telegram 4xx
  (`gotgbot.TelegramError` with a client status code) at `getChatMember`, and a 4xx or a non-group type at `getChat`,
  answer `settings_start_not_admin`; transport, timeout, 5xx, 429 and unreadable answers answer `settings_check_failed`.
  This replaces the `chat_status.IsBotMissingError` phrase check and the `settings_cannot_open` answer at that door;
  share one classifier with the pick so the two doors cannot drift.
- The gate is one function (the step 4b decision) shared by all five doors; the owner-state read (`getChatAdministrators`
  scan, 3 s timeout, per-chat singleflight, 30 s positive-only memo) lives behind a test seam. The binding part is the
  outcomes in "The owner-state read"; plan-phase research may replace the mechanism if the same outcomes hold.
- Extend the worst-case callback test, the page-fits-every-locale test (list page, empty list, Access, ON card, Main with
  the Access row, 8 locales) and `TestSettingsStaffPrivacy`; add a two-instance freshness test for the switch (D-12),
  and parity or drift tests for the Access write.
- **Required tests (contract level):**
  - Pick, same answer (R3): the alert text and the effect (list message not edited, nothing written, callback answered
    once) are identical for a presser who is a non-admin member in a chat the bot is in, a presser in a chat the bot is
    not in (bot-missing error at `getChatMember`), a chat that is gone, and a chat that is not a group or supergroup. All
    four answer `settings_pick_unavailable`. An unrecognised 4xx wording (a Telegram client error whose text
    `IsBotMissingError` does not match, for example a bad request with unusual wording or a 403 with a description
    outside the three known phrases) at `getChatMember`, and again at `getChat`, still answers
    `settings_pick_unavailable` with the same effect as the four cases above. A transport error, a timeout, a 5xx and a
    429 rate limit answer `settings_check_failed` at both the `getChatMember` and the `getChat` step. An admin presser whose gate refuses answers
    `settings_gate_owner_only`, and a proven admin whose gate cannot decide answers `settings_check_failed` (R7
    unchanged); in every case the list stays.
  - Deep link, same answer (R3): `/start settings_<id>` answers `settings_start_not_admin` with the same text and effect
    (no menu, no keyboard, nothing written) for a plain non-member of a chat the bot is in, a chat the bot is not in, a
    chat that is gone, and an unrecognised 4xx wording at `getChatMember` (a Telegram client error whose text
    `IsBotMissingError` does not match, for example a bad request or a 403 with a description outside the three known
    phrases): the reply is identical to a non-member's. At the later `getChat` step a 4xx and a chat that is not a group
    or supergroup also answer `settings_start_not_admin`. A 429, a transport error, a timeout and a 5xx answer
    `settings_check_failed` at both the `getChatMember` and the `getChat` step. A proven admin whose gate refuses still
    answers `settings_start_owner_only`, and a proven admin whose gate cannot decide answers `settings_check_failed`
    (R1, R7 unchanged).
  - Gate, owner-state read: creator makes no `getChatAdministrators` call; an admin with the switch on makes none; an
    admin with the switch off and a creator entry for another user is refused with the gated text; an admin with the switch
    off and no creator entry is let in; an error, a timeout, an empty list, and a list without the presser's own entry each
    refuse with `settings_check_failed` (never in, never the gated text); an unreadable switch refuses with
    `settings_check_failed`; two simultaneous presses in one chat make one call; a positive answer is remembered for
    at most 30 s and a "no owner" answer, an error and a timeout are never remembered.
  - Every door (group `/settings`, anonymous re-entry, deep link, press, pick) gives the same decision for the same
    member record and the same owner state.
- Run `make check-translations` first: `locales/uk.yml` is shorter than `en.yml` overall, but it already carries all 83
  Phase 9 `settings_` keys; this phase adds 19 keys and changes `settings_help_msg` in all 8 files. Whether to fill older
  uk gaps is the owner's call (STATE).
- Update `AGENTS.md` in the same commit: the locale count (8), the new callback codes and namespace, the gate step 4b and
  the owner-state read, the pick's neutral answers, the deep link's reclassification (the Handlers bullet for the `settings_` deep link still
  describes the Phase 9 three-phrase mapping and `settings_cannot_open` at `getChat`; it becomes the class rule: every 4xx
  except 429 at `getChatMember` or `getChat`, and a non-group chat, answer `settings_start_not_admin`), the Access table's
