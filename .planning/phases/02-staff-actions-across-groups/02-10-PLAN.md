<objective>
Close the lock half of verification Gap 2 (code review WR-02). The per-target lock alita:staff:lock:target:<id> has a fixed 30-minute TTL. A run slowed by long rate limits can outlive it, and a second Confirm on the same target can then start a parallel run, which defeats the restrict-replaces-ban protection the lock exists for. Plan 02-09 caps each wait at 60 s, but a run over many groups can still take longer than 30 minutes under sustained flood control.

## Phase Goal

**As a** staff member, **I want to** ban, mute or kick someone in every linked group at once, **so that** one command protects them all.

**This slice:** a slow run keeps exclusive hold of its target for as long as it runs, so two staff actions on one person never overlap.

<assumption_delta_decision>
Primary noun: target lock (alita:staff:lock:target:<id>). Decision: no-change. Rationale: there is still one lock per target with the card token as its value; this plan only renews its TTL while its run is alive. The "fallback" signal refers to plan 02-07's summary fallback, which this plan does not touch.
</assumption_delta_decision>

## Decisions taken here (Claude's discretion, recorded)

- Renewal lives in the coordinator's select loop (a second ticker next to the edit ticker), not in a new goroutine: the coordinator is already the run's single long-lived goroutine, and the lock's life then ends exactly with the loop.
- Renewal stops when the fan-out ends. The lock guards the group writes, and none happen during the final delivery, which can take a few minutes under flood control (plan 02-08). The last renewal leaves at least 20 minutes of TTL, and the release still runs after delivery.
- A vanished key (Redis restart or flush mid-run) is re-taken with the run's token, because nobody else can hold it at that moment: a second card's Confirm would have stored its own token. This narrows the window in which a second run could start. A lock that holds another token is only logged; the run is not cancelled, because cancelling mid-fan-out would leave groups half-done for no safety gain once both runs are already writing.
- Interval: 10 minutes, a third of the 30-minute TTL, so two renewals can fail in a row before the lock expires.

## Assumptions recorded (flagged, spec-less fallback)

- PLAT-01 (unclassified edge, flagged rather than resolved): the renewal and the pacer refusal are shared through Redis, so every replica sees the same lock TTL and the same block. During a rolling deploy, a replica still on the old binary keeps sleeping through a block above MaxWait and does not renew its locks until it is replaced. This is accepted for the deploy window: there is one owner, deploys are short, and the 30-minute TTL still covers ordinary runs.
