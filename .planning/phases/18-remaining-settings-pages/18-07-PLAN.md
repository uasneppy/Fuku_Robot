- Execution rules, the golden technique, the reader rule and `$SCRATCH` as 18-01's planner assumptions say. The Main-shape constants become `s|l / c|f / n|w / g|r / m|d / t|u / a / close` and 8 rows.
- The menu's own language (research S-04): `newSettingsPress` sets `p.tr` from `ctxTr(ctx)`, which is the group's language for a callback in a group and the presser's own in a private chat. After a successful write in a **group** menu, the control replaces `p.tr` with `i18n.MustNewTranslator(code)` built from the code it just wrote (never re-read: another replica's local layer may still hold the old value), then renders; in a private menu `p.tr` is not touched. `settings_pages.go` is not edited for this (the control's `Set` owns the press, D-03).
- A press of the stored language writes nothing and shows no notice: the page compares its before-read with `v` and calls no apply function then (A18-A17); `lang.ChangeGroupLanguage` is a no-op for an equal value anyway.
- The success notice is the callback's own text, `language_changed_group`, built exactly as the callback builds it (`tr.GetString("language_changed_group", i18n.TranslationParams{"s": keyboard.GetLangFormat(code)})`), in the redrawn language. The cells are `language_flag`, a space and `language_name` of each language's own locale file (flag first, as the UI-SPEC draws them), and the stored one `✅`, a space and its name (M36); the `/lang` keyboard's translate URL button is not drawn.
- Skew: `chat_lang`, `chat_settings` and `chat` are not in `skipLocal`, so another replica can answer in the old language for up to `CACHE_LOCAL_TTL`, exactly as after `/lang` (C-14, accepted).
