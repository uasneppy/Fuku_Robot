## Phase Goal

**As a** group owner, **I want** Telegram's service messages and the bot's own messages removed on a schedule I set, **so that** the chat stays readable.

After this plan the code knows which service messages exist and which are deletable, which five kinds of its own messages can be scheduled, what a stored rule means for each (the effective rule, with the shared /cleanservice flag), and has one write path for every rule. No update is acted on yet.

<objective>
Add the kind tables with their predicates and presets, the effective-rule function, `applyDeleteRule`, `applyCleanServiceRule` and the `/cleanservice` apply function, with the reflect coverage test that keeps the table honest across gotgbot upgrades (D-02, D-03, D-04, D-11, D-16, D-18, D-21, D-26; research S-02, S-03, S-06 "Apply functions").

Purpose: the watcher (16-03), the hooks (16-05, 16-06) and the page (16-08) all read these tables and call these functions; building them first, with pure tests, keeps each of those plans thin.
Output: two new production files, one edited production file (the `/cleanservice` toggle), three test files.
</objective>

Never deleted and never offered: `GroupChatCreated`, `SupergroupChatCreated`, `ChannelChatCreated`, `MigrateToChatId`, `MigrateFromChatId`, `ForumTopicCreated`.
- `deletionServiceKindOf` answers for joined and left too (they are rows of the table); who handles them is the watcher's and `cleanService`'s business (plan 16-03), not the table's.
- The stored-state comparison of `applyDeleteRule` ("a press of the stored state writes nothing") is judged on the cached loader (the key is in `skipLocal`, so another replica is not behind); a failed read before the write is a save failure with no write.
- Joined and left share ONE flag (`greetings.clean_service_settings`, D-02), so they are coupled by design: with the flag off both read Keep; a Now or After N on either row turns the flag on and the OTHER row then reads its own stored delay, or Delete now when it has none. This is D-02 as written, not a planner choice, and the matrix test pins it. The planner's one refinement inside D-02 is that Keep removes BOTH delay rows (research Open Question 1, settled by D-26 for the command): with the flag off the rows mean nothing, and a stale delay must never come back at a later Now. Flagged in the SUMMARY and in 16-SPIKE.md for the owner.
- `/cleanservice on` therefore means "flag true, both delay rows removed" and `off` means "flag false, both rows removed" (D-26); the command's replies, rights (`CanUserChangeInfo`) and `connectBotAdmin` behaviour are untouched. The read side of the command still uses `greetings.GetGreetingSettings`.
- Apply results follow the shape of `greetingApplyResult` and the shared `applyReadBack` generic of `greetings.go` (an outcome, the value read back, the error): the write error is logged with the chat ID and returned, a failed read-back after a stored write is logged and the outcome stays applied with an empty value so the caller reloads.
- dupl and gocyclo: the two table builders are plain composite literals; the predicate of `so` is one `||` chain split over a helper per ten fields so that no function passes 19 branches; the lint stand-in names any clone.
- Failure injection never uses DDL: no test drops, recreates or alters a table, because CI runs all of `fuku/modules` in one shared database where a drop can fail on a foreign key or break a later test. The seams of this plan (`deletionRulesLookup`, `deletionRuleWrites`, `deletionFlagLookup`) and the transaction hook of plan 16-01 are how a test makes a read or a write fail; plans 16-03, 16-04 and 16-08 reuse them.
- Test hygiene: every test uses a fresh chat ID from `uniqueModuleChatID()`, deletes its rule rows, greetings rows and the `delete_rules:<chat>` and `greetings:<chat>` cache keys in `t.Cleanup` and calls `dbcache.ResetLocalForTest()`; none skips a case or calls `t.Parallel`.
