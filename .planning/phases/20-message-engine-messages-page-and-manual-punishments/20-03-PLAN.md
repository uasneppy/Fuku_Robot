## Phase Goal

**As a** group owner, **I want** to set what the bot says in a group when an admin bans, kicks, mutes, unbans or unmutes someone, from that group's settings in the bot's private chat, **so that** the replies sound like my community, while a group that sets nothing sees no change.

After this plan the v1.1 message editor can edit any message a later page defines, not only Welcome, Goodbye and Rules, with no change to those three pages.

<objective>
Parameterise the message editor (D-20, the phase's main design question). An event message is one of many messages edited from one page, so the editor gains: a new kind `settingsEditEvent`, a definition registry outside the three built-in pages (`registerSettingsEditDef`), function hooks for the five places that today branch on Welcome, Goodbye or Rules (load, remove, write a typed part, draw, preview), extra callback fields that every editor button carries (the Messages page's `k`, the event code), the bot's own reserved buttons in the button check, and `settingsEditResolvedActions`, the five actions of a page that resolves its message from a press's fields.

Design (fixed here for plans 20-06 to 20-09):
- The wait's `p` is the definition's `Key`; an event definition's key is `h` + the event code + the destination code (`hbng` for the ban message of the group), so it never collides with a one-letter page key and Phase 21 adds `hbnp` with no change. The wait's `t` stays the part code (`x`, `m`, `b`), so every part-level path of the editor (state words, the check, the prompt's limit) is unchanged.
- A definition's `Fields` (the Messages page uses `{"k": <event code>}`) are added to the editor's action buttons only, never to Back, Close or the navigation row, so the core actions' field allow-lists are untouched.
- No new handler group, no new door: a hooked definition's typed reply goes through the editor branch of the door (`authorize(def.EditRight)`, the check, the claim, `Write`, the saved page, the prompt closed).

Purpose: the Messages page (plans 20-06 to 20-09) builds one definition per event from a table, so later phases add events as table rows with no editor edit.
Output: the editor changes, one new test file.
</objective>

## Planner assumptions (flagged)

- The hook signatures (all optional except `Load` and `Draw`, which `registerSettingsEditDef` requires):
  `Load func(ctx context.Context, chatID int64) (settingsEditState, error)`;
  `Remove func(ctx context.Context, chatID int64, part string, by int64) (greetingApplyOutcome, *settingsEditState)`;
  `Write func(ctx context.Context, chatID int64, part string, verdict settingsEditVerdict, by int64) bool`;
  `Draw func(v settingsView, def settingsEditPageDef, st settingsEditState, opts settingsEditScreenOpts) settingsScreen`;
  `Preview func(p *settingsPress, def settingsEditPageDef, st settingsEditState, part string) error` (part `""` is Full preview);
  `PreviewHeaderKey string` (empty keeps the greeting header).
- `isGreeting()` becomes `Kind == settingsEditWelcome || Kind == settingsEditGoodbye` (today `Kind != settingsEditRules`, the same for the three pages), so an event's text is previewable only once it is set and Main's On/Off branch never applies to it. An event's `Load` sets `TextIsDefault = Text == ""`, so `settingsEditPartIsSet` and `settingsEditStateWord` need no change (an unset event text reads `settings_state_default`).
- The text check of an event is the greeting text check (the commands' conversion, buttons in the text refused, 4096 or 1024 with media, the Welcome placeholders filled for the worst-case member; event placeholders such as `{reason}` are left as typed, D-21), with `ReservedButtons` added to both button counts.
- A hooked definition whose `Preview` is nil answers Preview and Full preview with `settings_edit_preview_failed` (an error from `settingsEditPreviewSend`), never with the greeting preview.
- `registerSettingsEditDef` panics at init on an empty key, a key equal to a built-in page's key, a duplicate key, a nil `Hooks` or a nil `Load` or `Draw`; it never checks the settings page registry (init order across files is not fixed).
- AGENTS.md is not edited here, so this plan can run in wave 1 beside 20-02 (which edits AGENTS.md): the hooks have no production user until plan 20-06 registers the first event definitions, and 20-06 documents them in the message editor bullet in the same commit (D-25).
- The test-only page follows `withTestSettingsList` (`fuku/modules/settings_list_env_test.go` line 199): it saves and replaces the registry entries of its page key and action codes and restores them in `t.Cleanup`, never `registerSettingsPage`. Test codes `qs qr qc qv qf` and page key `qt` are unused by every real page and test page (the list test page uses `zg zx zy za zc`, `TestSettingsPageActionValidate` registers `zv` and `zw`, the Timezone page owns `zo` and `zk`).
