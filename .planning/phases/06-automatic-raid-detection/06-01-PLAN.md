## Phase Goal

**As a** group admin, **I want to** have raids detected and locked down automatically, **so that** my group is protected when no admin is online.

**This slice:** a burst of joins locks the group with no admin online, and the Staff Group sees why.

## Decisions taken here (Claude's discretion, recorded)

- One migration holds the whole schema of the phase, written once: `chat_raid_detection` (no foreign key on chat IDs, the lockdown precedent), the three trigger columns on `chat_lockdowns`, the `(chat_id, lift_started_at)` index the D-15 cooldown reads, and the D-03 carry-over. The carry-over clamps with `LEAST(GREATEST(auto_antiraid_threshold, 3), 500)`: D-18 raises a value below 3 to 3, and an old value above 500 (which `/autoantiraid` allowed) becomes 500 so the copy satisfies the table's CHECK and the migration cannot abort startup.
- The model carries no `default:` tag on its booleans (a Go false would be dropped by GORM Create and the SQL default would turn the trigger back on); the defaults live in Go (`raiddetection.Defaults`) and in the SQL `DEFAULT`s.
- `trigger_kind` is `join_surge` or `flood`; `reason` stays empty for an automatic lockdown, and the trigger numbers are columns (`trigger_count`, `trigger_window` in seconds, `trigger_percent`) so every destination renders its own language (D-21). The alert's trigger lines for both kinds are added here because they share one renderer; the flood trigger itself lands in plan 06-03.
- Redis keys: a new operational family `alita:raid:{<chat>}:<part>` with a hash tag on the chat ID (cluster-safe multi-key scripts). `joined` is a sorted set, member = user ID, score = latest join in unix ms, so the chat_member update and the service message of one join collapse into one member (research Pattern 4); the Phase 5 tracker is left as it is because its JSON members double count.
- The trigger runs synchronously in the join handler (research Pattern 6): no goroutine, no drain. A crash mid-sequence leaves an unconfirmed row that the worker's settle step already resolves.
- The fire latch `alita:raid:{<chat>}:fire` (SET NX EX 60) is load shedding only; exactly one lockdown is still `uk_chat_lockdowns_active` plus `lockdown.Start` (plan 06-05 tunes the latch per outcome and adds the cooldown).
- The chat_member path is wired here; the service-message path, the shared input builders and every exemption test land in plan 06-02. The counting rule itself (`raidJoinCounts`) is complete here.
- The settings read goes through `cache.GetFromCacheOrLoad`; the `skipLocal` entry and the writes come with `/autolockdown` in plan 06-04 (D-12 is about changes reaching every replica).
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`. No PostgreSQL server is available, and executors must never start one by any means; the migration is proven on PostgreSQL in CI (migration chain, and the carry-over test of plan 06-10).
