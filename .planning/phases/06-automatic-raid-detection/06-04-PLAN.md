<objective>
The second trigger. A message watcher at the unused handler group -4 (after the join guard and fed-ban, before aispam, antiflood, locks and blacklists, so a message they later end was already counted) adds each countable item to three Redis sorted sets in one Lua call: all items, items from members who joined in the last 24 hours (the joined set of plan 06-02), and those members' IDs. When a 30-second window holds at least the threshold, at least 60% of it new-member items, from at least 3 new accounts, the bot locks the group through raidFire.

Task 1 is the end-to-end path: a flood from recent joiners locks the group and its alert names the flood. Task 2 pins what never counts and what does not trip the rule.

Purpose: ROADMAP Phase 6 criterion 2, RAID-02, RAID-07, D-05 to D-08.
Output: raid_flood.go, the -4 registration, AGENTS.md rules, tests.
</objective>

## Phase Goal

**As a** group admin, **I want to** have raids detected and locked down automatically, **so that** my group is protected when no admin is online.

**This slice:** a flood from freshly joined accounts locks the group; a busy chat among old members does not.

## Decisions taken here (Claude's discretion, recorded)

- Handler group -4 (research Pattern 2): unused, after -7/-6/-5 and before 3/4/5/6/7. The watcher returns `ext.ContinueGroups` on every path and is registered inside `LoadLockdown` (one module, one help page).
- What counts (research Pitfall 4, A6): user content of any kind, since "messages" covers it: text that is not a command (first entity a bot_command at offset 0), photo, animation (checked before document), sticker, video, video note, voice, audio, document, poll, contact, location, venue, dice and story. Forwards and replies count. An album counts once (item key `g:<media_group_id>`, otherwise `m:<message_id>`). Service messages (new members, left member, pins, title or photo changes, migrations) never count. Edited messages and channel posts never reach the handler (gotgbot defaults), and neither do bot senders.
- Exemptions are checked cheapest first (research Pitfall 3): supergroup, item key and sender shape (no sender, `sender_chat` set, automatic forward, a Telegram service ID from `staffServiceUserIDs`, the bot), then Redis, then the settings read (flood off returns), then `chat_status.IsApprovedForUpdate`, then the cached admin check `antifloodModule.userIsFloodExempt` (D-07 accepts the cached list; its bounded live fallback assumes admin when saturated, which only lowers counts).
- Redis keys in the plan 06-02 family: `alita:raid:{<chat>}:fi` (items), `:fn` (new-member items), `:fa` (new-member account IDs), each a sorted set scored in unix ms, trimmed to 30 s and capped at 2000 on every write, PEXPIRE 2 minutes. The script reads `:joined` with ZSCORE; a member scored within 24 h is "recently joined". The windows, the 60% and the 3-account floor are code constants (CONTEXT defers configurable windows).
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`. No PostgreSQL server is available; never start one.
