<objective>
One raid, one lockdown. Several triggers firing at once, in one replica or across replicas, already end in one lockdown because `lockdown.Start` inserts behind the `uk_chat_lockdowns_active` partial unique index and Phase 5's `BeginAlert` decides one alert; this plan proves it end to end and makes the trigger cheap around it: a trigger that finds a lockdown active stays silent before any Telegram call, a group lifted less than 10 minutes ago is left alone, and the fire latch lasts according to the outcome.

Task 1 is the end-to-end proof: two triggers and two replicas give one lockdown and one alert, and every start outcome is pinned. Task 2 adds the post-lift quiet period and the latch per outcome.

Purpose: ROADMAP Phase 6 criterion 4, LOCK-10, D-14 (nothing started when the bot cannot lock), D-15.
Output: lockdown.RecentlyLiftedFresh, raidFire's checks and latch lengths, tests.
</objective>

## Phase Goal

**As a** group admin, **I want to** have raids detected and locked down automatically, **so that** my group is protected when no admin is online.

**This slice:** whatever fires, on whichever replica, the group gets one lockdown and one alert, and a lifted group is not locked again at once.

## Decisions taken here (Claude's discretion, recorded)

- raidFire's order after the latch: `lockdown.GetActiveFresh` (an active row, confirmed or not, means silence; a read error shortens the latch and returns), then `lockdown.RecentlyLiftedFresh(chat, time.Now() - raidLiftQuiet)` (true means silence; an error shortens the latch and returns, research A10), then `startLockdownRow`. The quiet period reads `lift_started_at` from PostgreSQL, so it survives a Redis flush and needs no code on the lift path (research Architectural Map). It uses real time, not `raidNow`, because `lift_started_at` is written with real time.
- Latch per outcome (research Pitfall 11): Started, AlreadyActive and LockUnknown keep the 60-second latch (the worker settles an unknown lock); BotCheckFailed, PermissionsUnreadable and StateFailed shorten it to `raidRetryLatch` (10 s) with PEXPIRE; NotSupergroup, BotCannotRestrict and LockFailed lengthen it to `raidCantLockLatch` (10 minutes). Plan 06-06 adds the notice and the warning at the same switch.
- The latch is never the correctness mechanism; the concurrency tests also run with the latch removed and prove the database alone gives one lockdown.
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`. No PostgreSQL server is available; never start one. The partial unique index is already proven on PostgreSQL by `TestStartLockdownOneActivePerChat` and the alert gate by `TestBeginAlert` in `make test-postgres-integrity`.
