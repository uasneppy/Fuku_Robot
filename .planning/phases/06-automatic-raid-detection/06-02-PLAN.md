<objective>
The first end-to-end slice of the phase: a join surge locks a supergroup on its own. Both join deliveries already pass the group -7 guard; the chat_member path now records each counted join in a Redis sorted set keyed by user ID, and when 15 distinct accounts joined within 60 seconds the bot starts the same lockdown /lockdown starts, through plan 06-01's `startLockdownRow`, with the bot as starter and the surge's numbers on the row. The existing worker then posts the Phase 5 alert, whose trigger line (plan 06-01) names the join surge and its count.

Task 1 is the tracer: settings table, counter, hook, trigger, lock, alert. Task 2 pins the settings read: defaults, a stored threshold, an off switch.

## Phase Goal

**As a** group admin, **I want to** have raids detected and locked down automatically, **so that** my group is protected when no admin is online.

**This slice:** a burst of joins locks the group with no admin online, and the Staff Group sees why.

## Decisions taken here (Claude's discretion, recorded)

- This plan's migration creates `chat_raid_detection` (no foreign key on chat IDs, the lockdown precedent) and carries the old thresholds over; plan 06-01's migration already added the trigger columns and the quiet-period index. The carry-over clamps with `LEAST(GREATEST(auto_antiraid_threshold, 3), 500)`: D-18 raises a value below 3 to 3, and D-22 lowers a value above 500 (which `/autoantiraid` allowed) to 500 so the copy satisfies the table's CHECK and the migration cannot abort startup.
- The model carries no `default:` tag on its booleans (a Go false would be dropped by GORM Create and the SQL default would turn the trigger back on); the defaults live in Go (`raiddetection.Defaults`) and in the SQL `DEFAULT`s. The cached read uses `cache.DefaultCacheTTL`.
- An automatic lockdown has `trigger_kind` join_surge (flood comes in plan 06-04), an empty `reason`, and its numbers in the trigger columns (D-21); the alert's trigger line for it is plan 06-01's.
- Redis keys: a new operational family `alita:raid:{<chat>}:<part>` with a hash tag on the chat ID (cluster-safe multi-key scripts). `joined` is a sorted set, member = user ID, score = latest join in unix ms, so the chat_member update and the service message of one join collapse into one member (research Pattern 4); the Phase 5 tracker is left as it is because its JSON members double count.
- The trigger runs synchronously in the join handler (research Pattern 6): no goroutine, no drain. A crash mid-sequence leaves an unconfirmed row that the worker's settle step already resolves.
- The fire latch `alita:raid:{<chat>}:fire` (SET NX EX 60) is load shedding only; exactly one lockdown is still `uk_chat_lockdowns_active` plus `lockdown.Start` (plan 06-06 tunes the latch per outcome and adds the cooldown).
- The chat_member path is wired here; the service-message path, the shared input builders and every exemption test land in plan 06-03. The counting rule itself (`raidJoinCounts`) is complete here, and the counter hands the performer status it read to the guard, so a join keeps making at most one live lookup (the existing "a performer whose live lookup fails" case of lockdown_paths_test.go pins exactly one).
- The settings read goes through `cache.GetFromCacheOrLoad`; the `skipLocal` entry and the writes come with `/autolockdown` in plan 06-05 (D-12 is about changes reaching every replica).
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`. No PostgreSQL server is available, and executors must never start one by any means; the migration is proven on PostgreSQL in CI (migration chain, and the carry-over test of plan 06-11).
