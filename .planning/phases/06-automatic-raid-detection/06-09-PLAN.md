<objective>
A flood alert names the flood. When the flood trigger fires, the recently joined accounts that posted in the window are copied, with their join times, into a short-lived snapshot key; when the worker decides the alert it saves them, named from the users table, as the lockdown's burst rows beside the 10-minute tracker's joins. The alert's sample then lists them and "Ban N recent joiners" can ban them, through Phase 5's unchanged ban run.

Task 1 is the end-to-end path: the flooders are on the alert. Task 2 proves the Ban button bans them and pins the edges (surge alerts unchanged, a lost snapshot, unknown names).

Purpose: D-17 (owner amendment), research Pitfall 10, RAID-02 with LOCK-11 and LOCK-12 kept for the flood trigger.
Output: the flooders snapshot and lookup, the flood branch of lockdownBurstSnapshot, the flood counts line, FindUsersByIDs, tests.
</objective>

## Phase Goal

**As a** group admin, **I want to** have raids detected and locked down automatically, **so that** my group is protected when no admin is online.

**This slice:** after a flood lockdown, staff see the flooding accounts on the alert and can ban them with one tap.

## Decisions taken here (Claude's discretion, recorded)

- Snapshot at fire time (research Pitfall 10, D-17): raidFire, for a flood trigger, after the latch, the active check and the quiet period and before startLockdownRow, runs `raidFloodersScript` once: delete `alita:raid:{<chat>}:flooders`, take the newest members of `:fa` (at most `raidFloodersMax` = 500), keep each whose `:joined` score is within 24 h, store it scored by that join time, PEXPIRE `raidFloodersTTL` (15 minutes, which covers the settle path's one-minute grace). A failed snapshot is logged at debug and the lockdown still starts.
- The worker reads the snapshot in `lockdownBurstSnapshot` only for a lockdown whose trigger_kind is flood, through the seam `raidFloodersLookup` (no Redis: nothing, no error). The flooders are merged with the tracker's joins by user ID (the tracker's entry wins for name, username, link and bot flag; the earliest time wins), named from the users table with one `user.FindUsersByIDs` query (a failed read leaves the names empty and still saves the rows), and saved as `pre` burst rows by `lockdown.BeginAlert`'s winner, so the CHECK on `source` needs no migration and the ban run, the link line and the counts read them unchanged. The bot's own ID is skipped.
- A flood alert's counts line uses `lockdown_alert_counts_flood` (same placeholders as `lockdown_alert_counts`); `lockdownRenderSample` takes the trigger kind.
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`. No PostgreSQL server is available; never start one.
