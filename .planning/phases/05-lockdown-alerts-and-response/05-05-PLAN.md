<objective>
An admin of the locked group cleans up the raid with one button. "Ban N recent joiners" on the alert bans the whole burst for good: the accounts that joined in the 10 minutes before the lock and every joiner the lockdown recorded, except live admins, approved users and the bot. The run is DB-driven like the rest of the lockdown: a confirm card starts it, the worker executes it through the lockdown pacer, each account's live status decides its call, and the card reports the result. A joiner banned this way stays banned through the lift.

Task 1 is the end-to-end path: button, card, run, permanent bans, result. Task 2 makes it safe beside the Phase 4 worker and the lift, and keeps the counts honest.

## Phase Goal

**As a** group admin or staff member, **I want to** get a lockdown alert with one-tap fixes, **so that** we can see a raid and clean it up fast.

**This slice:** one press bans the raid's accounts for good, and the lift does not let them back.

## Decisions taken here (Claude's discretion, recorded)

- The run is DB-driven (research F3: the staff run engine is bound to linked groups, the Redis card and the staff pacer). Confirm inserts a `chat_lockdown_ban_runs` row; the partial unique index `(lockdown_id) WHERE state = 'running'` makes a second concurrent run impossible, the same idiom as `uk_chat_lockdowns_active`. The worker executes queued accounts in batches; the replica whose conditional finish wins edits the card.
- Confirm copies the joiner rows into `chat_lockdown_burst` (source joiner, `INSERT ... SELECT ... ON CONFLICT DO NOTHING`) and queues every burst row still unhandled (state '') that is not an approved user or the bot. Approved users and the bot are simply never queued; approval is re-checked fresh before each account.
- D-22 (owner, refines D-09): a joiner the lockdown recorded as exempt (let in by a live creator or administrator, or an anonymous admin, Phase 4 D-07/D-24) is never banned. Exempt is known before any call, so `CountBanCandidatesFresh` leaves those joiners out of N, and `StartBanRun` marks their burst rows skipped with reason `let_in` for the run in the same transaction (no Telegram call), so the result reports them. Because the chat_member path can turn a pending row exempt after the run was queued (Phase 4 D-24), each account's joiner row is read fresh again before its call, and an exempt one is skipped with `let_in` without a claim or a call.
- Approved users are read through a new uncached `approvals.ListApprovedIDsFresh` that returns its error, because the cached `IsUserApproved` turns a failed read into "not approved", which would ban. A failed read refuses the Ask and makes the run wait for the next cycle.
- The joiner row is claimed (its current state to acting) before the Telegram call and moved to `kept` with detail `response_ban` after a permanent ban (research Pattern 5). That claim is what keeps the worker's marker ban and the lift's unban away from the account; `kept` is final, so FinishLift never waits on it and the lift never unbans it. On a skip, a failure or a rate limit the joiner row goes back to the state it came from. Rows held by someone else (acting, unbanning) put the account back in the queue without an attempt.
- The ban sends no `until_date` (permanent: Telegram treats an absent or over-366-day date as forever) and Telegram also deletes the account's messages in a supergroup, which the confirm card says. A declined join request is banned the same way (D-21) and its burst row is marked with reason `request` for plan 05-06's report.
- While the lockdown is no longer active the run is left untouched; plan 05-06 stops and reports it.
