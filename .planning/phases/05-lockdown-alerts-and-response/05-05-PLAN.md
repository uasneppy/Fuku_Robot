<objective>
Remember who joined each group recently, so a manual lockdown's alert can name the accounts that got in just before the lock (D-02 as amended by D-17). The two group -7 join handlers write every supergroup join into a dedicated 10-minute Redis tracker with one pipelined round trip, best effort and bounded in time; a snapshot read returns each user once for a window. Plan 05-07 saves that snapshot with the lockdown when its alert is decided and shows it.

Task 1 is the path from a join update to a snapshot entry. Task 2 pins the tracker's limits and proves the guard is unchanged.

Purpose: ROADMAP Phase 5 success criterion 1 ("a sample of the accounts that joined during the burst"), LOCK-11, D-02, D-17.
Output: lockdown_recent.go, the guard hooks, a test file, AGENTS.md rules.
</objective>

## Phase Goal

**As a** group admin or staff member, **I want to** get a lockdown alert with one-tap fixes, **so that** we can see a raid and clean it up fast.

**This slice:** the bot keeps the last 10 minutes of joins of every group, so the raid's first accounts are not lost when an admin locks the group a few minutes in.

## Decisions taken here (Claude's discretion, recorded)

- Key `alita:lockdown:recent:<chat>`: a sorted set scored by join time in unix milliseconds, member a compact JSON `{i: id, n: name, u: username, b: bot, l: link}`. One pipelined round trip per join: ZADD for each user, ZREMRANGEBYSCORE older than 10 minutes, ZREMRANGEBYRANK keeping the newest 500, EXPIRE 700 s, under a 250 ms timeout (research Pattern 9). The key is in the operational `alita:lockdown:*` family, outside `alita:cache:`, so `CLEAR_CACHE_ON_STARTUP` keeps it. Antiraid's 60-second list is not used (D-17).
- Join requests are not tracked: a request is not a join. The bot's own join is not tracked.
- Deduplication across the two join paths happens at read time by user ID (the earliest join time wins; a non-empty link, name or username fills in), because the chat_member path carries the invite link and the service message does not.
- The snapshot read is a package variable (`lockdownRecentLookup`) so tests can make it fail, in the style of Phase 4's seams.
- This plan touches no alert code, so it runs beside plan 05-04 in wave 4 (it waits for plan 05-03 only because both edit AGENTS.md).
