<objective>
A lockdown nobody lifted keeps reminding staff. Every hour after the alert, the worker posts a short reminder into the alert's destinations with fresh counts and the same three buttons; the previous reminder loses its buttons so only the newest and the original alert stay pressable; reminders stop at the lift and every copy is closed then.

Task 1 is the hourly cycle of reminder copies. Task 2 is what a reminder says and does, and where it goes.

Purpose: ROADMAP Phase 5 success criterion 5, LOCK-14, D-15, D-16.
Output: reminder slots in alerts.go, the reminder step and text in lockdown_alert.go, the worker hook, a test file, locale keys, AGENTS.md rules.
</objective>

## Phase Goal

**As a** group admin or staff member, **I want to** get a lockdown alert with one-tap fixes, **so that** we can see a raid and clean it up fast.

**This slice:** a lockdown nobody lifted comes back to the top of the Staff Group every hour.

## Decisions taken here (Claude's discretion, recorded)

- A reminder is a copy row of kind `reminder` with `seq = floor((now - alert_started_at) / lockdownReminderEvery)`, inserted with `ON CONFLICT DO NOTHING` on the existing slot key, so exactly one row exists per reminder and destination whichever replica plans it, and the existing poster, claims, retries, stale release and close step handle it (research Pattern 3). Counting from `alert_started_at`, not `locked_at`, means lockdowns older than this phase do not fire a burst of catch-up reminders. Only the current seq is ever planned.
- A pending reminder whose seq is behind the current one is not posted (marked failed with detail "superseded"), so a long outage never posts a stale reminder.
- "The same destinations as the alert" (D-15) is read as the alert's destination kinds, each resolved again when the reminder is planned: the Staff Group only while the group is still linked (to its current Staff Group), the log channel only while it is set with its admin category on. A Staff Group that was unlinked since gets no reminder, and a kind the alert did not go to gets none.
- The previous reminder in a destination loses its buttons through plan 05-12's sync step (`buttons_live` false, `edit_pending` true); the original alert keeps its buttons until the lift (research Pattern 3 interpretation of D-15 with D-12).
- The reminder carries the invite link line (D-13 format) when a link is known, because it carries the Revoke button and LOCK-14 makes it a re-post of the alert; it never carries the sample (D-16).
- `lockdownReminderEvery` is a package variable (`time.Hour`) so tests can age the alert instead of sleeping.
