<objective>
The policy and safety core of "Ban N recent joiners", before any button reaches it. One function decides and bans one account of the burst: the live status decides the call through a pure decision table, approved users, the bot and joiners an admin let in are skipped, and a joiner-backed account claims its joiner row first so the Phase 4 worker and the lift can never overwrite or undo the ban. The ban run's storage (one running run per lockdown, the queue, the finish and the tally) is added here too. Plan 05-10 puts the button, the confirm card and the worker loop on top.

Task 1 is the decision and the per-account ban. Task 2 proves it is safe beside the worker and the lift and keeps the counts honest. Task 3 is the run storage.

## Phase Goal

**As a** group admin or staff member, **I want to** get a lockdown alert with one-tap fixes, **so that** we can see a raid and clean it up fast.

**This slice:** the bot can ban a raid's account for good without ever touching an admin, an approved user or someone an admin let in, and the lift does not let it back.

## Decisions taken here (Claude's discretion, recorded)

- The run is DB-driven (research F3: the staff run engine is bound to linked groups, the Redis card and the staff pacer). The partial unique index `(lockdown_id) WHERE state = 'running'` makes a second concurrent run impossible, the same idiom as `uk_chat_lockdowns_active`.
- `StartBanRun` copies the joiner rows into `chat_lockdown_burst` (source joiner, `INSERT ... SELECT ... ON CONFLICT DO NOTHING`), marks the unhandled rows of joiners recorded as exempt skipped with reason `let_in` for that run (D-22: known in advance, so no Telegram call, and the result reports them), and queues every other unhandled row that is not an approved user or the bot. Approved users and the bot are simply never queued; approval is re-checked before each account.
- `CountBanCandidatesFresh` (the N on the button and the card) leaves out excluded IDs and exempt joiners, so N counts the accounts the run will act on; live admins are only known at run time and are skipped then.
- The joiner row is claimed (its current state to acting) before the Telegram call and moved to `kept` with detail `response_ban` after the ban (research Pattern 5). That claim keeps the worker's marker ban and the lift's unban away from the account; `kept` is final, so FinishLift never waits on it and the lift never unbans it. On a skip, a failure or a rate limit the joiner row goes back to the state and detail it came from. Rows held by someone else (acting, unbanning) put the account back in the queue without an attempt. Exempt rows are never claimed: the account is skipped `let_in`.
- The ban call is `banChatMember` with empty options: no `until_date` (so the ban has no end date) and no `revoke_messages`. Every text about it says only that the account is banned for good and cannot rejoin; nothing claims anything about the account's messages.
- A declined join request is banned the same way (D-21) and its burst row is marked with reason `request` for the report.
- Approved users come into `lockdownResponseBanOne` as a map from its caller (plan 05-10 reads them fresh), so this plan has no approvals dependency.
