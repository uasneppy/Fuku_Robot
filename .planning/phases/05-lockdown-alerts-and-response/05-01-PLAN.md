<objective>
The first end-to-end slice of the phase: a manual lockdown of a group that is linked to a Staff Group posts one alert into the Staff Group, and an admin of the locked group lifts the lockdown from that alert. The alert is decided once per lockdown by a conditional database update, posted by the existing DB-driven lockdown worker through the lockdown pacer, and every posted copy is remembered so it can be closed at the lift. The Lift button runs the exact /unlockdown path through one shared lift function.

Task 1 is the tracer: lock, alert, press Lift, Confirm, lifted. Task 2 closes every copy at the lift and makes old buttons harmless.

Purpose: ROADMAP Phase 5 success criteria 1 and 2 (Staff Group half), LOCK-11, LOCK-06 (alert button), D-01, D-04 to D-08, D-19.
Output: migration 20261011120000, the alert model and repository, lockdown_alert.go, lockdown_alert_callbacks.go, the shared lift function, worker steps, locale keys, AGENTS.md rules.
</objective>

## Phase Goal

**As a** group admin or staff member, **I want to** get a lockdown alert with one-tap fixes, **so that** we can see a raid and clean it up fast.

**This slice:** the Staff Group sees the lockdown and an admin of the locked group lifts it with one button.

## Decisions taken here (Claude's discretion, recorded)

- One row per posted copy in `chat_lockdown_alerts`, keyed `UNIQUE (lockdown_id, kind, seq, dest)`: the alert is kind `alert`, seq 0; Phase 5's reminders reuse the same rows (kind `reminder`, seq n). The whole row shape (message ID, stored body, link, buttons_live, edit_pending, close stamp, claim, attempts) is created in this one migration so later plans add no ALTER on it (research Pattern 2).
- The alert is decided once by `lockdown.BeginAlert`: one conditional update `alert_started_at IS NULL` inside a transaction that also inserts the destination rows (research Pattern 1). It runs only in the worker (`lockdownPlanAlerts`), for every active lockdown whose lock is confirmed and that has no alert yet, so the /lockdown path, the settle path and a crash in between are one code path. /lockdown only wakes the worker after `ConfirmLocked`.
- `chat_title` is stored on the lockdown row at `lockdown.Start` (from the command's chat), so the worker never needs a getChat for the alert header. A lockdown started before this migration renders the chat ID instead.
- The rendered text is stored on the copy's row after the send (`body`), and closing edits append a footer to it, so the alert "stays as posted" (D-04) and is never re-rendered from changed data.
- Confirm cards are stateless: Confirm and Cancel carry the asker's user ID (`u`) and an expiry in unix minutes (`e`) inside the callback data, so the buttons work with Redis down (research F4, Pattern 4). Every authority fact is checked live again at Confirm. This plan writes `e`; plan 05-02 enforces it.
- Callback data: Ask `lockdown|v1|a=lk&r=<copy row id>`, Confirm `a=lc&e=..&r=..&u=..`, Cancel `a=x&r=..&u=..`. The handler loads the copy row, then its lockdown, and takes the locked chat from the lockdown row.
- Interactive answers (the card, its edits, toasts) are sent directly like the staff cards; the public lift notice into the locked group and every worker send go through `lockdownPaced`.
