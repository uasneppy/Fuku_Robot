<objective>
The first end-to-end slice of the phase: a manual lockdown of a group linked to a Staff Group posts one alert into the Staff Group. /lockdown records the group's title and wakes the worker; the worker decides the alert once with a conditional database update, creates one copy row per destination, and posts it through the lockdown pacer, remembering the message and its exact text so later plans can add buttons, close it at the lift and re-post it as a reminder.

Task 1 is the tracer: lock, decide, post. Task 2 pins the gate's edges: no destination, a link made later, a lockdown that lifts before its alert is posted, and lockdowns that predate this phase.

Purpose: ROADMAP Phase 5 success criterion 1 (Staff Group half), LOCK-11, D-01.
Output: migration 20261011120000, the alert model and repository, lockdown_alert.go, the worker hook, two locale keys, AGENTS.md rules.
</objective>

## Phase Goal

**As a** group admin or staff member, **I want to** get a lockdown alert with one-tap fixes, **so that** we can see a raid and clean it up fast.

**This slice:** the Staff Group sees, at once, that one of its groups was locked down, by whom and why.

## Decisions taken here (Claude's discretion, recorded)

- One row per posted copy in `chat_lockdown_alerts`, keyed `UNIQUE (lockdown_id, kind, seq, dest)`: the alert is kind `alert`, seq 0, and the reminders of plan 05-13 reuse the same rows (kind `reminder`, seq n). The whole row shape (message ID, stored body, link, buttons_live, edit_pending, close stamp, claim, attempts, detail) is created in this one migration with idempotent statements, so later plans add no ALTER on it (research Pattern 2).
- The alert is decided once by `lockdown.BeginAlert`: one conditional update `alert_started_at IS NULL` inside a transaction that also inserts the destination rows (research Pattern 1). It runs only in the worker (`lockdownPlanAlerts`), for every active lockdown whose lock is confirmed and that has no alert yet, so the /lockdown path, the settle path and a crash in between are one code path. /lockdown only wakes the worker after `ConfirmLocked`.
- `chat_title` is stored on the lockdown row at `lockdown.Start` (from the command's chat), so the worker never needs a getChat for the alert. A lockdown started before this migration shows the chat ID instead, and gets its alert on the first worker cycle after the deploy (it has no `alert_started_at`).
- The text sent is stored on the copy's row (`body`), so later edits (closing, revoke) append to exactly what was posted and the alert "stays as posted" (D-04).
- The Phase 5 models go into the AutoMigrate lists of the test harnesses whose tests use them (`alita/modules/test_harness_test.go` here; `alita/db/lockdown/testmain_test.go` when plan 05-03 adds the repository tests). The `alita/db` package's own tests never touch these tables, so its list is left alone (AGENTS.md "Adding a module" step 4: the affected harness).
- This plan's alert has no buttons yet; plan 05-02 adds the Lift button together with its handler, so no dead button is ever posted.
