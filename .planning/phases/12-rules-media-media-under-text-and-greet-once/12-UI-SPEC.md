# Phase 12 - UI Design Contract

> Visual and interaction contract for what Phase 12 adds to the message editor: the Media and Buttons parts on the Rules
> page, the "Media under text" switch on Welcome, Goodbye and Rules, the "Greet once" switch on Welcome, the row budget
> that fits them, every new string, and the checks that prove it.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Upstream: 12-CONTEXT.md D-01..D-17 (locked, not reopened), REQUIREMENTS EDIT-07, EDIT-08, EDIT-09, the APPROVED Phase 11
> contract (`11-UI-SPEC.md`), 11-CONTEXT.md D-01..D-13, AGENTS.md (message editor pages, Set/Cancel/Remove, the wait, the
> typed-reply door, Previews, Staff Group privacy), and the code of `settings_edit.go`, `settings_pages.go` and
> `fuku/i18n/settings_locale_test.go`.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard that the bot
edits in place, plus messages the owner types in the bot's private chat. This contract **extends** the Phase 11 contract
and the Phase 9 and 10 contracts under it. **Anything not restated here is unchanged and applies to every new screen**:
the message anatomy (header, group line, body, notice), the text styling, the status icons, the press pipeline
(`settingsPress.verify`, owner gate at step 4b, one answer per press), where Set and Remove work (private only, the group
note and Open in private row in a group menu), the wait and the typed-reply door (the order of its checks, what ends and
what keeps the wait), the Remove-is-one-tap rule, the Preview rules (to the presser's private chat only, never writes),
the "never name the Staff Group" rule, and the Phase 11 limits table. Section names below follow Phase 11's mapping of the
web template to Telegram (Message Layout for Spacing, Text Styling for Typography, Status Icons for Color).

## Amendments to earlier contracts

Three earlier rules are changed on purpose by this phase. Each is stated here once so no reader has to infer it; where the
rest of this contract says "amended" or "superseded" it means these rows.

| # | Earlier rule | What this phase does to it |
|---|--------------|----------------------------|
| M1 | Phase 11 (`11-UI-SPEC.md`, Status Icons): "State is icon plus word, never icon alone" | **Amended for exactly five label keys** and nothing else: `settings_btn_edit_switch_welcome`, `settings_btn_edit_switch_goodbye`, `settings_btn_edit_switch_clean` (Delete last, shared by Welcome and Goodbye), `settings_btn_edit_switch_below` and `settings_btn_edit_switch_once`. On those five half-width switch buttons the state is the icon alone (`✅` on, `❌` off) and the state **word** moves to a body line of the same page (`settings_edit_line_*`, icon plus word, "Welcome: ✅ On"). Every other label keeps the Phase 11 rule: the Main grid status lines, the part state words (`Set · length 120`, `Photo`), the Phase 9 and 10 toggles and steppers, and every body line still show icon plus word. A GIF saved earlier **stays a document**, still shows `File or GIF`, and gets no Media under text switch until the owner sets the GIF again. Phase 11's "File or GIF" label therefore stays, but only for documents |
| M3 | AGENTS.md, Previews paragraph: "The Rules Full preview's heading is built in the presser's language (`buildRulesText` with the presser's translator), not the group's as `/rules` has it, so it is not word for word what members see" | **Superseded.** The Rules Full preview heading and its no-rules line are built in the group's language, as `/rules` builds them, so Full preview is the message members see (D-02, D-16; section "Preview on Rules"). The plan that changes the code **must rewrite that AGENTS.md sentence, and the matching comment above the Rules Full preview in `settings_edit_preview.go`, in the same commit** (AGENTS.md rule: update it with any change that invalidates a rule). The header line that precedes the preview stays in the presser's language |

## Message Layout (replaces Spacing Scale)

The Phase 11 body stands (header, group line, blank, part lines, optional note, hints, optional notice). Phase 12 changes
the body in three places only, and the keyboard in one block.

### Body of the three editor pages

```
⚙️ Settings · Welcome                 <- unchanged
Fuku Test Group  -1001234567890       <- unchanged
<blank>
Text: Set · length 120                <- part lines: Welcome and Goodbye as before; Rules now has all three
Media: Photo
Buttons: Set · total 3
<note, only for a sticker or video note>      <- settings_edit_note_no_caption, now also on Rules
<blank, only when there is at least one switch line>
Welcome: ✅ On                        <- NEW: switch lines, one per switch drawn, in the grid's order, icon plus word
Delete last welcome: ❌ Off
Media under text: ✅ On               <- only while the stored media is a photo, video or GIF animation (D-07)
Greet once: ❌ Off                    <- Welcome only
<blank>
<hint paragraph>                      <- Welcome, Goodbye: unchanged; Rules: settings_edit_hint_rules (text changed)
<blank>
<clean hint paragraph>                <- Welcome, Goodbye only, unchanged
<blank, Welcome only>
<greet-once hint paragraph>           <- NEW, Welcome only
<blank, only while the stored media is a document>
<file-or-GIF hint paragraph>          <- NEW, all three pages, only for a document
<blank, only with a notice>
<notice line>
```

Why the switch lines exist: the five switch buttons are half-width cells that cannot carry a state word in every language
(`Desactivado`, `Désactivé`, `Desligado` push `Bienvenida: ❌ Desactivado` to 26 code points), so a button shows the
state as an icon and the body states it in words. This is the amendment M1 above to the Phase 11 rule "icon plus word, never
icon alone": for these five buttons the icon is on the button and the word is on the body line, so the person still sees both,
exactly as the Main grid does (Phase 10 MENU-15: button is "icon name", state lives in the status block of the body). Every
other label keeps the Phase 11 rule. Rules has no switch line until its one switch is drawn.

The switch lines are text only: they carry no stored text, no button name and no link.

### The Rules page now shows three parts

Rules gains the Media and Buttons lines and rows from the same parts table (D-01); nothing in the renderer is reworked.
Its state words are the Welcome ones (`Photo`, `Set · total 2`, and so on).

### Keyboard blocks, in order

1. Part rows: one row per part in table order (text, media, buttons), `[Set]` or `[Set | Remove]` (unchanged; Rules now has
   three).
2. Preview rows: Preview for each part that has something to show, then Full preview last, two per row (unchanged; on Rules
   Preview text is drawn only while the rules text is set, Preview media and Preview buttons while set, Full preview always).
3. **Switch block (new layout):** the switches the page draws, in the order below, laid out as a two-column grid filled left
   to right; an odd last cell sits alone on its row. Every cell is at most 20 code points rendered, so a cell never
   depends on whether it has a partner.
4. Open in private row (group menu only, unchanged).
5. Navigation row, Back left and Close right (unchanged).

Switch order: Welcome page `[Welcome on/off, Delete last]`, `[Media under text, Greet once]`; Goodbye page `[Goodbye
on/off, Delete last]`, `[Media under text]`; Rules page `[Media under text]`. A page whose Media under text is not drawn
closes up: Welcome `[Welcome, Delete last]`, `[Greet once]`; Goodbye `[Goodbye, Delete last]`.

### Row budget (the proof that the limits hold)

Rows per block, worst case = every part set, media a photo (so Media under text is drawn), every Preview drawn. Limits are
8 rows private and 9 in a group (Phase 11, AGENTS.md). Phase 11 already stood at 8 on Welcome and Goodbye; stacking the new
switches one per row would have been 10 (Welcome), 9 (Goodbye) and 8 (Rules) private, which is why the switch block is a
grid.

| Page | Part rows | Preview rows (min to max) | Switch cells (min to max) | Switch rows (min to max) | Nav | Open in private | Private worst | Group worst |
|------|-----------|---------------------------|---------------------------|--------------------------|-----|-----------------|---------------|-------------|
| Welcome | 3 | 1 to 2 | 3 to 4 | 2 to 2 | 1 | +1 in a group | 3+2+2+1 = **8** | **9** |
| Goodbye | 3 | 1 to 2 | 2 to 3 | 1 to 2 | 1 | +1 in a group | 3+2+2+1 = **8** | **9** |
| Rules | 3 | 1 to 2 | 0 to 1 | 0 to 1 | 1 | +1 in a group | 3+2+1+1 = **7** | **8** |

Preview rows: Welcome and Goodbye always draw Preview text and Full preview (1 row), plus Preview media and Preview buttons
while set (2 rows). Rules draws Full preview alone (1 row) when nothing is set, up to four buttons (2 rows) when everything
is. Switch cells: Welcome has Welcome on/off, Delete last and Greet once always (3 cells) plus Media under text while
eligible (4); Goodbye has two always plus Media under text while eligible; Rules has Media under text only while eligible.
The best case of every page is below the worst, so no page ever exceeds the limit. A notice, a note or a hint adds body
lines, never keyboard rows. The largest keyboard is Welcome's: 8 rows and 17 buttons including the navigation row, far under
Telegram's 100.

A test builds each page at its worst case in a private menu and in a group menu and asserts `len(rows) <= 8` and `<= 9`
(see "Rendered-size and content checks").

## Interaction Contract

### 1. Rules: media and buttons parts (EDIT-08, D-01 to D-05)

Set, Remove, Cancel, Preview, the wait, the typed-reply door and every refusal of Phase 11 apply to Rules `m` and `b` as they
apply to Welcome `m` and `b`. Only the differences are listed.

**Rights (unchanged table, now covers `m` and `b`).** Rules Set and Remove, parts `x`, `m` and `b`, need
`settingsRightAdminBotAdmin` (the page's `EditRight`, the command's own predicate `chat_status.IsBotAdmin`); a refusal is
the notice `chat_status_bot_not_admin` and the page is redrawn with the warning line. The typed-reply door re-checks the
same right (Phase 11 step 4), so a bot that stopped being an administrator ends a Rules wait for media and buttons too.
Cancel, Preview and Full preview need only `settingsRightAdmin`.

**What Rules media and buttons accept.** The same input and the same refusal keys as Welcome: media is one photo, video, GIF,
file, sticker, audio or voice message (a GIF sent from now on is stored as an animation, D-08), an album keeps one item and
says so (`settings_edit_album_cut`), a caption is ignored and the saved page says so (`settings_edit_caption_ignored`);
buttons are the existing `[Name](buttonurl://...)` syntax with `:same`, valid buttons replace the set, a link that is not
http or https is refused with the button's number, at most 100 buttons and 8 per row (`settings_edit_refuse_need_media`,
`settings_edit_refuse_buttons_syntax`, `settings_edit_refuse_button_url`, `settings_edit_refuse_buttons_limit`). The prompts
are `settings_edit_wait_media` and `settings_edit_wait_buttons` unchanged.

**Refusals new to Rules (D-03).** One message means the media's caption is the `/rules` heading plus the rules text. The
rule is the Welcome's: 1024 with media, and the editor says why. The wait stays open on each refusal, with
`settings_edit_still_waiting` and Cancel, exactly as in Phase 11.

**Which media the 1024 applies to: every kind, the Welcome's rule.** Rules follows the Welcome's rule for every media kind, by
sharing one predicate, so the two can never differ (D-03: "Welcome, Goodbye and Rules all follow this one rule"; the owner's
answer was "Refuse, like the welcome"; D-01 lists sticker among the kinds). The contract adds no exemption for any kind. What
the shared check in `settings_edit_check.go` actually does today, which Rules inherits unchanged:

- **Text side.** `settingsEditCheckGreetingText` switches to the caption limit (1024) whenever `settingsEditPartIsSet(state,
  media)` holds, that is whenever a file ID is stored with a media type the editor names (photo, video, document or GIF
  document, sticker, audio, voice, video note), and it takes the stored media type as the data type for the commands' own
  length refusal (`content.TextLengthRefusal`: over 1024 characters of stored HTML for any non-text type). So a **sticker or a
  video note stored on a Welcome puts its text under 1024 exactly like a photo does**; there is no carve-out.
- **Media side.** `settingsEditCheckMedia` accepts a photo, video, document or GIF, sticker, audio or voice message and holds
  the stored text to 1024 (rune count first, then the filled length), refusing with `settings_edit_refuse_media_text_long`. A
  **sticker is therefore refused over a text longer than 1024**, like any other kind. A **video note is not accepted as typed
  media at all** (`dataType == db.VIDEO_NOTE` gives `settings_edit_refuse_need_media`, as does anything that is not media);
  a video note can only be on a message stored by `/setwelcome` or `/setgoodbye` by reply, and then it still holds the text
  to 1024 through the text side above.
- **What Rules takes from it.** The Rules typed-reply path stops being "text only" (`settingsEditCheck`'s Rules arm for media
  and buttons is removed) and uses the same two predicates: a Rules text is held to 1024 (heading included) while
  `settingsEditPartIsSet(state, media)` holds, whatever the kind, and a Rules media is refused over a stored text whose heading
  plus text is over 1024, for every kind `settingsEditCheckMedia` accepts; a video note sent as Rules media is refused with
  `settings_edit_refuse_need_media`, as on Welcome. The plan shares the predicates by calling them, not by copying them. What
  Rules adds is only the measure: the length is the `/rules` heading (with the group's real title, in the longest of the
  8 languages, as `settingsEditRulesHeadings` already does) plus the rules text, because placeholders do not exist in rules.
- **Note for the planner (not an owner question).** `11-UI-SPEC.md` ("Media and text of a sticker") says that setting a sticker,
  or text over a sticker, is allowed. The code does not do that: a stored sticker holds the text to 1024 and a text over 1024
  refuses a sticker, as for every other kind, and a video note cannot be typed at all. The note shown for a sticker or a video
  note (`settings_edit_note_no_caption`, "sent without text, so the text is not shown") describes what a member sees, not a
  relaxation of the limit. Rules stays equal to the Welcome; if the Phase 11 sentence is ever to be made true, that is a change
  to the shared predicate for all three pages, not a Rules exception.

| Typed part | Condition | Refusal key | Notes |
|------------|-----------|-------------|-------|
| Rules text | media of any kind is set (`settingsEditPartIsSet(state, media)`, the Welcome's test) and the visible length of heading plus new text is over 1024 UTF-16 units | **new** `settings_edit_refuse_text_rules_long` (`{n}` = that length, `{max}` = 1024) | Rules-specific wording, no "names": "With the heading added, this would be {n} characters, and the limit with media is {max}. Please shorten it." The heading is built with the group's real title by the same code `/rules` uses; no placeholders exist in rules. `settings_edit_refuse_too_long_filled` is **not** used for Rules and stays unchanged for Welcome and Goodbye |
| Rules media | the media being set is any kind `settingsEditCheckMedia` accepts (photo, video, document or GIF, **sticker**, audio, voice) and the stored text, with the heading, is over 1024 | **new** `settings_edit_refuse_media_rules_long` (`{n}`, `{max}`) | says the heading counts and to shorten the rules first. Welcome and Goodbye keep `settings_edit_refuse_media_text_long`. A sticker is refused here exactly as it is on Welcome |
| Rules text | no media stored: stored form over 3800 as before; dry run heading plus text over 4096 | unchanged (`content_text_too_long` and the stored-form key of Phase 11) | removing the media keeps a long text, up to 3800 (D-03); the 1024 applies only while media is stored |
| Rules media or buttons | not media (a video note included, as on Welcome), not text, bad syntax, bad link, too many | the Welcome keys above (`settings_edit_refuse_need_media` for a video note) | no new key |

The wait prompt for Rules text shows `Up to {max} characters` with **1024 while the group's Rules has media of any kind stored
(the same `settingsEditPartIsSet(state, media)` test the check uses) and 3800 otherwise** (no media; a code constant, as in
Phase 11 A7; the dry run is exact and the heading eats part of the 1024, so the refusal number is the true one). Assumption A6.

**"Rules is set" (Assumption A1).** A rules message exists when the text, the media or the buttons are non-empty. `/rules`
answers `rules_no_rules_set` only when all three are empty; with media or buttons and an empty text it sends the heading as
the caption (or as the text) with them. The Rules page, `Full preview` and the Main state line use the same test. This keeps
"Remove text" from orphaning a media the owner still wants, and it leaves every rules row saved before this phase reading
exactly as today (D-05: the new columns read as zero, so only the text decides).

**Remove (D-04).** Remove media on Rules clears the media and its type (notice `settings_edit_removed_media`), Remove buttons
clears the buttons (`settings_edit_removed_buttons`), Remove text clears the text (`settings_edit_removed_text_rules`, the
existing key). Each is one tap, no card; a stale press on an empty part is `settings_edit_nothing_to_remove` and writes
nothing. The three Remove presses together store exactly what `/clearrules` stores. Neither Remove nor `/clearrules` touches
the Media under text flag (Assumption A3).

**What a member sees (D-02, D-03, D-05).** `/rules` in the group (private rules off), the private rules message, and Full
preview are one message built by one builder: with media, the media with `heading + text` as its caption and the buttons
under it; with no media, the text message with the buttons under it as before. A rules row saved before this phase sends the
same text-only message as today, byte for byte. With a sticker or a video note the text is not shown (Telegram sends them without text)
and the page shows `settings_edit_note_no_caption` on Rules as it does on Welcome; the note describes what a member sees and
relaxes no limit: the 1024 rule above holds for them as for every kind. `/rules` in the group has its heading in the group's language, and Full preview builds it the same way
(section "Preview on Rules"). When private rules is on, the click-to-read
message in the group carries no media and no buttons; they appear in the private message the member opens (Assumption A8).

**Preview on Rules.** Preview text sends the stored text alone (heading not included, as before); Preview media sends the media
alone with no caption and no buttons; Preview buttons sends `settings_edit_preview_buttons_body` with the buttons as a keyboard;
Full preview sends the whole `/rules` message through the shared builder, **exactly as `/rules` sends it in the group with
private rules off**, and `rules_no_rules_set` only when all three parts are empty. Preview media is drawn only while
media is set, Preview buttons only while buttons are set, Preview text only while text is set, Full preview always. Previews
never write, never post into the group, and answer as in Phase 11 (empty in private, the toast in a group menu, the same
three alerts).

**Language of the Rules Full preview (supersedes the Phase 11 difference, amendment M3).** Members read `/rules` with its
heading (`rules_for_chat_header`) and its no-rules line (`rules_no_rules_set`) in the **group's language**, because `/rules`
translates with the language of the chat it runs in. Full preview must show the same words, so:

- The heading, the no-rules line and every other string the shared Rules builder translates use a translator for the
  **group's language**, never the presser's. The group's real title is spliced in as before.
- How the group's language is obtained: by the same per-chat language read `/rules` reaches when it runs in the group (the
  cached `chat_lang` entry of the group's chat ID in `fuku/db/lang`, which falls back to the bot's default language exactly as
  `/rules` does when the read fails or no language is stored), looked up **by the group's chat ID** in both a private menu and
  a menu opened in the group, so there is one path. `lang.GetLanguage(ctx)` is not usable for this, because in a private menu
  the update's chat is the presser's private chat and it would return the presser's language; the plan adds a by-chat-ID
  accessor on the same cached read in `fuku/db/lang` and no second language source. The read creates no row (check 9).
- The line that precedes the preview, `settings_edit_preview_header_rules`, **stays in the presser's language**, because it
  addresses the presser and is not part of what members see. So a preview is two messages in two languages when they differ:
  the header in the presser's, then the exact member message in the group's.
- When private rules is on, Full preview still shows the group form of the message (the one `/rules` sends in the group with
  private rules off, so the owner can check the whole content). Members then reach the same text, media and buttons through the
  private message, whose heading is translated in the opening member's own language; that one language is member-specific and
  cannot be shown by any single preview (Assumption A12). Everything else is identical because both go through the one builder.
- Preview text, Preview media and Preview buttons have no heading and are unaffected.

### 2. Media under text switch (EDIT-07, D-06 to D-09)

| Property | Contract |
|----------|----------|
| Pages | Welcome, Goodbye, Rules |
| Meaning | on = the caption sits above the media (Telegram `show_caption_above_media`), so the media appears below its text; off = today's layout |
| Label (button) | `✅ Media under text` / `❌ Media under text` (icon is the current state; `settings_btn_edit_switch_below`, at most 20 rendered) |
| Line (body) | `Media under text: ✅ On` / `Media under text: ❌ Off` (`settings_edit_line_below`) |
| Drawn when | only while the stored media is a **photo, video or GIF stored as an animation** (D-07, D-08). Not drawn, and its body line not shown, for a document, audio, voice, sticker, video note, a GIF saved before this phase (a document), or no media |
| Press | `tg` with `p` = page, `t=u`, `v=0` or `1`; absolute value, so a double tap is harmless; works in a private menu and in a group menu (like every Phase 11 switch) |
| Right | the page's `EditRight` (Assumption A2): Welcome and Goodbye `settingsRightChangeInfo` (refusal alert `settings_no_change_info`), Rules `settingsRightAdminBotAdmin` (refusal notice `chat_status_bot_not_admin`) |
| Apply function | one per message beside its Set-media apply function (`applyWelcomeMediaBelow`, `applyGoodbyeMediaBelow`, `applyRulesMediaBelow`): validation, column-targeted write, `cache.DeleteCache`, typed result read back |
| Result | success redraws from the value read back with no notice (like the other switches); a failed write redraws the freshly loaded page with `⚠️ common_settings_save_failed` and the old state |
| Stale press | a press when the stored media is no longer eligible (replaced or removed since the page was drawn) writes nothing and redraws the page with the warning `settings_edit_below_unavailable` |
| Stored "on" | kept when the media is replaced by an ineligible kind or removed: it is then ignored (not sent, not shown) and returns the next time an eligible media is stored (D-07). The body line shows it again at that moment |
| Not touched by | Remove media, Remove text, `/resetwelcome`, `/resetgoodbye`, `/clearrules` (Assumption A3: it is a display setting, not one of the three parts) |
| Where it applies | the join, the leave, `/welcome`, `/rules`, private rules and Full preview, through the one builder. Preview media alone has no caption, so it is unaffected |

A GIF saved before this phase is a document, shows as `File or GIF`, and gets no switch (D-08). So the owner is not left
guessing, the page adds one hint paragraph while the media is a document: `settings_edit_hint_below_file` ("Media under text
works for a photo, video or GIF. If this file is a GIF saved earlier, set it again to use it."). It is shown on all three
pages for a document and nowhere else. A GIF sent from now on reads `GIF` (`settings_edit_media_animation`).

### 3. Greet once switch (EDIT-09, D-10 to D-13), Welcome only

| Property | Contract |
|----------|----------|
| Page | Welcome only; Goodbye and Rules have no such control, and a callback naming it there is an invalid request |
| Meaning | on = a member is welcomed only the first time they ever join; off = every join, as today |
| Label (button) | `✅ Greet once` / `❌ Greet once` (`settings_btn_edit_switch_once`) |
| Line (body) | `Greet once: ✅ On` / `Greet once: ❌ Off` (`settings_edit_line_once`) |
| Hint | `settings_edit_hint_once`, a paragraph after the Delete-last hint. It says what the switch does and the one limit an owner must know: members who joined before it was turned on are welcomed once more |
| Drawn | always on Welcome, whether or not the Welcome switch itself is on and whatever the media; default off |
| Press | `tg`, `p=w`, `t=o`, `v=0` or `1`; works in a private menu and in a group menu |
| Right | `settingsRightAdmin`, the same as `/welcome on|off` (D-10); no refusal beyond the pipeline's |
| Apply function | `applyWelcomeOnce` beside `/welcome`; no command of its own, so the tests are a drift test and an authority test instead of a parity test |

## Notes for the planner (contract level)

- **Parts table.** Rules `Parts` becomes text, media, buttons; the existing `settingsEditMediaPart` and `settingsEditButtonsPart`
  entries are reused. The Phase 11 refusal of `t=m` and `t=b` on Rules becomes valid input and `t=z` is the invalid example.
- **Switch block.** Replace `settingsEditSwitchRows` with a block that builds a list of switch cells (label, control, value) from
  the page definition and the state, and lays them two to a row. The state struct gains `MediaBelow`, `Once` and the
  eligibility test; Rules gains media, buttons and `MediaBelow` through an extended `rules.LoadRulesContext` that still creates
  no row. `settingsEditMainState` for Rules uses the new "is set" test.
- **State icon.** Add `settingsStateIcon(on bool)` (`✅`/`❌`); `settingsStateWord` stays for the body lines.
- **Eligibility.** One function of the media type decides: photo, video and the new animation type. The page, the stale-press
  check and the sender use it; the sender also reads the stored flag only through it, so a stored "on" with another kind is ignored.
- **Locales.** `make check-translations` first; add 13 keys and rename 4 in all 8 files (editor keys by the counting rule in
  "New locale keys": 62 + 15 = 77 before, 74 + 16 = 90 after; all `settings_` keys 186 before, 199 after, the number the limits
  table must cover exactly), change `settings_edit_hint_rules` in all 8,
  update the limits rows (the five switch rows count `{state}` as 1 and carry 20) and the two label tests. `AGENTS.md` (Callbacks, Data,
  Subsystem traps) is updated in the same commit as the code, including the new controls `u` and `o` and the Rules parts, and the
  rewritten Previews sentence on the Rules Full preview heading (amendment M3).
- **Rules Full preview language.** Build the Rules Full preview message with a translator for the group's language, got by the
  group's chat ID through a new accessor on the cached language read in `fuku/db/lang` (the read `/rules` reaches); keep the
  presser's translator for the header line only. Update the comment above the Rules Full preview in `settings_edit_preview.go`.
- **Caption rule.** Rules follows the Welcome's rule for every media kind, by sharing one predicate, so the two can never
  differ. Do not write a Rules-only kind list. The text side is `settingsEditPartIsSet(state, media)` (any stored kind the editor
  names, sticker and video note included) switching the limit to 1024; the media side is `settingsEditCheckMedia`'s accepted kinds
  (a video note is refused as typed media, `settings_edit_refuse_need_media`). Remove the "Rules has a text part only" arm of
  `settingsEditCheck` so Rules media and buttons reach those functions, and give `settingsEditCheckRulesText` the same
  media-stored branch (limit 1024 on heading plus text, `settings_edit_refuse_text_rules_long`) beside its no-media limit. The
  prompt's `{max}` uses the same test. A parity table test (check 8) runs Welcome and Rules over every stored kind. Phase 11's
  sentence "a sticker, or text over a sticker, is allowed" is not what the code does (see "Which media the 1024 applies to"); the
  planner keeps Rules equal to the Welcome and does not ask the owner.
- **Spike first** (roadmap flag): `show_caption_above_media` on photo, video and animation on a real client, the 1024 limit, and a
  GIF through `sendAnimation`; the dry run and the Rules caption rule depend on it.
