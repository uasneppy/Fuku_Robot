## Planner assumptions (flagged)

- **UI-SPEC Assumption A1 (owner confirmation open):** Rules is "set" when the text, the media or the buttons exist; a media-only rules message has the bare heading as its caption. If the owner prefers text-only, the editor would instead refuse Set media and Set buttons while the text is empty (one check in 12-13); this plan's builder would not change.
- **UI-SPEC Assumption A8:** with private rules on, the group gets the unchanged click-to-read message, no media, no buttons.
- The legacy text branch reproduces each caller's old options exactly by taking them as `textOpts` and only replacing `ReplyMarkup` with the rules keyboard when the row has buttons: `/rules` passes `ReplyMarkup: rulesKb` (the zero-value markup today), its reply target and `AllowSendingWithoutReply: true` with no link-preview option; the deep link passes `formatting.Shtml()` with `ReplyParameters.MessageId` set to the `/start` message (what `msg.Reply` filled in). The 12-01 goldens decide.
- `/rules` in a connected private chat keeps its current language (the sender's) and its reply into the private chat; only the content grows media and buttons.
- The degrade covers only `/rules` and the deep link (`degrade` true); Full preview (12-14) passes false so the owner sees the failure.

## Deliberate deviation from D-03

- **D-03 says** rules with media are one message: the media, the text as its caption and the buttons under it. **The member-path fallback of Task 3 deviates from it on purpose**: when Telegram definitely refuses the media send (a 4xx other than 429), `/rules` and the private-rules deep link send a different message, the text and the buttons alone, without the owner's media.
- **Why it is kept:** it fires only for stored data the editor would have refused (a caption over 1024 that `/setrules` stored after media was set, a backup import, another bot's file ID). Without it every member's `/rules` fails silently with a 400. A 4xx means Telegram sent nothing, so the retry cannot duplicate a message.
- **How it stays visible:** every fallback is logged at Warn with the chat ID only; Full preview never falls back (12-14 passes `degrade` false), so the owner sees the refusal as `settings_edit_preview_failed` and can fix the stored message.
- **Required of the executor:** Task 3 writes this deviation into the AGENTS.md "Rules message" bullet, so operators know why a rules media can disappear from `/rules`, that it is logged, and that Full preview does not fall back.
