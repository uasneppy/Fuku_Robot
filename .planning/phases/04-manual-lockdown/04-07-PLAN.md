<objective>
Someone unmuted during a lockdown can talk after it lifts. All four unmute paths go through `resolveUnmutePermissions`, which today copies the group's live default permissions into the user's own restriction. During a lockdown those defaults are the locked set, so the user would stay muted after the lift (Pitfall 7b). The function now returns the active lockdown's stored pre-lockdown permissions instead, and reports a lookup failure as an error so no caller announces an unmute that did not happen.

Task 1 is the tracer through /unmute. Task 2 proves the other three callers and the failure path.

Purpose: ROADMAP Phase 4 success criterion 5 (anyone unmuted during the lockdown can still talk after it lifts), LOCK-08, D-23.
Output: the new resolveUnmutePermissions and its four call sites, the /unmute lockdown note, tests, AGENTS.md rule.
</objective>

## Phase Goal

**As a** group admin, **I want to** lock my group down during a raid and lift it when safe, **so that** attackers are stopped and settings survive.

**This slice:** unmuting someone during a lockdown never leaves them muted after it.

## Decisions taken here (Claude's discretion, recorded)

- One choke point (D-23): `resolveUnmutePermissions(chatInfo *gotgbot.ChatFullInfo) (gotgbot.ChatPermissions, error)`. With `chatInfo.Id` set it reads the active lockdown fresh; an active row's `PrePermissions` is decoded and returned. The `Id != 0` guard keeps the existing parallel pure tests (Id 0) away from the database.
- Only an active row counts: once the lift starts, the restore has already put the snapshot back, so the live defaults are right again.
- The per-user restrict calls stay as they are (no independent-permissions flag), matching today's behaviour; research notes the residual difference only for groups with independently configured permissions.
- The /unmute reply gets `mutes_unmute_lockdown_note` during a lockdown (CONTEXT "Wording and formats").
- A test seam `lockdownSnapshotLookup` (a package variable defaulting to `lockdown.GetActiveFresh`) lets tests force a lookup error.

## Assumptions recorded

- A7 (research): a user's effective permissions are the group default combined with their own restriction, so a per-user grant cannot exceed the locked default (the owner's spike, D-02, saw the per-user toggle greyed out). The user therefore stays muted until the lift.
