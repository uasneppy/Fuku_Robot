## Planner assumptions (flagged)

- Names are the research's (Claude's discretion, D-06/D-07): `chat_requirements`, `chat_requirement_holds`, the cache module `member_requirements`, the rule IDs `last_name`, `username`, `russian`, `arabic`, `chinese` whose columns are `<id>_action`. The rule bits (1, 2, 4, 8, 16) live in the modules' rule table (13-02), not here; `chat_requirement_holds.rules` only needs to be positive here.
- The hold model's `ID` is `int64` (`primaryKey;autoIncrement`): it is the `h` of the "I fixed it" button, parsed later by `settingsCardNumber` (positive 63-bit). `RestoreHold` inserts that explicit ID back with `ON CONFLICT DO NOTHING` and no target; PostgreSQL accepts an explicit value in a BIGSERIAL column and the sequence is never reused.
- `RevertHoldToPending(ctx, id)` (one conditional update: `punished_at` NULL and `created_at` now, for a punished hold) is what 13-08 uses when a mute notice cannot be delivered and the mute is lifted: the row stays only as the two-minute backoff (planner revision of the failed-notice rule).
- `TakeHoldByID` and `TakeHoldsBefore` use `DELETE ... RETURNING` through GORM's `clause.Returning{}` (SQLite 3.35+ and PostgreSQL both support it). If the SQLite build in the harness rejects it, read then delete by ID and check `RowsAffected`, and say so in the SUMMARY. `TestRequirementHolds` joins the PostgreSQL list so the take and clean semantics are proved on PostgreSQL too.
- Every exported function here has no production caller until 13-05 onward; each is called by a test of this plan.
- Test hygiene: every test of this plan uses fresh chat IDs (`time.Now().UnixNano()`-based negatives, as the package's existing tests do) and deletes its rows and the `member_requirements:<chat>` key in `t.Cleanup`, then calls `cache.ResetLocalForTest()`; nothing writes a users row. On PostgreSQL the tests run on the migration-built schema and never skip.
