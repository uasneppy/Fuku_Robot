# Phase 13 - UI Design Contract

> Visual and interaction contract for Member requirements. It covers the new settings page and its per-rule screens,
> the confirm card for kick, ban and mute, the public notice a violation posts in the group, the "I fixed it" button and
> every answer it gives, the Main grid entry, every callback with its worst-case size, every new string with its key and
> ceiling, and the checks that prove it.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker (APPROVED with flags, all folded in).
> Upstream: 13-CONTEXT.md D-01..D-18 (locked, not reopened), REQUIREMENTS MREQ-01..MREQ-09 and MREQ-13, ROADMAP Phase 13
> (goal, owner decisions, success criteria), the APPROVED Phase 12 and Phase 11 contracts (`12-UI-SPEC.md`,
> `11-UI-SPEC.md`), AGENTS.md (Handlers, Callbacks `settings|v1`, Permissions, the settings rules), and the code of
> `settings_pages.go`, `settings_menu.go`, `settings_card.go`, `settings_lockdown.go`, `settings_captcha.go`,
> `settings_antiflood.go`, `settings_access.go`, `settings_edit.go`, `warns.go` and `fuku/i18n/settings_locale_test.go`.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard. There are two
surfaces. The first is the settings menu (private, or opened in the group), which the bot edits in place. The second is
the group itself: the bot posts a notice there and edits it after "I fixed it". This contract **extends** the Phase 9 to
12 contracts. **Anything not restated here is unchanged and applies to every new screen**: the message anatomy (header,
group line, body, notice), the text styling, the status icons, the press pipeline (`settingsPress.verify`, owner gate at
step 4b, one answer per press), the two-tap card (`settings_card.go`), the "never name the Staff Group" rule (D-21,
D-32), the Main grid (MENU-15), and the Phase 11 and 12 limit tables. Section names follow Phase 11's mapping of the web
template to Telegram (Message Layout for Spacing, Text Styling for Typography, Status Icons for Color).

## Message Layout (replaces Spacing Scale)

The Phase 9 anatomy stands (header `settings_header` with the page name, group line with the escaped title and the
`<code>` chat ID, one blank line, body, then a blank line and the notice when there is one). This phase adds one page,
one sub-screen of it, one card and one group message.

### The Member requirements page (page `m`)

```
⚙️ Settings · Requirements            <- settings_header + settings_page_mreq
Fuku Test Group  -1001234567890       <- group line, unchanged
<blank>
<intro line>                          <- settings_mreq_intro
<all-off line, only when every rule is Off>   <- settings_mreq_all_off
<blank>
Must have a last name: 🔇 Mute        <- one line per rule, fixed order, settings_mreq_line
Must have a username: ❗ Warn
No Russian name: ❌ Off
No Arabic name: ⛔ Ban
No Chinese name: ❌ Off
<blank>
Check on join: ✅ On                  <- settings_mreq_line_join
Delete messages: ❌ Off               <- settings_mreq_line_delete
<blank>
<letters hint>                        <- settings_mreq_hint_letters (MREQ-13, success criterion 1)
<blank>
<blank last name hint>                <- settings_mreq_hint_blank
<blank>
<who and when hint>                   <- settings_mreq_hint_join
<blank>
<delete hint>                         <- settings_mreq_hint_delete
<blank>
<mute hint>                           <- settings_mreq_hint_mute
<blank, only with a notice>
<notice line>                         <- ⚠️ line (save failed, card expired)
```

The rule order is fixed and is the order of the code's rule table: last name, username, Russian, Arabic, Chinese. Phase
14 and Phase 15 append their rules to the same table, so their lines and cells come after these without reworking the
renderer. A rule line shows the punishment as **icon plus word** (`🔇 Mute`); the word is the reused option key
(`settings_state_off_plain`, `settings_opt_warn`, `settings_opt_kick`, `settings_opt_ban`, `settings_opt_mute`).

### Keyboard of the page, in order

1. **Rule grid:** one cell per rule in rule order, two per row filled left to right; an odd last cell sits alone on its
   row. A cell is `{punishment icon} {short rule name}` (amendment M4), at most 20 code points rendered. A press opens that
   rule's screen (`a=mo&t=<rule>`).
2. **Switch row:** `[ {✅|❌} Check on join | {✅|❌} Delete messages ]`, two half-width cells (amendment M4). A press
   sends the opposite absolute value (`a=tg`).
3. **Navigation row:** `[ ⬅️ Back | ✖️ Close ]`, unchanged (Back opens Main).

There is **no Open in private row**, in either menu (Assumption A5). Nothing on this page awaits typed input, so a menu
opened in the group works exactly like a private one: every control writes or draws the card in place. The only
differences between the two menus are the owner field of the callbacks (`c` private, `u` group) and that a menu opened
in the group is read by every member (as every settings page is).

### The rule screen (a sub-screen of page `m`)

```
⚙️ Settings · Requirements
Fuku Test Group  -1001234567890
<blank>
Must have a last name                 <- settings_mreq_rule_<rule>
<what breaks the rule>                <- settings_mreq_desc_<rule>
<blank last name hint, last-name rule only>   <- settings_mreq_hint_blank (reused)
<blank>
Punishment: 🔇 Mute                   <- settings_mreq_now
<blank>
<choose hint>                         <- settings_mreq_choose_hint
<actions hint>                        <- settings_mreq_actions_hint
<blank, only with a notice>
<notice line>
```

Keyboard: `[ Off | Warn ]`, `[ Kick | Ban | Mute ]` (choice rows through `settingsChoiceRow`, the selected option
prefixed `✅ `; the top row changes at once, the bottom row asks first), then `[ ⬅️ Back | ✖️ Close ]` where Back
returns to the page (amendment M5). Three rows.

### The confirm card (D-05)

```
⚙️ Settings · Requirements
Fuku Test Group  -1001234567890
<blank>
Set “No Arabic name” to Ban?          <- settings_mreq_confirm ({rule}, {action} = the plain word)
<blank>
<what happens>                        <- settings_mreq_confirm_kick | _ban | _mute
```

Keyboard: `settingsCardRows` unchanged: `[ ✅ Yes | ❌ No ]` then `[ ⬅️ Back | ✖️ Close ]`. Two rows.

### The group notice (one per violation, D-04, D-13)

```
🔇 Alex, you are muted: no last name, Russian letters. Fix your Telegram profile, then tap “I fixed it”.
[ ✅ I fixed it ]                     <- mute only
```

One paragraph, no header, no group line, no chat ID. The member is a mention (see "Naming the member"), the broken rules
whose punishment is not Off are a comma list of short phrases in rule order. Only a mute has a keyboard: one full-width row with the button.

## Text Styling (replaces Typography)

Phase 11 styling stands: `<b>` on "Settings" and the group title, `<code>` on the chat ID, no other tags in settings
strings, user text escaped and spliced in after translation, button labels plain text. Additions:

| Role | Markup | Used for |
|------|--------|----------|
| Rule name, punishment word, state word | plain text | every line of the page and the rule screen; no new `<b>` |
| The letters ы, ъ, э, ё | plain literal characters | `settings_mreq_hint_letters`, `settings_mreq_desc_russian`; never translated, transliterated or wrapped, in all 8 locales |
| Member in a group notice | a mention `<a href="tg://user?id=<id>">name</a>`, built by `formatting.MentionHtml` (which escapes) and spliced in **after** translation | every `mreq_notice_*` key; the template itself carries a `{name}` token and no markup |
| Group notice text | plain text plus that one link | no `<b>`, no `<code>`; link previews disabled |

Quotation marks around “I fixed it” and around the rule name on the card are the language's own (curly quotes in English,
« » in French, „ " in Ukrainian and Russian at the translator's choice); they are part of the translation. The words
inside the quotes are not: in each language, the quoted button name in `mreq_notice_mute`, `settings_mreq_actions_hint`,
`settings_mreq_hint_mute` and `settings_mreq_confirm_mute` (the only confirm key that names the button) must be exactly
the words of that language's `mreq_btn_fixed` label without its `✅ ` prefix, so the text never names a button the
member cannot find. `TestMemberReqLocaleKeys` asserts it (check 11).

## Interaction Contract

### 1. Opening the page and the Main grid (MREQ-01, D-16)

| Property | Contract |
|----------|----------|
| Registration | `registerSettingsPage` from the page's own file (for example `settings_mreq.go`), page key `m`, `Order` 80, icon 🛂, `TitleKey` `settings_page_mreq`. `settings_pages.go` is not edited |
| Main grid | after Rules (70) and before Access (90): `s|l / c|f / w|g / r|m`, then the owner-only Access row. The grid button is `🛂 Requirements` (14 code points) |
| Main state (`MainState`) | `Off` (`settings_state_off_plain`) when every rule is Off, whatever the two switches say; otherwise `{n} on` (`settings_state_mreq_on`, n = rules not Off, 1 to 5). A failed read is `❔` (`settingsUnknownState`). Database only, through the same cached loader the watcher reads, no Telegram call, no row created |
| Page read | the side-effect-free loader of `chat_requirements` (D-06, D-16), through `cache.GetFromCacheOrLoad`. A chat with no row draws everything Off and both switches Off. A failed read is the cannot-open edit (`settings_cannot_open` with the alert `settings_cannot_open_alert`), as the Antiflood page does; a page never guesses Off |
| Right to open | `settingsRightAdmin` (the live admin check every press makes, behind the owner gate) |
| Never shown | the Staff Group, a chat ID other than the group line's, the owner gate switch, any member name, any count of held or punished members |

### 2. Choosing a rule's punishment (MREQ-01, D-04, D-05)

A rule cell opens its rule screen (`a=mo&t=<rule>`, page action, right `settingsRightAdmin`). On the rule screen the
five choices are `st` presses of the rule's control with the absolute target `v`:

| `v` | Choice | What a press does |
|-----|--------|-------------------|
| `0` | Off | writes at once through the apply function, redraws the **rule screen** with the ✅ on Off, no notice |
| `1` | Warn | writes at once, redraws the rule screen, no notice |
| `2` | Kick | writes nothing, draws the **confirm card** for (rule, Kick) |
| `3` | Ban | writes nothing, draws the card for (rule, Ban) |
| `4` | Mute | writes nothing, draws the card for (rule, Mute) |

- **Same value.** A press whose `v` equals the stored value writes nothing, draws no card and redraws the rule screen. So
  pressing the already-selected Mute never asks again (Assumption A7). The stored value for this comparison is read by a
  **direct fresh database read** of the chat's row (a missing row is Off), never through the cached loader, because the
  in-process layer of another replica can be up to `CACHE_LOCAL_TTL` behind and a stale "same value" would skip a card
  the owner should see. A failed fresh read redraws the rule screen with `⚠️ common_settings_save_failed` and draws no card.
  The page, the rule screen and Main keep reading through the cached loader, and so does the watcher on every group
  message (D-06); whether that cache key joins `skipLocal` stays a research item.
- **`st` only.** A rule control accepts the `st` action only. A `tg` naming a rule control (`a=tg&t=ln&…`) is
  `common_callback_invalid_request` in step 1, before any I/O. `settingsControl.Validate` sees only `v`, so the page
  declares the allowed action with the control (an optional action allow-list on `settingsControl`, read by
  `settingsControlFieldsValid` together with `Validate`), never a refusal inside `Set` after the member lookup.
- **Moving between strict values** (Ban to Mute, Kick to Ban) draws the card like any move to Kick, Ban or Mute (D-05).
  Moving from a strict value to Off or Warn writes at once.
- **Write failed.** The rule screen is redrawn from a fresh read with `⚠️ common_settings_save_failed` and the old value.
- **Values are absolute** (`v`), so a double tap is harmless and two admins pressing at once leave the last value.
- **Apply function.** One per setting beside where a command would be (D-17): `applyMemberReqAction(ctx, chatID, rule,
  action)` validates the rule and the value 0..4, makes the column-targeted upsert (a Go 0 is written), deletes the cache
  key it affects and returns a typed result with the row read back. The page draws from the read-back. There is no
  command, so the tests are a drift test and an authority test instead of a parity test.

### 3. The confirm card (D-05)

| Drawn by | an `st` press with `v` 2, 3 or 4 that passed the whole press pipeline **and** the right `settingsRightRestrict`; nothing is written |

Each consequence line says the rule acts on **every member at their next message, members already in the group included** (D-05) |
| Buttons | `settingsCardRows`, unchanged: `✅ Yes` (`a=my&t=<rule>&v=<2|3|4>&e=<expiry minute>`) and `❌ No` (`a=no&p=m`), then the navigation row |
| Expiry | `settingsCardLifetime`, 5 minutes, lazy (`settingsCardExpired`): an expired Yes writes nothing and redraws the **rule screen** with `⚠️ settings_card_expired`. A bad `e` is `common_callback_invalid_request` before any I/O |
| Yes | runs the whole press pipeline again (live `getChatMember`, owner gate step 4b, right `settingsRightRestrict`), so an admin demoted since the first tap is refused with the alert `settings_no_restrict` and nothing is written; then `applyMemberReqAction` with the card's `v`; then the **rule screen** is redrawn from the read-back with the ✅ on the new value and no notice. | No | the core cancel: redraws the **Member requirements page**, nothing written (Assumption A6) |

| Off and Warn | never draw a card (D-05) |

### 5. Rights (press pipeline step 5, D-16)

| Press | Right | Refusal |
|-------|-------|---------|
| open the page (`op p=m`, Main grid, Refresh), open a rule screen (`mo`), the rule screen's Back (`op p=m`), the card's No (`no p=m`) | `settingsRightAdmin` | none beyond the pipeline's (`settings_not_admin`, `settings_check_failed`, the owner gate texts) |

The bot's own rights (restrict, delete) are **not** checked or shown on this page in this phase. A rule that cannot work
in a group (the bot cannot restrict or delete, a basic group where a mute cannot be placed) is the "this rule cannot
work here" line of Phase 14 (MREQ-10), which adds body lines, not rows (Assumption A14). The punisher's own refusals
are covered in section 7: a punishment Telegram refuses posts no notice.

### 7. The group notice (MREQ-05, D-02, D-04, D-13)

One notice per episode, posted in the group, in the **group's language**, only after the punishment took effect (a warn
recorded, a kick, ban or mute confirmed by Telegram). A punishment Telegram refuses, and a check that cannot be answered
(D-11), post nothing. Further messages of a held member post nothing (D-07, D-14). The notice is a new message, not a
reply, because "Delete messages" may already have removed the message it would reply to (Assumption A9).

The punishment is the strictest of the broken rules (ban over kick over mute over warn, D-04), and `{rules}` lists
**every broken rule whose punishment is not Off** (whatever that punishment is; a rule set to Off is never checked and
never listed) as the `mreq_rule_*` phrases in rule order, joined by `", "` (a code constant; all 8 languages use the
comma).

| Punishment | Key | English | Keyboard |
|------------|-----|---------|----------|
| Warn, below the limit | `mreq_notice_warn` | ❗ {name}, your profile breaks this group's rules: {rules}. Warning {n} of {limit}. | none |
| Warn that reaches the limit, limit action kick | `mreq_notice_warn_limit_kick` | ❗ {name} broke this group's rules: {rules}. That is {n} of {limit} warnings, so they were removed. | none |
| … limit action ban | `mreq_notice_warn_limit_ban` | ❗ {name} broke this group's rules: {rules}. That is {n} of {limit} warnings, so they were banned. | none |
| … limit action mute | `mreq_notice_warn_limit_mute` | ❗ {name} broke this group's rules: {rules}. That is {n} of {limit} warnings, so they were muted. An admin can unmute them. | **none**: a warn-limit mute is the warn module's mute, not a requirement mute, so it gets no "I fixed it" (MREQ-07) |
| Kick | `mreq_notice_kick` | 👢 {name} was removed: {rules}. They can join again once they fix their profile. | none |
| Ban | `mreq_notice_ban` | ⛔ {name} was banned: {rules}. An admin can unban them. | none |
| Mute | `mreq_notice_mute` | 🔇 {name}, you are muted: {rules}. Fix your Telegram profile, then tap “I fixed it”. | `[ ✅ I fixed it ]` |

- **Warn count.** `{n}` is the member's warn count after this warn and `{limit}` the group's warn limit, both as the warn
  module stored and read them (D-13: the warn goes through the warn module's own path and counts toward its limit). The
  warn's stored reason is `mreq_warn_reason` ("Requirements: {rules}") in the group's language, so `/warns` shows it.
  The warn module's own reply (`warns_user_warning`, its Remove warn and Rules buttons) is **not** sent for a requirement
  warn: the notice is the one message (Assumption A9). If the limit action Telegram refused, the notice is the plain
  `mreq_notice_warn` with the count, never a removal it did not make.
- **Naming the member.** `{name}` is a mention of the member (`formatting.MentionHtml`, which escapes), so the member is
  notified and a muted member finds the button (Assumption A8). Its text is, in order of preference: the first name, if it
  has a visible character by the same test the last-name rule uses (D-10); else `@username`; else `mreq_name_unknown`
  ("user {id}", the numeric ID). The 64-rune cap counts the name only. The two Unicode isolates U+2068 and U+2069 are
  then added around it inside the link (66 code points at most), so an Arabic or other right-to-left name cannot reorder
  the sentence around it. The rendered-length tests count the isolates. The token is spliced in after translation (the
  `lockdownSplice` pattern); a name never passes through the translator.
- **Size.** Every notice, rendered with a 64-rune name plus its two isolates, all five rule phrases and two-digit numbers,
  is at most 400 code points of visible text (the mention's link text, not its markup) in every language. **The
  rendered-length test is the binding check**; the per-key ceilings in "New `mreq_` keys" are set so that it can be met
  by any translation within them. Worst cases: English as written 247 (`mreq_notice_warn_limit_mute`); any language at
  its ceilings 354 (`mreq_notice_warn_limit_mute` at 170, phrases at 24/24/27/27/27). They are public, so they stay one
  paragraph.
- **A failed mute-notice send.** The mute is already in place when the notice is sent: the hold is inserted first, the
  mute is applied, and the notice message ID is stored on the hold only after the send. If Telegram refuses the send (or
  it times out), the notice is retried **once**. If the retry fails too, the mute and the hold are kept, one Warn log line
  names the chat ID and the user ID only (never the name or the notice text), and nothing else is posted. This is an
  **accepted limit**: that member has no "I fixed it" button for this episode, and an admin can unmute them with
  `/unmute`. The bullet below ("never dropped by notice pacing") is about the bot's own pacing, not about a refusal by
  Telegram.
- **Held welcome (D-02), in words.** A member muted by the join check gets no welcome. The welcome waits until "I fixed
  it" succeeds, and is then sent once through `SendWelcomeMessage`, so Greet once (Phase 12) claims the member only when
  the welcome really goes out. A member kicked or banned on join gets no welcome. A member warned on join gets the warn
  notice first, then the usual welcome. A member muted later by the message check was already welcomed, so "I fixed it"
  sends no welcome for that hold. In a captcha group the captcha's own success note comes first (the captcha runs before
  the check, D-01), then the notice; the captcha's greeting is the one held back.
- **Pause notice (D-13 research flag, Assumption A15).** If research keeps a per-chat cap on punishments per minute, the
  moment the cap stops punishments the group gets one `mreq_notice_paused` ("⏸ I paused the requirement punishments
  here for {minutes} minutes: more than {n} members broke a rule within one minute. An admin can check Requirements in
  /settings."), at most once per pause, with the numbers from research. If research drops the cap, the key is dropped.
- **A mute notice is never dropped by notice pacing.** It carries the only "I fixed it" button, so the bot's pacing or cap
  may delay it but must not skip it (planner note). A refusal by Telegram is the previous bullet.

## Callback data (64-byte cap)

Built only with `encodeCallbackData`. Settings buttons are in `settings|v1|` (12 bytes); worst case `c` =
`-1001234567890` (14 characters, 16 bytes with `c=`), `u` = `1234567890` (12 bytes with `u=`); the card's `e` is today's
unix minute (8 digits). Byte counts include the namespace.

| Button | Data (private) | Bytes private | Bytes group |
|--------|----------------|---------------|-------------|
| Main grid button, page Refresh, rule screen Back | `settings\|v1\|a=op&c=-1001234567890&p=m` | 37 | 33 |
| Rule cell (open rule screen) | `settings\|v1\|a=mo&c=-1001234567890&t=ln` | 38 | 34 |
| Punishment choice | `settings\|v1\|a=st&c=-1001234567890&p=m&t=ln&v=4` | 46 | 42 |
| Switch | `settings\|v1\|a=tg&c=-1001234567890&p=m&t=j&v=1` | 45 | 41 |
| Card Yes | `settings\|v1\|a=my&c=-1001234567890&t=ln&v=4&e=29876543` | **53** | 49 |
| Card No | `settings\|v1\|a=no&c=-1001234567890&p=m` | 37 | 33 |

Codes. Page key `m`. Page actions `mo` (open a rule screen, field `t`) and `my` (card Yes, fields `t`, `v`, `e`), both
registered by the page; `registerSettingsPage` panics on a clash, and neither is a core code or used by another page.
Rule controls (`t` values): `ln` last name, `un` username, `ru` Russian, `ar` Arabic, `zh` Chinese; Phases 14 and 15 add
their own two-letter codes. Switch controls: `j` Check on join, `d` Delete messages. Values: a rule's `v` is the stored
action number of D-06 (0 off, 1 warn, 2 kick, 3 ban, 4 mute).

Validation, strict and in step 1 before any I/O (`common_callback_invalid_request`):

- `mo`: exactly the field `t`, a rule code of this page (`Validate`).
- `st` on `p=m` with a rule control: `v` is one digit 0 to 4 (the control's `Validate`). A rule control accepts **`st`
  only**: `tg` naming a rule control (`a=tg&p=m&t=ln&v=1`) is invalid, by the action allow-list declared with the control
  and read in the same step (section 2, "`st` only").
- `tg` or `st` on `p=m` with `j` or `d`: `v` is `0` or `1` (the switches accept both actions alike, the Access precedent).
- `t=j&v=4`, `t=ln&v=5`, `t=ln&v=04`, `t=xx`, a missing field and an extra key are each invalid.
- `my`: exactly `t`, `v`, `e`; `t` a rule code; `v` one of `2`, `3`, `4` (a Yes can never carry Off or Warn); `e`
  digits only, positive, at most 19 digits (the `settingsCardNumber` shape).

"I fixed it" is in `mreq|v1|` (8 bytes): `mreq|v1|a=f&h=<hold id>&u=<user id>` (the codec sorts keys).

| Case | Example | Bytes |
|------|---------|-------|
| typical (10-digit user, 6-digit hold) | `mreq\|v1\|a=f&h=123456&u=1234567890` | 33 |
| worst (16-digit user, the 52-bit ceiling of Telegram IDs; 19-digit hold) | `mreq\|v1\|a=f&h=9223372036854775807&u=9007199254740991` | **52** |

Callback data carries only codes and numbers, never a title, a name, a rule text or a chat title.
`settingsScreen.Omitted` is 0 on every screen of this phase.

## Accessibility and phone-width notes

- State is never icon alone on a screen: every icon-only cell has its word on a body line (amendment M4), and the five
  punishment icons have distinct shapes (cross, exclamation, boot, no-entry, muted speaker).
- The bottom choice row has three cells; the longest label (uk "Заглушення" with the ✅ prefix, 12) already ships on the
  Captcha page's three-cell action row, so it is not a new width risk.
- Right-to-left names: the member's name is isolated (U+2068 … U+2069) inside its link, so "Arabic letters" notices do not
  reorder on any client. None of the 8 UI languages is right-to-left.
- The "I fixed it" button is a full-width row, the largest tap target in the notice.
- A notice is one short paragraph; it never repeats the group's title or the rule settings.
