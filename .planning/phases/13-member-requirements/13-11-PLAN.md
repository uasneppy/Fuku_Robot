## Planner assumptions (flagged)

- When the switch is on and a rule is on, the entry reads the member's hold even with Check on join off: a punished requirement mute hold (the D-08 race, a member who posted before the captcha attempt existed) records welcome_held and sends no welcome, so D-02 holds whatever the switch says. With the switch off, or every rule off, the entry is at most one cached settings read plus `SendWelcomeMessage`, which keeps every existing join, captcha and greet-once test unchanged.
- A warn that reached the group's limit and kicked or banned is a removal (no welcome); one whose limit action was the warn module's mute is welcomed like any warn (13-07 assumption, D-02).
- The captcha guard sits behind the switch too (planner revision): while `memberReqLive()` is false it returns at once with no hold read, no Telegram call and no error. So no commit before 13-13 changes a real captcha unmute: the pass, `restoreCaptchaPermissions`, restart recovery and the `captcha_muted_users` retry worker all unmute exactly as at HEAD, and a database fault in the new table can never block one. Once the switch is on, a hold-read error fails closed. The guard returns the error, so the member stays muted. Each caller then handles it exactly as it handles a failed, non-permanent Telegram unmute today: `restoreCaptchaPermissions` writes the `captcha_muted_users` row; the retry worker keeps its row for the next 5-minute pass; restart recovery (`releaseIncompleteCaptchaAttempt`) returns the error, which is logged, and deletes no row. That handling holds only while the error is not read as permanent. So the guard wraps its read error with chat and user IDs only, and `isPermanentUnmuteError` must answer false for it. A permanent answer would make the worker delete its row and leave the member muted with no retry. The alternative, unmuting on a read error, could free a member the requirements muted. A member kept muted by a passing database fault is unmuted at the next retry. This is an accepted, documented cost (AGENTS.md and T-13-58).
- `memberReqHoldRead` is a package variable so a test can count and fail the hold read. `captchaApplyBrokenDB` is not used for the off-switch test, because it also breaks the lockdown read inside `resolveUnmutePermissions`, and so cannot tell a skipped hold read from a failed one.
- Test hygiene: `memberReqEnv` (enforcement on through `withMemberReqLive`, except the off test) with the greetings module loaded (`LoadGreetings` on the env's dispatcher; the settings env already loads the captcha module, so `loadJoinModules`, which loads both, is not used: it would register the captcha handlers twice), `mreqMember` IDs and `memberReqCleanup`, which also deletes the captcha rows of its chats (`captcha_attempts`, `captcha_muted_users`) and the `fuku:recentJoinProcessing:<chat>:<user>` keys of its members; the web-pass subtest builds its own `newCaptchaWebEnv` and gives its member a fresh `uniqueLinkOwnerID()` instead of the fixed 42 the older web tests use, cleaning that member's users row, cache key and captcha rows in `t.Cleanup`.
