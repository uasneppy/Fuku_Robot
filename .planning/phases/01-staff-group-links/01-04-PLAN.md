<objective>
Close D-10's remaining race in the database. "A Staff Group can't be linked, and a linked group can't become a Staff Group" spans two tables, so UNIQUE and CHECK constraints cannot express it. The in-transaction app checks (plans 01-02 and 01-05) cover a single replica, but two replicas running `/setstaff X` and "link X" at the same moment could both commit. The research recommends a PostgreSQL trigger with a per-chat advisory lock (Open Question 4). It is a new one-way schema decision the owner has not yet made, so this plan gates it with a decision checkpoint first.

Purpose: D-10 says "Enforce this in the database where possible, not only in code."
Output: a recorded decision. If the trigger is chosen, also the trigger migration, a PostgreSQL-gated test, and the Makefile and skip-gate wiring.
</objective>

## Phase Goal

**As a** community owner, **I want to** make one group my Staff Group and link my groups to it, **so that** staff have one control room.

**This slice:** the database itself guarantees a chat never holds both roles, even under concurrent requests on several replicas.

## Assumptions recorded

- A8: a per-chat `pg_advisory_xact_lock` taken first inside a BEFORE trigger, followed by the cross-table check, makes the exclusivity race-free under READ COMMITTED. The 20-iteration concurrency case in the PostgreSQL test verifies this in CI.
- A10 / OQ4: unresolved until the checkpoint below. If the owner chooses app-level only, the in-transaction checks in `CreateStaffGroup` (plan 01-02) and `CreateLink` (plan 01-05) are the only cross-table enforcement. They prevent the overlap on one replica but do not close the two-replica race: `/setstaff X` and a link of X running at the same moment on different replicas can both commit, which leaves X as both a Staff Group and a linked group. Nothing in this phase detects or repairs that state. The hourly sweep in plan 01-10 deletes only orphan links (`DeleteOrphanLinks`: links whose `staff_chat_id` has no `staff_groups` row) and never looks for a chat that holds both roles. RESEARCH.md A8 lists such a sweep check as a mitigation, but no plan in this phase implements it. The overlap stays until the owner removes one role by hand, with `/unsetstaff` (plan 01-02) or `/unlinkstaff` (plan 01-06) in that chat. The race window is narrow: both paths require X's live creator, so only X's own owner can trigger it, by starting both at the same moment. With pg-trigger, the trigger closes the race and the 20-round concurrency subtest checks that in CI.
- The trigger error is a generic DB error to the repository. A race loser gets the could-not-verify reply, and a retry hits the app-level check, which gives the precise reason (fail closed). This keeps the plan from editing `alita/db/staff/repository.go`, which plan 01-02 owns in this wave.
- No PostgreSQL server exists in this sandbox. The trigger test runs in CI (the migration-chain step applies the migration, then `make test-postgres-integrity` runs the test).
