# Phase 9 - Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram client to bot (callback data) | Callback data is client-controlled and delivered to every member's client; a modified client or userbot can send any bytes. Nothing in it is an authority; the only authority is the live `getChatMember` of the presser |
| Group member to group menu | A menu posted in the group is readable, and its buttons pressable, by every member |
| Forwarded or copied menu to another chat | A menu message may sit in a chat other than the one it was drawn for; the press is judged in the chat the message really sits in |
| Anyone to the deep link, private chat to a group's settings | A `t.me/<bot>?start=settings_<chat id>` link can be tapped, and the payload typed, by anyone; a private menu acts on another chat than the one it sits in, named by an unauthenticated `c` |
| Menu values to the settings rows | `captcha_settings`, `antiflood_settings` and `chat_raid_detection` are reached only through one validating apply function per setting, shared with the command |
| Admin to a group's lockdown | A lift reopens a group under raid; it needs the restrict right, the restore-then-record order, and must happen once |
| Issuer to the Staff Group link | Linking and unlinking need the live creator of both groups; the refactor must keep every check in order |
| Group-menu readers to the Staff Group's identity | A group menu is readable by every member of the linked group, and a private menu by every live admin of it, who need not be staff |
| Translation files and stored user text to rendered messages | Locale text, group titles, names and a lockdown's reason are spliced into HTML messages and alerts |
| Help text, docs and the checklist to readers and the owner | Public text describing the menu's rights; a hand-run checklist on the owner's real groups |

## Unregistered Flags

The 14 SUMMARY files list no threat flag. This audit found five items that no plan registered; none is a failed mitigation and none reaches the `high` threshold.

- **U-1, WARNING (unregistered), the private press keeps the "is the bot in chat X" oracle that IN-03 closed on the deep link (severity low).** `settings_menu.go:304-312`: for a private menu, `getChatMember(c, presser)` failing with a bot-missing error ("bot was kicked", "bot is not a member", "chat not found") is `p.cannotOpen()` (alert `settings_cannot_open_alert` plus an edit) before the presser's rights are known, while a chat where the bot is present answers a non-admin `settings_not_admin` (`:315-317`). `c` is unauthenticated callback data, so a user with a modified client can send `settings|v1|c=<id>` on any message the bot sent them privately and learn from the two answers whether the bot is in any chat ID they try. The deep link was changed for exactly this reason (`settings.go:120-124`); the press path was not, because a stale menu of a real admin needs the cannot-open note (D-11) and the bot cannot prove the presser's role once it is gone. Impact: bot membership of a chat ID (Telegram chat IDs are not secret); no write, no data; each probe costs the prober a callback and the bot one or two reads. Optional hardening: answer a bot-missing error on a private press the way a non-admin is answered, or record it in `AGENTS.md` as accepted. On the deep link, a lookup that fails for another reason answers `settings_check_failed`, which can differ from `settings_start_not_admin` (O-7).
- **U-2, WARNING (unregistered), a settings callback can be aimed at any message of the bot in a chat the presser administers (severity low).** The press edits or deletes the message the button sits on (`p.edit`, `closeMenu`: `settings_menu.go:127-140,404-411`) and trusts nothing in `query.Data` about which message that is. A user with a modified client who is a live administrator of a group can send a well-formed `settings|v1|a=cl&u=<own id>` (or `a=bk`) on another message the bot posted there (a welcome, a captcha challenge, a lockdown alert, a staff card) and delete it or overwrite it with the Main page. It needs a live admin of that chat, who can already delete the bot's messages, and leaves every setting untouched; the same holds for every callback module of the bot, because `AGENTS.md` states callback data is unauthenticated. Noted for completeness; no hardening needed beyond the live admin check.
- **U-3, WARNING (unregistered), opening or refreshing the Staff Group page is a live-health refresh that can write (severity low).** `settingsStaffRender` calls `buildStaffPanelRows` (`settings_staff.go:265-284`), which runs `recheckLink` and `applyLinkHealth` (`staff_panel.go:455-471`, `staff_recheck.go:162-247`): the same conditional statements as `/staff`, Refresh and the hourly sweeper (`DeleteLinkIfOwner` removes a link whose recorded owner is no longer the live creator, `SetLinkHealth` records a health change, each posts one notice to the Staff Group only when `RowsAffected == 1`). Through the menu the trigger is any live administrator of a linked group, including a non-creator admin in a private menu, because Open needs only `settingsRightAdmin`. The outcome is decided by Telegram's live answer and the presser cannot choose it; the cost is that of AR-09-09. Noted because the plans call only the Staff Group's own variant read-only and say nothing of this trigger for the linked group's variant.
- **U-4, WARNING (unregistered), hardening: the private press writes to the chat `getChat` returned, while authority was checked for `c` (severity low).** `settings_menu.go:300-343`: the live check uses `groupID` (the parsed `c`), then `p.group = &group` from `full.ToChat()`, and every write uses `p.group.Id`. Telegram answers `getChat` with the chat asked for (a migrated group's old ID is an error), so the two are equal, and no assertion or test pins it. A defensive `group.Id == groupID` check would make the equality explicit.
- **U-5, info, documentation drift.** `09-CONTEXT.md` D-26 still says the menu Lift posts the public notice "in both menu variants"; WR-04 amended it for the group variant, and the amendment lives in `09-REVIEW-FIX.md` and `AGENTS.md` only. Not a code gap.
