## Phase Goal

**As a** group owner, **I want** members' commands, late edits and, when I choose, every message removed automatically, **so that** the group stays clean and an edited message cannot slip spam in later.

After this plan a self-destruct entry handed to the batcher becomes a durable queue row without the dispatcher ever waiting on the database, sheds toward keeping a message under load, stops cleanly at shutdown, and the worker drains many busy groups at once and never deletes after the owner switched the rule off.

<objective>
Build the self-destruct write path (D-07, D-08, D-09, D-27): a bounded in-process batcher that turns offered entries into `deletion.ScheduleBatch` writes with the rule re-check (D-26a), the exact ceiling (D-09, D-31) and the shed accounting; join it into `StopDeletionWorker`'s 3 s wait (D-19); and change the worker so it claims 1000 rows a cycle (D-32) and screens claimed self-destruct rows against the current rule (D-26b). The tracer comes first: one offered entry flushed and then deleted by the real worker.
Purpose: plan 17-07's watcher only offers entries; everything durable, bounded and shutdown-safe about self-destruct lives here.
Output: one production file, worker changes, two test files, toolkit additions, AGENTS.md.
</objective>

## Planner assumptions (flagged)

- Execution rules are `handoff/executor-brief-17.md`'s; "of NN" reads "of 11". Invariant gates use `42c48c4`.
- The Staff Group read of the flush lives inside `deletion.ScheduleBatch` (plan 17-01, deviation note 1); the flush makes no second read.
- The flush order: take everything buffered (non-blocking), dedupe by (chat, message) keeping the earliest `delete_at` (`SentAt + DelaySecs`), group by chat in ascending chat ID, and per chat: one `deletionRulesLookup` (the self-destruct rule present and accepted by `deletion.ValidateRuleDelay`, else the chat's entries are dropped as correct, not shed; an unreadable rule drops them as a shed: the message is kept); one `deletion.CountPending(ctx, chat, deletion.KindMemberSelfDestruct, memberSelfDestructCeiling)`; room is the ceiling minus the count, and entries past it (latest first) are shed; then one `memberDeleteBatchWrite` over every kept entry of every chat; a returned error is logged once by chat count and its entries are shed. Each flush runs on `context.WithTimeout(context.WithoutCancel(<batcher context>), deletionRecordTimeout)` and wakes the worker only when a written entry is already due.
- Shed reasons are counted separately (full channel, draining, ceiling, unreadable rule, failed write) in atomic counters read by the tests; the log gate allows one Warn per chat per hour with the chat ID and the reason name only, never a message ID; when the gate's map holds 10,000 chats it forgets entries older than an hour, and when none can be forgotten it logs nothing more for a new chat (one process-wide warning says so once).
- The batcher goroutine starts in `StartDeletionWorker` (idempotent, beside the worker, `defer error_handling.RecoverFromPanic`), loops on a ticker of `memberDeleteFlushEvery` and a non-blocking kick that `memberDeleteOffer` sends when the buffer reaches `memberDeleteFlushAt`, and on its stop signal runs one final flush bounded to 2 s on a detached context, then closes its done channel. `StopDeletionWorker` keeps its existing order (cancel the root first), sets draining, signals the batcher, and waits for both done channels against one `time.After(deletionWorkerStopWait)`.
- Test hygiene: fresh chat IDs (`uniqueModuleChatID()`); every test that offers entries drains the queue in `t.Cleanup` (`drainMemberDeleteQueue`) before the row cleanup; a test that starts or stops the worker registers `restoreDeletionWorker` and `restoreMemberDeleteBatcher`; swapped package variables (`deletionBatch`, `memberSelfDestructCeiling`, `memberDeleteBatchWrite`, `deletionRulesLookup`, `memberDeleteQueue`) are restored through `mreqSwap`; `deletionInline.wait` is registered last; no case is skipped.
