# Phase 17 - UI Design Contract

> Visual and interaction contract for the **Member messages** section of the Deletion page of the settings menu: one
> new hub line and cell, one section list, three row screens (Commands, Edited messages, Self-destruct), the one
> two-tap confirm card (Self-destruct on or a changed delay), the delete-right line on every one of them, the Staff Group
> exclusion, every new callback with its worst-case size, every new string with its key and ceiling, and the checks that
> prove it.
> Generated by gsd-ui-researcher; to be verified by gsd-ui-checker.
> Upstream: 17-CONTEXT.md D-01..D-20 (provisional owner defaults, treated as locked here; the UI decisions are D-14 to
> D-18, and D-01 to D-13 define the behaviour the copy must state truthfully), REQUIREMENTS DEL-03, DEL-04, DEL-05,
> ROADMAP Phase 17, the APPROVED Phase 16 contract (`16-UI-SPEC.md`, whose tokens, layout rules, copy register, status
> line, row and section screens, size budgets and numbered assumptions this file reuses and continues: M24 to M28 and
> A16-A1 to A16-A15 stay in force, this file continues with M29 and A17-A1), AGENTS.md (Callbacks `settings|v1`, the
> Deletion page bullet, the Member requirements page bullet for the card shape, Permissions, Subsystem traps) and the code
> of `fuku/modules/settings_deletion.go`, `deletion_kinds.go`, `settings_card.go`, `settings_menu.go`,
> `fuku/db/deletion/kinds.go` and `locales/en.yml`.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard, on the one
surface the settings menu always had: the menu message, private or opened in the group, edited in place. There is **no
group-side text** in this phase: the deletions themselves post nothing (a command, an edit and a self-destruct delete are
silent), so no group string exists. Anything not restated here is unchanged and applies to the new section: the message
anatomy, text styling, the press pipeline (`settingsPress.verify`, owner gate at step 4b, one answer per press), the
rights model, the delete-right line, the "never name the Staff Group" rule (D-21, D-32 of the menu) and the Phase 11 to 16
limit tables.

The section is a table entry of the existing page (`settingsDelSections`) and three rows of a new row table
(`deletionMemberRows`); `settings_pages.go` is **not** edited (D-14). All three rules are **Off by default** (a missing row
means Off) and nothing is preselected.

new screen (the tallest has 4 of 8).

**Why `{1,3,3}` for the seven Self-destruct choices (A17-A7).** There are seven buttons (Off and six delays). Rows of at
most three are the proven shape (Phase 13 Kick, Ban, Mute; Phase 16 `[10 s, 1 min, 10 min]`): the widest cell is
`✅ ` + a delay label, and the delay labels are at most 6 code points in English and 10 in the other languages (Phase 16
ceilings, the new `5 min` and `15 min` included), so a cell is at most 12 code points and a row of three at most 36, well
under the 15-per-cell ceiling and the width that fits a phone. A row of four (`[Off, 1 min, 5 min, 10 min]`, `[1 h, 6 h,
24 h]`) would put 4 cells of up to 12 in a row (48) and would wrap in hi, ru and uk. `{3,3,1}` leaves one stranded
`24 h` cell. `{2,3,2}` mixes. `{1,3,3}` puts the **switch (Off) apart from the delays**, which is the real distinction on
this screen (Off cancels what is queued, a delay does not), reads in ascending order left to right and top to bottom, and
keeps the two delay rows identical in shape to the Phase 16 bot screen.

## Text Styling (replaces Typography)

Phase 11 to 16 styling stands: `<b>` only on "Settings" and the group title, `<code>` on the chat ID, plain text for names,
state words, status lines and hints, button labels plain text. **No new markup.** Command names are plain text and are not
translated. The delete-right line keeps its code-side prefix (`🚫 ` or `❔ `), and the state icon of a line and of a cell is
a code-side prefix (`{icon} {name}`), so a name is the same string in the cell, the line and the screen title. The card text
is two paragraphs inside one key, separated by a blank line (`\n\n`, as `settings_edit_wait_text` does), so the card needs
no second key.

**No string of this phase carries a group title, a member, a user, a chat ID, a count of messages or members, the Staff
Group or a number other than `{n}` (the hub and Main state, and the custom delay) and `{delay}` (a preset label).**

## Status Icons (replaces Color)

Phase 16's three state icons stand (`➖` none, `🗑` delete now / on, `⏳` a delay) and its `🚫` `❔` `✅` `⚠️`. This phase
adds **one icon**, the section's `💬` (hub cell and hub line; unused by every other page and section: pages `👥 🔒 🧩 🌊 🔑 🎉 👋
📜 🛂 🧹`, sections `🔔 🤖`; confirmed by `grep` of the settings code, 2026-11-12). Each member row draws its stored state as:

| Row | Stored | Icon | Word (key) | Marked choice |
|-----|--------|------|------------|---------------|
| Commands | no row | `➖` | Off (`settings_state_off_plain`) | Off |
| Commands | 0 | `🗑` | On (`settings_del_state_on`, via `ZeroKey`) | On |
| Edited messages | no row | `➖` | Off | Off |
| Edited messages | 30, 60, 300, 900, 3600 | `⏳` | Grace {delay} (`settings_del_state_grace`, via `AfterKey`) | that preset |
| Self-destruct | no row | `➖` | Off | Off |
| Self-destruct | 60, 300, 600, 3600, 21600, 86400 | `⏳` | After {delay} (`settings_del_state_after`) | that preset |

Why the Edited row says **Grace** and not `After {delay}`: `After 1 min` reads as "deleted 1 minute after sending", which is
the Self-destruct rule, and is false for edits (the message is deleted when the edit is made, only if the edit is later than
the grace). DEL-04 and D-05 call the number the grace period, so the state word is "Grace 1 min" and the description
explains it. Why `🗑 On` for Commands: the command message is deleted (no wait beyond the bot's own answer), and a stored 0 is
a switch there, so the word is On, not Delete now.

A stored value that no row choice carries (reachable only from outside the menu, a database edit) follows Phase 16 section 2
unchanged: the row's `AfterKey` template with `settings_del_delay_custom` (`{n} s`) and **no choice marked**; a stored 0 on
a row that does not offer 0 (Edited messages, Self-destruct) reads `🗑` `Delete now` and marks nothing, as a 0 on a bot row
does (A17-A10).

### 2. Choosing a value (D-05, D-09, D-15)

Presets are the only choices; there is no stepper, no typed number, no custom delay (D-15, deferred). Every button sends the
**absolute** target in `v`, so a double tap is harmless:

| `v` | Commands | Edited messages | Self-destruct | Label key |
|-----|----------|-----------------|---------------|-----------|
| `n` | Off | Off | Off | `settings_state_off_plain` |
| `0` | **On** | no | no | `settings_del_state_on` |
| `30` | no | yes | no | `settings_del_delay_30s` (new) |
| `60` | no | yes (the 1-minute default, not preselected) | yes | `settings_del_delay_1m` |
| `300` | no | yes | yes | `settings_del_delay_5m` (new) |
| `600` | no | no | yes | `settings_del_delay_10m` |
| `900` | no | yes | no | `settings_del_delay_15m` (new) |
| `3600` | no | yes | yes | `settings_del_delay_1h` |
| `21600` | no | no | yes | `settings_del_delay_6h` |
| `86400` | no | no | yes | `settings_del_delay_24h` |

Validation, in step 1 before any I/O, `common_callback_invalid_request`: a control's `Validate` accepts exactly its row's
presets in canonical digits or `n` (A16-A5): `mc` takes `n` and `0` only; `me` takes `n, 30, 60, 300, 900, 3600`; `ms` takes
`n, 60, 300, 600, 3600, 21600, 86400`. `v=60` on `mc`, `v=30` on `ms`, `v=0` on `me` or `ms`, `v=600` on `me`, `v=05`,
`v=-1`, `v=86401` and `tg` naming any of the three are invalid. The three rules' Go delay rules (D-14) are enforced in the
apply function as well, so a value the table did not catch is refused before any write.

**What a press does**, per row:

| Press | Result |
|-------|--------|
| `mc` `v=0` or `v=n` | writes at once through `applyDeleteRule` (On stores a 0, Off removes the row), redraws the row from the read-back |
| `me` any value | writes at once (a preset upserts, Off removes the row), redraws the row; no card |
| `ms` `v=n`, a rule is stored | writes at once: removes the row **and drops the chat's pending `member:selfdestruct` queue rows in the same transaction** (D-12), redraws; **no card** (switching it off must stay one tap) |
| `ms` `v=n`, no rule stored | writes nothing, redraws |
| `ms` `v=<preset>`, equals the stored value | writes nothing, **draws no card**, redraws |
| `ms` `v=<preset>`, no rule stored or another value stored | **writes nothing and draws the card** (section 3) |

"The stored value" is judged by the cached loader (`deletionRulesLookup`), whose key `delete_rules:*` is in `skipLocal`, so
another replica is not behind. A failed write redraws the row from the stored state with `⚠️ common_settings_save_failed`
(reused); a read-back that failed reloads through the cached loader, and when that fails too it is the cannot-open edit.
Every write calls `cache.DeleteCache` for every key it affects (the rules key; Self-destruct Off also drops the queue rows).
Turning Commands or Edited messages off drops nothing (D-15 gives them no queue; a command's delete and an edit's delete are
inline decisions).

**The default grace (D-05).** The page offers presets only, so "switching Edited messages on" is always a chosen preset; the
1-minute default of the roadmap is the **one the owner is most likely to tap, not a preselected value**, and not a code path
of the page. (A17-A12.)

### 3. The Self-destruct card (D-15, M30)

- **Draw.** The `st` control of `ms` with a non-Off preset that differs from the stored state draws the card **in place of the
  row screen**, writes nothing, and goes through `settingsDelPrepare` (database read, the press answered empty, one live right
  read), so it carries the delete-right line like every deletion screen.
- **Text.** `settings_del_confirm_self` with `{delay}` = the chosen preset's label: "Delete every message members send from
  now on, 10 min after it was sent?" then a blank line, then what stays. It says exactly D-15's two facts (messages already sent
  are not touched; admins, approved members and pinned messages stay) and that the owner can undo it; it names no member, count,
  chat or Staff Group.
- **Keyboard.** `settingsCardRows`: `[✅ Yes | ❌ No]` (reused `settings_btn_yes`, `settings_btn_no`, which already carry their
  icons) then the navigation row. Yes carries `a=dy`, `t=ms`, `v=<seconds>` and `e`, the expiry minute (unix minutes,
  `settingsCardLifetime` 5 minutes ahead, a variable only for tests); No carries `a=no&p=d`.
- **Yes**, `dy` (`settingsActDelYes`), runs the whole press pipeline again, so a presser **demoted since the first tap is
  refused with `settings_no_change_info`** and nothing is written, and then, in order, each step refusing before the next:
  (1) step 1 strict decode: exactly `t` a row whose table entry has a `ConfirmKey`, `v` that row's preset and never `n`, `e` a
  positive 63-bit number in digits only, else `common_callback_invalid_request` with no `getChatMember`; (2) the Staff Group gate
  (a Staff Group is the generic invalid alert, an unreadable row the cannot-open edit, nothing written); (3) the expiry
  (`settingsCardExpired`): an expired Yes redraws the Self-destruct screen with the existing notice `settings_card_expired`
  ("This confirmation expired. Nothing changed. Ask again.") and writes nothing; (4) the stored-state check: a Yes of the value
  already stored writes nothing and redraws the row (a double tap of Yes is harmless); (5) the write through `applyDeleteRule`
  and a redraw of the row screen from the read-back, with the save-failed notice on a failed write.
- **No**, `no&p=d`, redraws the hub (the helper's `noPage`); nothing is written and the card simply goes away. Expiry is lazy: no
  timer, no Redis key, so the card works on any replica with Redis down, and a card left on screen is harmless.
- **Never a card for**: Off, a press of the stored value, any Commands or Edited messages choice, any Phase 16 row. The card is
  the only safeguard the page adds (D-15).

### 4. The delete-right line (D-16, DEL-08)

Unchanged from Phase 16 section 4 and drawn on **every** member screen: the hub, the Member list, the three row screens and the
card. One live `getChatMember` of the bot per draw through the deletion pacer under `settingsDelHereTimeout` (3 s), after the
press is answered empty and before the edit; nothing when the bot can delete, `🚫 ` + `settings_del_no_right` for a definite
cannot, `❔ ` + `settings_del_right_unknown` for anything that could not be established; never an error text, a refusal or the
cannot-open edit; no button is ever disabled by it. **The Phase 16 keys are reused as they are** (no new key). On the member
screens the line is stricter than on the bot screens: deleting a **member's** message needs the right (a plain-member bot
cannot delete other people's messages at all), so here "some of these settings may not work" is true for all three rules; the
softer wording stays because the line is one shared key (A17-A5).

### 5. Rights, the Staff Group and stale state (D-16, D-17)

| Press | Right | Refusal |
|-------|-------|---------|
| open the page, `dl`, `dr`, Back, Close, No | `settingsRightAdmin` (the live admin check every press makes, plus the owner gate at step 4b) | the pipeline's own |
| a choice on `mc`, `me` or `ms` (`st`) | `settingsRightChangeInfo`: the creator, or an administrator with `can_change_info`, from the same fresh member record | alert `settings_no_change_info`, nothing edited or written |
| the card's Yes (`dy`) | `settingsRightChangeInfo`, judged again on a fresh member record | alert `settings_no_change_info`, nothing edited or written |

- **No command exists** for these rules, so each rule carries a drift test and an authority test in place of a parity test
  (`TestSettingsDriftDeletionMember`, `TestSettingsAuthorityDeletionMember`, D-16).
- **Staff Group** (D-17, unchanged mechanism): the page is not drawn in a Staff Group; a press of `dl`, `dr`, a control or `dy`
  there is the generic `common_callback_invalid_request` as the press's one answer, edits and writes nothing and makes no
  `getChatMember` of the bot (the gate runs before any read, write or right read); an unreadable Staff Group row is the
  cannot-open edit with no write. No screen, card or alert says the group is a Staff Group (D-21).
- **Forged callbacks.** `dl` with `t=m` plus another key, `dr` with a section-only or unknown `t`, `st&p=d` with `t=ms` and a `v`
  outside its presets, `tg` naming a row, `dy` with `t=mc` or `t=me` (no `ConfirmKey`), `dy` with `v=n`, `v=30` or `v=0`, `dy`
  with a missing or non-numeric `e`, an extra key, `c` and `u` together or neither: `common_callback_invalid_request` in step 1,
  before any `getChatMember`.
- **Stale screens.** A card or screen drawn before another admin changed the rule shows the old state until the next press;
  every draw reads the rule fresh through the cached loader (key in `skipLocal`) and the right line fresh. A Yes writes the
  **absolute value its card named** even if another admin changed the rule meanwhile, which is what the card said it would do;
  an expired one writes nothing.
- **Nothing is read or written for a press that does not pass.** The owner gate (4b) re-judges every press, Close included.

### 6. What opening a screen costs

| Draw | Database reads | Telegram calls | Redis |
|------|----------------|----------------|-------|
| Main grid entry and Main state | rules (cached), greetings flag, a fresh Staff Group read | **0** | none beyond the cache's own |
| Hub, Member list, any row screen, the card | rules (cached), the Staff Group read | **1** (`getChatMember` of the bot through the deletion pacer) | the pacer's two slot keys when Redis is configured |
| A choice press (`st`) that writes | the above plus the write and its read-back; Self-destruct Off also the queue-row drop in the same transaction | the pipeline's `getChatMember` of the presser (and `getChat` in a private menu), then **1** for the right line on the redraw | as above |
| A Yes (`dy`) | the Staff Group read, the stored read, the write and the read-back | the pipeline's calls, then **1** for the redraw | as above |
| A press refused (right, Staff Group, forged data, expired Yes) | none or the Staff Group read | the pipeline's own only | none |

No screen starts background work, keeps state or needs a drain; the batcher, the watchers and the worker are the code's, not
the menu's (D-19). The UI adds no Redis key and no migration.

## Accessibility and phone-width notes

- State is never icon alone: every list line and the Currently line carry the state word, and the choice buttons are words.
- The widest rows are `[Off | 30 s | 1 min]`-shaped (three cells of at most 15 code points, the Phase 13 shape) and the card's
  `[✅ Yes | ❌ No]`; the Self-destruct screen's lone `[Off]` is a full-width cell, never wider than any other.
- The hub and the Member list are readable without the keyboard: the body lists every state. The Edited screen's description,
  hint and time line state the whole rule in words.
- `🚫` and `❔` stay distinct from the three state icons; `⚠️` stays reserved for foot notices (the expired card, a failed write).
- A group menu's text is readable by every member of the group and shows which member messages are deleted: this is settings
  content like the other pages' (no member, user or count appears).
- hi, ru and uk cells are checked on a phone (A16-A9) for the three new row names and the section name.
