## Phase Goal

**As a** group admin, **I want to** verify new members with Turnstile in a Telegram Mini App, **so that** bots stay out with little friction.

**This slice:** a member who joins a Turnstile group taps one button, and once the bot's server has checked Telegram's signed data and Cloudflare's answer, the member is unmuted exactly as with the existing captcha.

## Decisions taken here (Claude's discretion, recorded)

- Package `alita/utils/captchaweb` (D-29): imports the standard library, `github.com/redis/go-redis/v9` and `github.com/sirupsen/logrus` only, never a package of this module, so it is testable without a database; the `Backend` implementation lives in `alita/modules/captcha_web.go`.
- Token: 16 bytes from `crypto/rand`, `base64.RawURLEncoding` (22 characters), validated by `^[A-Za-z0-9_-]{1,64}$` (`ValidToken`). Reserved answer: `ts1:` plus 16 random bytes in lowercase hex (D-25), so a forged callback can neither guess nor convert it.
- Redis key `alita:captcha:ch:<token>`: a hash with fields `u` (user ID), `a` (attempt ID), `c` (chat ID), `x` (attempt expiry, unix ms), all decimal strings because Lua numbers lose exactness above 14 digits; TTL = time until the attempt's `ExpiresAt` plus 5 minutes (`ChallengeGrace`). Every Store round trip is bounded at 250 ms (`RedisTimeout`).
- Consume script (research Pattern 10, run on miniredis by the researcher): `HGET u`; absent returns `{0}`; a different user returns `{2}` and changes nothing; the right user gets `{1, pttl, HGETALL}` and the key is deleted. The barrier is the signed `user.id`, never the secrecy of the token (D-26).
- `cData` = lowercase hex of SHA-256 of `cd1:` + challenge (D-19, `CData`); action `captcha_join` (`TurnstileAction`, 12 characters, inside Cloudflare's 32-character rule). The widget option is spelled `cData` (camelCase) in the page (D-27); `siteverify` returns it as `cdata`.
- Verify JSON: request `{"init_data", "turnstile_token", "challenge"}`; response `{"result": passed|failed|expired|invalid|not_for_you|retry, "action": kick|ban|mute}` with `action` only on failed and expired (D-22). Status 200 for a decided answer, 400 `invalid` for a malformed body, 405 for a non-POST, 503 `retry` when Redis or the backend errs. Every answer carries `Content-Type: application/json`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and never an error text, ID or code.
- The challenge the server binds to is the body's `challenge`; when the verified `initData` carries `start_param`, it must equal `challenge` or the answer is `invalid` (D-27, research Pitfall 3).
- Post-claim work runs on `context.WithoutCancel(r.Context())` with its own 20 s deadline (`passWorkTimeout`), so a client that disconnects never abandons an unmute (research Pitfall 5). The finish step (summary, delete challenge, success note, greeting) runs through `startCaptchaLifecycleTask`, which joins `captchaLifecycleWG` that `StopCaptchaLifecycle` already drains, or inline when the lifecycle is not running; no new shutdown drain.
- Availability (D-09): `captchaWebAvailable` = a runtime is installed, the bot has a username, and a Redis `PING` under 250 ms succeeded within the last 5 s (memoised in atomics, so a raid of joins costs one probe per 5 s). `cache.IsRedisAvailable` is not used: it only says a client object exists. A fallback to math logs one Info line at most once a minute.
- The Turnstile challenge message uses the new keys `captcha_web_welcome` (`%s` mention, `%d` minutes, the shape of the existing `captcha_welcome_*` keys, called with `i18n.TranslationParams{"first", "number"}` exactly like them) and `captcha_web_button` (UI-SPEC "Challenge message").
- Environment: golangci-lint cannot lint Go 1.26 here, so `go vet -tags testtools` and `gofmt -l` stand in for `make lint`. The orchestrator runs `make test` after the wave.
