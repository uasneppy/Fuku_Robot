# Phase 8 — UI Design Contract

> Visual and interaction contract for the Turnstile captcha page (a Telegram Mini App) and the Telegram-side
> messages around it. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Upstream: 08-CONTEXT.md D-01..D-18 (especially D-04, D-09, D-10..D-14), REQUIREMENTS CAPT-01..08, PLAT-04.

There is exactly one screen: one embedded static HTML page, opened by Telegram inside its WebView on Android, iOS
and Desktop (and the Web clients), usually as a compact bottom sheet about 320 px wide. Everything else in this
phase is a Telegram message or a command reply (section "Telegram-side pieces").

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none (hand-written HTML + CSS + a small script; no framework, no build step) |
| Icon library | none: 8 inline SVG icons authored in this spec (stroke icons, 24x24 viewBox) |
| Font | system stack only, no external fonts: `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, "Noto Sans", sans-serif` (Devanagari and Cyrillic fall back to the platform's own faces) |

Design source of truth for colour, surface and text: Telegram's `themeParams`, exposed as `--tg-theme-*` CSS
variables by `telegram-web-app.js`, each with a safe fallback (section Color). There is no brand palette. Telegram
exposes no corner-radius parameter, so radius is fixed (12 px).

Project scan (Step 2): no `components.json`, `tailwind.config.*`, `package.json`, or any `.tsx`/`.css` in the repo.
The Go HTTP server (`alita/utils/httpserver/server.go`) is the only host. Nothing existing to reuse or re-specify.

## Page Anatomy and Layout

Single column, centred, one panel. Order top to bottom, all centred text:

1. Icon (48 x 48, decorative, `aria-hidden="true"`)
2. Headline (`<h1>`)
3. Body line (`<p>`)
4. Action slot: either the Turnstile widget region (ready state only) or one button (try-again, failed, expired, invalid) or nothing (loading, verifying, passed, unsupported)

Containers:

| Element | Contract |
|---------|----------|
| `<body>` | margin 0; background `--c-bg`; `min-height: var(--tg-viewport-stable-height, 100dvh)`; overflow-y auto (the sheet may scroll, never clip); `color-scheme: light dark` |
| `<main>` | `max-width: 360px`; margin-inline auto; flex column, `align-items: center`, `justify-content: center`, `min-height` of body; vertical gap per spacing table |
| Panel (`.panel`) | background `--c-surface`; radius 12px; padding 24px 16px; width 100% |
| Safe area | `padding-top: max(24px, env(safe-area-inset-top), calc(var(--tg-safe-area-inset-top, 0px) + var(--tg-content-safe-area-inset-top, 0px)))`; same for left/right; `padding-bottom: max(24px, env(safe-area-inset-bottom), var(--tg-safe-area-inset-bottom, 0px))` |
| `<meta viewport>` | `width=device-width, initial-scale=1, viewport-fit=cover` (needed for `env(safe-area-inset-*)`) |
| `<html lang>` | the user's locale code (`en`, `es`, `fr`, `hi`, `id`, `pt`, `ru`); set at boot to the resolved language and updated if it changes |
| `<title>` | key `captcha_web_page_title` |
| Robots | `<meta name="robots" content="noindex">` |

Responsive rules (320 px is the design width; nothing may depend on a wider viewport):

- Content width at 320 px viewport = 320 - 2x16 = 288 px. Cloudflare's normal and flexible widget sizes need 300 px, so the page renders the widget as `size: 'compact'` (150 x 140) when the widget container is narrower than 300 px, otherwise `size: 'flexible'`. Decide once, at render time, from `container.clientWidth`.
- The widget region reserves its height before the widget exists (`min-height: 65px` flexible, `140px` compact) so the layout does not jump when the widget appears.
- When `window.innerHeight < 420` (compact sheet with the larger widget) the icon is hidden (`display: none`); the headline and body already carry the state, the icon is decorative.
- Text wraps, never truncates, never uses `text-overflow: ellipsis`. Headline up to 2 lines, body up to 5 lines at 288 px.
- No horizontal scrolling at any width from 280 px up; no fixed pixel widths on text blocks; `overflow-wrap: anywhere` on headline and body (long Russian and Hindi words).
- No `expand()` call: the page keeps whatever size Telegram opened it at (compact sheet or full). It calls `Telegram.WebApp.ready()` once the first paint is done, and `disableVerticalSwipes()` when `isVersionAtLeast('7.7')` so a swipe during the solve does not close the sheet. It calls `setHeaderColor('bg_color')` and `setBackgroundColor('bg_color')` when available.
- Optional, to be confirmed in the spike (`08-SPIKE.md`): append `&mode=compact` to the Mini App direct link so Telegram opens the compact sheet. Not required for the contract.

Three sizes, two weights. Sizes in `rem` with 1rem = 16px so the platform's text-size setting is honoured.

## Color

All colours are CSS custom properties. Each takes the Telegram variable first and a fallback second. The fallbacks
below are the values used when `--tg-theme-*` is missing (before `telegram-web-app.js` has run, or outside Telegram)
and are chosen to meet the contrast rules; light is the default, dark applies under
`:root[data-theme="dark"]` (set from `Telegram.WebApp.colorScheme`) and, before that attribute exists, under
`@media (prefers-color-scheme: dark)`.

| Token | Telegram variable | Fallback light | Fallback dark | Role |
|-------|-------------------|----------------|---------------|------|
| `--c-bg` | `--tg-theme-bg-color` | #ffffff | #212121 | Dominant (60%): page background |
| `--c-surface` | `--tg-theme-secondary-bg-color` | #f1f1f4 | #181818 | Secondary (30%): the panel |
| `--c-text` | `--tg-theme-text-color` | #000000 | #ffffff | Headline, body |
| `--c-hint` | `--tg-theme-hint-color` | #5f6368 | #aaaaaa | Neutral icons (loading, expired, try-again, invalid, unsupported), caption |
| `--c-accent` | `--tg-theme-button-color` | #1c6fc2 | #8ab4f8 | Accent (10%) |
| `--c-on-accent` | `--tg-theme-button-text-color` | #ffffff | #0b1a2e | Label on the accent button |
| `--c-danger` | `--tg-theme-destructive-text-color` | #c62828 | #ff8a80 | The failed-state icon only |
| `--c-success` | none (fallback only) | #1e7e34 | #5fd07a | The passed-state icon only |

Accent reserved for: (1) the fill of the single action button, (2) the ready-state shield icon and the
loading/verifying spinner arc. Nothing else: not links, not the headline, not the focus ring (the ring uses `--c-text`
because an accent ring is invisible on an accent button). Destructive and success colours are never used for text or
fills, only for the one icon of their state, and every state also differs by icon shape and headline text, so colour is
never the only signal.

Computed contrast of the fallbacks (WCAG 2.x relative luminance):

| Pair | Light | Dark | Needs |
|------|-------|------|-------|
| text on bg | 21:1 | 16:1 | 4.5 |
| text on surface | 18:1 | 17:1 | 4.5 |
| hint on bg | 6.0:1 | 6.9:1 | 4.5 |
| hint on surface | 5.3:1 | 6.3:1 | 4.5 |
| on-accent on accent | 5.1:1 | 8.3:1 | 4.5 |
| accent on bg (button edge) | 5.1:1 | 7.6:1 | 3 |
| danger on surface (icon) | 5.0:1 | 6.6:1 | 3 |
| success on surface (icon) | 4.5:1 | 7.9:1 | 3 |

Contrast guard (required): Telegram's own themes can fail 4.5:1 (its default blue button with white text is about
4.1:1; its default hint grey is lower). At boot and on every `themeChanged` event the script computes the ratio of
`text/bg`, `text/surface`, `hint/surface` and `on-accent/accent` from the resolved variable values. Any pair under 4.5:1
is replaced by the fallback for the active scheme (for the button pair both colours are replaced together). The user
still sees their Telegram theme whenever it is readable.

Turnstile widget theme: `theme` is `Telegram.WebApp.colorScheme` (`'light'` or `'dark'`), never `'auto'`, so the iframe
matches the Telegram theme and not the OS setting.

## State Machine and Per-State Contract

Eight visible states. Every state is: icon + one headline + one body line + at most one button. State content is
rendered into one live region; switching state replaces the text with `textContent` (never `innerHTML`).

| State id | Icon | Headline key | Body key | Button (key) | Entered when | Leaves when |
|----------|------|--------------|----------|--------------|--------------|-------------|
| `loading` | spinner | `captcha_web_loading_title` | `captcha_web_loading_body` | none | page start | Telegram object and `initData` present and Turnstile script loaded and widget rendered -> `ready`; no `window.Telegram.WebApp` after 8 s, or `initData` is empty -> `unsupported`; Turnstile script not loaded after 10 s -> `retry` |
| `ready` | shield | `captcha_web_ready_title` | `captcha_web_ready_body` | none (the widget region is the action) | widget rendered | widget `callback(token)` -> `verifying`; `error-callback`, `timeout-callback`, `expired-callback` -> `retry` |
| `verifying` | spinner | `captcha_web_verifying_title` | `captcha_web_verifying_body` | none; the widget region is removed from view and from the tab order | widget returned a token and the one POST was sent | server answer arrives, or the 12 s client timeout fires |
| `passed` | check | `captcha_web_passed_title` | `captcha_web_passed_body` | none | server answer `passed` | `Telegram.WebApp.close()` after 2000 ms |
| `failed` | cross | `captcha_web_failed_title` | `captcha_web_failed_body_<action>` | Close (`captcha_web_close_button`) | server answer `failed` with `action` kick, ban or mute | terminal |
| `expired` | clock | `captcha_web_expired_title` | `captcha_web_expired_body_<action>` | Close (`captcha_web_close_button`) | server answer `expired` with `action` | terminal |
| `retry` | retry | `captcha_web_retry_title` | `captcha_web_retry_body` | Try again (`captcha_web_retry_button`) | see Interaction contract | tap -> widget reset -> `ready` |
| `invalid` | slash | `captcha_web_invalid_title` | `captcha_web_invalid_body` | Close (`captcha_web_close_button`) | server answer `invalid` or `not_for_you` (another member, or token used or unknown); no action was taken | terminal |
| `unsupported` | info | `captcha_web_unsupported_title` | `captcha_web_unsupported_body` | none (there is no Telegram to close) | no Telegram WebApp object or empty `initData` | terminal |

Terminal states never navigate. `failed`, `expired`, `invalid` and `unsupported` show no countdown and never retry.
Only `retry` can go back to `ready`.

Which body to show for `failed` and `expired`: the group's failure action is kick (default), ban or mute, and only a
kick lets the member rejoin, so the page picks `_kick`, `_ban` or `_mute` from the `action` field of the server answer
(an unknown or missing `action` uses `_kick`, the group default). The body text states what the server already did in the past tense ("You were removed...").

The page never says "you passed" or "you failed" on its own: it renders a state only from a server answer
(`passed`, `failed`, `expired`, `invalid`, `not_for_you`, `retry`) or from a local, non-decision condition
(`loading`, `ready`, `verifying`, `unsupported`, `retry` for a client error).

Transitions animate with a 150 ms opacity fade of the text block; under `prefers-reduced-motion: reduce` there is no
animation at all (instant swap, static spinner arc). The `passed` auto-close delay (2000 ms) is unchanged by reduced
motion, so a screen reader has time to announce the headline.

Haptics (optional, feature-checked): `HapticFeedback.notificationOccurred('success')` on `passed`, `'error'` on
`failed` and `expired`. Never required.

## Interaction Contract

Boot sequence:

1. HTML paints in the `loading` state with English text from a static fallback (the page ships a first-paint English
   `loading` block so it is never empty).
2. The server has embedded the string table for all 7 locales as `<script type="application/json" id="i18n">` (JSON
   escaped for `</script>`), plus `data-sitekey`, `data-action` and `data-turnstile-lang` attributes on `<main>`. All
   values are plain text: no HTML, no format verbs, no emoji, no placeholders.
3. Language resolution (display only, never a trust decision): `Telegram.WebApp.initDataUnsafe.user.language_code`,
   else `navigator.language`, else `en`. Lowercase, take the part before `-`, map `in` to `id`, accept only
   `en es fr hi id pt ru`, anything else is `en`. Set `<html lang>` and render. The server still derives the language it
   trusts from the verified `initData` for anything it sends in Telegram; the page's language choice affects no
   decision.
4. Read the challenge token from `Telegram.WebApp.initDataUnsafe.start_param`. A missing or malformed value (not
   `[A-Za-z0-9_-]{1,64}`) goes straight to `invalid` with no widget and no POST.
5. Render the Turnstile widget with `turnstile.render(container, options)`:

| Option | Value |
|--------|-------|
| `sitekey` | `data-sitekey` (server-injected) |
| `action` | `data-action` (server-injected, a fixed string such as `captcha_join`; the server requires `siteverify` to echo it) |
| `cdata` | derived from the challenge token (see "cdata delivery" below) |
| `theme` | `Telegram.WebApp.colorScheme` |
| `size` | `'flexible'` or `'compact'` (see Page Anatomy) |
| `language` | `data-turnstile-lang` (server-injected code for the resolved locale, or `'auto'`) |
| `appearance` | `'always'` (the widget region is the instruction, no hidden widget) |
| `retry` / `refresh-expired` / `refresh-timeout` | `'never'` (the page, not the widget, decides when to reset; the widget is reset only from the `retry` state) |
| `callback` | `onToken` |
| `error-callback`, `timeout-callback`, `expired-callback` | `onWidgetProblem` (-> `retry`) |

The option names above are the Cloudflare client-side names as known to the researcher; the Cloudflare docs were not
reachable from this session, so the executor must confirm each name and each `language` code against Cloudflare's
current "client-side rendering" and "supported languages" pages. An unconfirmed language code maps to `'auto'`.

Submit rules:

- `onToken(token)` sets a module-level `submitting = true` and returns immediately if it was already true (callbacks
  can fire twice). It switches to `verifying`, then sends exactly one request:
  `POST /captcha/verify`, `Content-Type: application/json`, body `{ "init_data": Telegram.WebApp.initData,
  "turnstile_token": token, "challenge": start_param }`, `credentials: 'omit'`, `cache: 'no-store'`, timeout 12 s via
  `AbortController`. The server SHOULD also require `challenge` to equal the `start_param` inside the signed
  `initData`.
- The page never retries a POST by itself and never sends a second request for the same widget token (Turnstile tokens
  are single use). A repeated tap, repeated callback or `Enter` key does nothing while `submitting` is true.
- The page never logs or displays `initData`, the Turnstile token, the challenge token, user ids, HTTP status codes or
  response bodies. `console.*` is not used on the success or answer path.
- The Telegram `main button` and `secondary button` are not used; the page has its own single in-page button.

Server answer to state mapping (JSON `result` is the only field that picks a state; `action` is read only for
`failed` and `expired`):

| Server `result` | HTTP | State |
|-----------------|------|-------|
| `passed` | 200 | `passed` |
| `failed` | 200 | `failed` (+ `action`) |
| `expired` | 200 | `expired` (+ `action`) |
| `invalid`, `not_for_you` | 200 or 4xx | `invalid` |
| `retry` | 200 or 5xx | `retry` |
| network error, timeout, 429, 5xx, non-JSON, unknown `result` | any | `retry` (a client or transport problem is never reported as a failed solve) |

`retry` state: the button `captcha_web_retry_button` calls `turnstile.reset(widgetId)`, clears `submitting`, and
returns to `ready` (the only place the widget is reset). If the widget was never rendered (the Turnstile script did
not load) the button calls `location.reload()` instead, which keeps the hash launch parameters. Tapping Try again is
allowed any number of times; the group's time limit still applies and the server rate-limits.

`passed` state: after 2000 ms call `Telegram.WebApp.close()` (guarded; if it is missing, the passed state simply stays
on screen). `failed`, `expired`, `invalid`: the Close button calls `Telegram.WebApp.close()`.

cdata delivery (decision and a conflict with the brief): the brief says the server injects the `cdata` value. The page
is served by `GET /captcha` before anyone knows which challenge will open it, and Telegram passes `startapp` only in the
URL fragment and in the signed `initData`, so the server cannot inject a challenge-specific value into the HTML. The
contract therefore sets `cdata = lowercase hex of SHA-256("cd1:" + start_param)`, computed by the page with
`crypto.subtle.digest`, and the server recomputes it from the challenge token it consumed and requires `siteverify` to
echo it (D-03). The prefix string `cd1:` is the only server-chosen constant and is injected as `data-cdata-prefix` so
the server can rotate it. If the planner prefers a server-issued value, the alternative is an extra route that returns
it for a given `initData`; that adds a route D-10 does not list, so it is not the default. Either way the UI is
unchanged.

Server-contract dependencies the UI relies on (planner must carry these into the plans):

1. D-03 consumes the challenge token with a compare-and-delete when verification starts. A `retry` answer (Cloudflare
   or network error, D-09) must give the challenge back (same token, remaining lifetime unchanged), otherwise the
   Try again button can never succeed and every error silently becomes a failure at the time limit. A `failed`,
   `passed`, `expired` or `invalid` answer must not.
2. `failed` and `expired` answers carry `action` (`kick`, `ban`, `mute`), the group's failure action, already applied.
3. All answers are generic: no error text, no ids, `Cache-Control: no-store`.

## Accessibility Contract

| Requirement | Contract |
|-------------|----------|
| Status region | the headline + body block is `<section id="status" role="status" aria-live="polite" aria-atomic="true">`; its text is replaced on each state change so the new headline and body are announced once |
| Heading | one `<h1>` per state (the headline), inside the status region |

| Contrast | text >= 4.5:1, icons and button edge >= 3:1 against both fallback themes (table in Color), enforced at runtime by the contrast guard |
| Not colour alone | each state has a distinct icon shape and a distinct headline; success and danger hues are never the only difference |

| Widget label | the widget container is `role="group"` with `aria-label` from `captcha_web_widget_label` |
| Pressed feedback | `button:active { opacity: .85 }` (not colour only) |
| Zoom and text size | rem units, no `user-scalable=no`, no `maximum-scale` |
| Direction | left-to-right only (RTL is out of scope) |
| No-JS | `<noscript>` block with the English `captcha_web_unsupported` text in Caption style; the page cannot work without script |

Button style (the only one): width 100%, min-height 48px, padding 0 24px, radius 12px, border 0, background
`--c-accent`, label colour `--c-on-accent`, Button typography, one line, `cursor: pointer`, `touch-action: manipulation`,

## Copywriting Contract

Rules for every string: plain text; no HTML; no format verbs; no emoji on the page; present tense for what is
happening, past tense for what the server already did; say what happened and what the user can do; never show raw error
text, tokens, ids or status codes. Limits are character counts. "EN" is the English source; "Other" applies to
es, fr, hi, id, pt, ru (30 to 40 percent longer; allow it and wrap rather than truncate). The headline is one line at
320 px in English (20 px semibold fits about 26 characters in 288 px); in other languages a headline may wrap to two
lines. Button labels must stay on one line in every language.

### Page strings (26 keys, all 7 locale files, prefix `captcha_web_`)

| Key | English | Max EN | Max other |
|-----|---------|--------|-----------|
| `captcha_web_page_title` | Verification | 24 | 32 |
| `captcha_web_loading_title` | Getting ready | 24 | 34 |
| `captcha_web_loading_body` | Setting up the check. This takes a moment. | 100 | 140 |
| `captcha_web_ready_title` | Verify you are human | 24 | 34 |
| `captcha_web_ready_body` | Complete the check below to join the group. | 100 | 140 |
| `captcha_web_widget_label` | Security check | 24 | 32 |

## Telegram-side Pieces

### Challenge message in the group (CAPT-02, D-06)

Sent after the member is muted and the attempt row exists. One inline keyboard row, one `url` button (the Mini App
direct link `https://t.me/<bot>/<app>?startapp=<token>`; it is a plain URL button, not callback data, so the 64-byte
`callbackcodec` cap does not apply to it).

| Key | English | Limits |
|-----|---------|--------|
| `captcha_web_welcome` | `👋 Welcome %s!` + blank line + `Tap the button below to verify you are human.` + blank line + `⏱ You have <b>%d minutes</b> to finish.` | `%s` is the member mention, `%d` the group's time limit in minutes (1 to 10); the leading 👋 and ⏱ follow the existing `captcha_welcome_*` keys; whole message under 250 characters in every language |
| `captcha_web_button` | Verify with Turnstile | 24 EN, 30 other, one line |

The message is deleted on a pass and handled on failure or timeout exactly like the existing captcha messages (D-06,
D-07). The failure notice in the group reuses the existing `captcha_timeout_failure_kicked`, `_banned` and `_muted`
keys; no new key is needed for it.

### `/captchamode turnstile` (CAPT-01, D-05, D-09)

The command accepts `turnstile` and replies with the existing `captcha_mode_set_formatted` using the new description
key. It refuses, with the reason and without changing the stored mode, in this order:

| Key | English | Limit |
|-----|---------|-------|
| `captcha_mode_turnstile_desc` | `Cloudflare Turnstile web check` | 40 EN, 52 other (it fills the `(%s)` of `captcha_mode_set_formatted`) |
| `captcha_web_refuse_not_configured` | `Turnstile captcha is not set up on this bot yet. Ask the bot owner to finish the web captcha setup. Math and text captcha still work.` | 160 EN, 224 other |
| `captcha_web_refuse_no_redis` | `Turnstile captcha is unavailable right now because the bot's shared storage is down. Try again later, or use math or text captcha.` | 160 EN, 224 other |
| `captcha_web_refuse_no_rights` | `I need to be an admin with the Restrict members right to run the Turnstile captcha. Give me that right and try again.` | 160 EN, 224 other |

The rights text must name the same rights the math and text captcha already require (the executor confirms against
`SendCaptcha` and the unmute path; adjust the key text if it also needs Delete messages). All three are replies in the
admin's language (HTML parse mode as the other `captcha_*` replies). They contain no secret names, no env var names, no
URLs.

Existing keys that must change in all 7 locale files so the mode list stays true:

| Key | Change |
|-----|--------|
| `captcha_mode_specify` | list `math`, `text` and `turnstile` |
| `captcha_mode_invalid` | list `math`, `text` and `turnstile` |
| `captcha_help_msg` | add "Turnstile: a Cloudflare check on a web page" under Captcha Types; `/captchamode <math/text/turnstile>` |
| `captcha_invalid_mode_error` | `'math', 'text' or 'turnstile'` (log-style text, still a locale key) |

At join in a Turnstile group whose web captcha is unavailable (D-09) the member gets the math captcha with the
existing math keys. No extra message and no new key.
