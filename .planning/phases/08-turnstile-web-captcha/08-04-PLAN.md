<objective>
Make the third mode real in production storage: an append-only migration widens `chk_captcha_mode` so PostgreSQL accepts `turnstile` (D-05), the repository's `SetCaptchaMode` accepts it, and a PostgreSQL-only test in CI proves the constraint that SQLite cannot.

Research correction found while planning: the first captcha migration (`20250807103246_add_captcha_tables.sql`, line 6) declares `captcha_mode ... CHECK (captcha_mode IN ('math', 'text'))` inline, which PostgreSQL names `captcha_settings_captcha_mode_check`. Migration `20260412000000` added `chk_captcha_mode` beside it and never dropped it, so every database built by the chain has two checks. Dropping only `chk_captcha_mode` (the research's draft) would leave the inline check rejecting `turnstile`. The migration therefore also drops every other CHECK on the table whose definition mentions `captcha_mode`, by a `DO` block over `pg_constraint`, which both appliers pass through untouched.

NEVER start PostgreSQL by any means (no su, sudo, setpriv, initdb, pg_ctl, docker). The PostgreSQL proof is a test that skips without `ALITA_TEST_DATABASE=true` and `DATABASE_URL` (a skip the `make test` gate allows only in `./alita/db/migrations`, exactly like `TestRaidDetectionCarryOver`) and runs in CI through `make test-postgres-integrity`.

Purpose: CAPT-01 (the mode can be stored), D-05, D-29 (DROP first, re-add NOT VALID).
Output: the migration, `TestCaptchaModeMigrationStatements`, `TestCaptchaModeTurnstileConstraint`, the Makefile entry, `SetCaptchaMode` accepting turnstile with its tests, AGENTS.md facts.
