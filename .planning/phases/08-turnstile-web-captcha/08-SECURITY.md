# Phase 8 - Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Mini App page to the verify handler | Everything in the POST body is attacker-controlled until Telegram's `initData` HMAC and Cloudflare's `siteverify` answer are checked; the page decides nothing |
| Group members to the challenge link | The `startapp` token is in the button URL, so every member can read it; the barrier is the signed `initData` `user.id`, never the token's secrecy |
| Telegram callback data to `captcha_verify` / `captcha_refresh` | A modified client or userbot can send any callback bytes |
| Bot to Cloudflare `siteverify` | The Turnstile secret leaves the server only in this request body; the answer (and its body) is untrusted text |
| Environment to config, config to logs | The owner's four settings decide whether the web captcha exists; the secret must never come back out in a log or an error |
| Migration file to the two appliers | The Go runner and `scripts/migrate_psql.sh` rewrite statements before PostgreSQL sees them |
| Group admin to `/captchamode` | The stored mode drives what every future join of the group does |
| Bot HTTP server to the member's WebView | The page and its CSP are what the member's client runs; seven translated tables and the site key are placed into the document |
| Third-party scripts | `telegram-web-app.js` and Turnstile's `api.js` run with the page's privileges |
| Replica to replica | Several bot processes share PostgreSQL and Redis and may act on one attempt at once |
| Internet to the verify route, reverse proxy to the bot | Behind the owner's proxy the route is public; forwarding headers are believable only from the owner's own proxies |
| Public reverse proxy to the bot's single HTTP port | `/captcha` shares the port with `/metrics`, `/db_metrics`, `/health`, pprof and the webhook |
| Locale files to the page | Translated strings become text on a page served to every joining member |
| Documentation to the owner's deployment | The owner configures the public proxy, BotFather, Cloudflare and the keys from the guide |

## Unregistered Flags

- **U-1, WARNING (unregistered), the key mismatch breaker is attacker-influenceable shared state (review fix WR-04, severity low).** `alita:captcha:streak` (`breaker.go:11-47`) is one fleet-wide counter of failed solves (`OutcomeFailed` of any reason) with no confirmed pass in between; from the 6th on, `suspectKeyMismatch` turns a provable failure into a `retry` (`verify.go:661-676`). It was added after the first review to stop a bad site key and secret pair from kicking every joiner (T-08-23), and no plan row maps it. Any member can feed it: a garbage token is `invalid-input-response`, a token minted for another challenge is a `cdata` failure, and a kicked account can rejoin, so one account can trip it with six join-and-fail cycles; a streak that goes on renews its 10 minute expiry, and a confirmed pass (`ClearFailedSolves`) ends it. While it is tripped, failing members are held as retry (still muted, attempt and challenge intact, nobody removed) instead of removed at once, and the attempt's own timeout still applies the group's `/captchaaction`. Bounds that remain: a pass still needs signed `initData` and a Cloudflare-confirmed token for the right hostname, action and cData, so nobody passes without solving; per-user (20/min) and per-token-and-user (8/min) windows apply; Redis errors fail open (the failure is enforced). The cost is that "one solve only" (CAPT-06) is relaxed fleet-wide while the breaker is tripped, and the Error line `suspected key mismatch` can be provoked once a minute. It is documented in `AGENTS.md` and in the guide's troubleshooting (`captcha-web.md:194`) and covered by `TestVerifyRouteKeyMismatchBreaker` and `TestCaptchaWebKeyMismatchCannotMassKick`. Optional hardening: count only the codes a hostile client cannot produce on demand, or trip per chat rather than fleet-wide.

## Audit Notes

Not register threats. None blocks the phase, and no production code was changed by this audit.

- **O-1, T-08-06 has no client-disconnect test.** The mitigation is in the code (`context.WithoutCancel` on the claim, the re-arm, the marker, the streak and the pass work, plus the durable unmute row), and the durable-row half is tested, but no test cancels the request context in the middle of a verify and checks the pass completes. Optional hardening: such a test with a `slowPassBackend`-style backend and a cancelled `httptest` request.
- **O-2, T-08-19 and the CSP text.** `TestPageHeadersAndNonce` compares the `Content-Security-Policy` header with `CSPFor(nonce)`, so it fails if the header disappears but not if a directive in `CSPFor` is weakened (for example `unsafe-inline` added or `frame-ancestors` widened). The audit read `page.go:127-137`: `default-src 'none'`, `script-src` the nonce plus two hosts, `style-src` the nonce, `frame-src` Cloudflare, `connect-src 'self'`, `base-uri 'none'`, `form-action 'none'`, `frame-ancestors` three Telegram web origins. Optional hardening: pin those directives in a test. The CSP against a real managed widget is spike check 6, not run.
- **O-3, tests the audit could not run.** The PostgreSQL half of the migration, `TestCaptchaModeTurnstileConstraint` (exactly one CHECK left on `captcha_settings`, turnstile accepted, the statements rerunnable), SKIPS without `DATABASE_URL`/`ALITA_TEST_DATABASE` and is in `make test-postgres-integrity` for CI (the Makefile list was updated). T-08-15 rests here on the migration text, the unchanged appliers and the database-free `TestCaptchaModeMigrationStatements`, which pins the statement order. PostgreSQL was never started.
- **O-4, not run here.** `make test` (whole suite), `make lint` (the installed `golangci-lint` is built for an older Go), `make check-translations` (its script runs `go mod tidy`; `TestCaptchaWebLocaleKeys` and `TestStringTable` ran instead) and the live items of `08-SPIKE.md` (real Android, iOS and Desktop clients, the Turnstile widget inside Telegram's WebViews, `siteverify` for the owner's hostname, signed data older than 5 minutes). Those are the owner's deferred spike (D-18) and are not security evidence.
- **O-5, "a test that would fail without it" was judged by reading assertions.** The audit did not mutate code. The forged-callback, wrong-user, consume-once, never-logs, redirect and limits tests assert the protected state directly (attempt row unchanged, key owner unchanged, zero Cloudflare or backend calls, forbidden strings absent from every log entry). `08-REVIEW-FIX.md` records that the WR-01 tests fail against the old code.
- **O-6, small log notes.** The two `Debugf` lines of `verify.go` (`:247`, `:280`) print the error of a failed response write; a network write error can carry the peer's address, never a token, `initData`, name or Cloudflare text. Client addresses are held in Redis keys `alita:captcha:rl:ip:<ip>` (IPv6 by /64) for 60 s, documented in `AGENTS.md`; nothing about the member, including the address, is sent to Cloudflare (`siteverify.go:128-131` posts `secret` and `response` only).
- **O-7, UX that is not a security gap.** An old token after a re-join is answered `expired` with the group's action text although the new attempt is untouched (T-08-04 holds); initData older than 5 minutes is answered `invalid` with copy that says "belongs to another member or was already used" while the challenge is not consumed and reopening the button recovers (IN-06, open in `08-REVIEW-FIX.md`, spike check 14).
- **O-8, unsigned-by-Telegram input that is used.** The signed `first_name` is spliced into public messages through `formatting.MentionHtml` (existing escaping), and a missing signed `start_param` lets the posted `challenge` stand alone; both are covered by the user-bound consume (T-08-01), so a forged challenge value can only be one the signed user owns.
- **O-9, scope held.** No endpoint, auth path, file access or schema was added beyond the three captcha routes, the `captcha_mode` CHECK and the Redis key families of `AGENTS.md` (`alita:captcha:ch:*`, `alita:captcha:done:*`, `alita:captcha:rl:*`, `alita:captcha:streak`). `alita/db/migrations/runner.go` and `scripts/migrate_psql.sh` have no diff since `c3cd9515`; `alita/utils/captchaweb` is a leaf package (standard library, go-redis, logrus), and its test fixtures carry the `testtools` build tag.
