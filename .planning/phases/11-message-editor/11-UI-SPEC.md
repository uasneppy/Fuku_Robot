# Phase 11 - UI Design Contract

> Visual and interaction contract for the message editor: the Welcome, Goodbye and Rules settings pages, the
> waiting prompt that follows Set, every refusal, Preview and Full preview, the Welcome and Goodbye switches, how the
> pages join the Main grid, every callback with its worst-case size, and every new string with its locale key.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Upstream: 11-CONTEXT.md D-01..D-11 (locked, not reopened), REQUIREMENTS EDIT-01..EDIT-06, EDIT-10, EDIT-11, ROADMAP
> Phase 11 success criteria, research PITFALLS 10 to 12, the approved Phase 10 contract (`10-UI-SPEC.md`), AGENTS.md
> (Handlers, Callbacks, Permissions, Data, settings rules), and the code of `greetings.go`, `rules.go`,
> `fuku/utils/content/content.go`, `fuku/utils/formatting/formatting.go`, `fuku/utils/media/sender.go`,
> `fuku/db/greetings`, `fuku/db/rules`, `settings_pages.go`, `settings_antiflood.go`, `settings.go`.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard that the bot
edits in place, plus messages the owner types in the bot's private chat. Template sections that assume CSS, fonts,
pixels or colour are replaced by their Telegram equivalent, exactly as Phases 9 and 10 did. This contract EXTENDS the
Phase 9 and Phase 10 contracts: anything not restated here (message anatomy, the group line, status icons, toggles that
show the current state, notices versus alerts, the one-answer-per-press rule, the press pipeline `settingsPress.verify`
with the owner gate at step 4b, the "never name the Staff Group" rule) is unchanged and applies to every new screen.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Telegram Bot API, gotgbot v2) |
| Preset | not applicable |
| Component library | none: `gotgbot.InlineKeyboardMarkup` rows of `InlineKeyboardButton`, built with `settingsKeyboard` |
| Icon library | Unicode emoji only, not localized (same practice as Phases 9 and 10); every word around them is a locale key |
| Font | none: Telegram client fonts. Styling is limited to the HTML tags in "Text Styling" |

Project scan: no `components.json`, `tailwind.config.*`, `package.json`, `.tsx` or `.css` in the repo. Component
Inventory is omitted (`Tool: none`). Existing Telegram UI matched in style and wording: the Antiflood page
(`renderSettingsAntiflood`), the Access page, the shared `settingsCompose` anatomy, the content refusals of
`fuku/utils/content/content.go` (`content_text_too_long`, `content_caption_too_long`) and the greetings command replies.

Telegram limits this contract is built inside:

| Limit | Value | Where it bites |
|-------|-------|----------------|
| Message text | 4096 characters after parsing; the bot caps its own settings HTML at 3800 UTF-16 units | the pages are far below it (a Welcome page is under 900 units); a test renders the worst case in all 8 locales |
| Caption | 1024 characters | text set together with media; the editor refuses over it (EDIT-03) |
| Callback data | 64 bytes, through `fuku/utils/callbackcodec` only | table "Callback data"; the worst case of this phase is 45 bytes |
| Buttons | at most 8 per row, 100 per message | URL buttons the owner writes (EDIT-05) are refused over either limit; a page has at most 8 rows |
| `answerCallbackQuery` alert text | 200 characters, plain text (no HTML) | every new alert key is held to 120 EN / 160 other |
| Button label | about 20 visible characters in a half-width (two-column) cell, about 40 on a full-width row | rules in "Copywriting Contract" |
| Bot API file ids | a `file_id` can be reused by the same bot | media is stored as `file_id` plus a type, as `/setwelcome` stores it; no file is downloaded |

## Message Layout (replaces Spacing Scale)

The Phase 9 anatomy stands: header line (`settings_header` plus the page name), group line (bold escaped title, `<code>`
chat ID), one blank line, body lines, and, when there is a notice, one blank line then the notice (`settingsCompose`).
The keyboard ends with the navigation row, Back left and Close right. This phase adds two screens that are not pages.

### The three editor pages share one body

```
⚙️ Settings · Welcome                 <- settings_header + settings_page_welcome
Fuku Test Group  -1001234567890       <- group line (title escaped, 64 runes at most)
<blank line>
Text: Set · length 120                <- one line per part, in this order: text, media, buttons
Media: Photo
Buttons: Set · total 2
<blank line>
<hint paragraph>                      <- settings_edit_hint_greeting (Rules: settings_edit_hint_rules)
<blank line>
<clean hint paragraph>                <- Welcome and Goodbye only
<blank line, only with a notice>
<notice line>                         <- ⚠️ or ✅ line, as in Phase 9
<keyboard: part rows, preview rows, switch rows, optional Open in private row, navigation row>
```

The Rules page has only the Text line in this phase. Phase 12 adds Media and Buttons lines and rows to the same
renderer by registering more parts; nothing in this contract is reworked by that (see "Parts table").

### The waiting prompt is a screen, not a page

```
⚙️ Settings · Welcome
Fuku Test Group  -1001234567890
<blank line>
<prompt body for the part>            <- settings_edit_wait_*
<blank line>
<wait footer: until what time, Cancel, /cancel>
<blank line, only when a wait was replaced>
<replaced note>
<keyboard: [ ❌ Cancel ]>
```

The prompt has **no Back and no Close**: Back would leave a wait open behind a page the owner thinks is idle. Cancel is
the only way out of the screen (besides sending the message, `/cancel` and the 10-minute expiry).

### Refusal and confirmation messages in private

| Message | Anatomy | Keyboard |
|---------|---------|----------|
| Refusal of a typed reply | a reply to the owner's message (`AllowSendingWithoutReply`): the reason, one blank line, `settings_edit_still_waiting` | `[ ❌ Cancel ]` (so the owner does not scroll back to the prompt) |
| Saved | a NEW message at the bottom of the chat: the page redrawn with a ✅ notice (and the album or caption line when they apply). It is the confirmation and it names the target through the page's own header and group line (Pitfall 10) | the page's keyboard |
| Ended wait (owner lost access, gate refused) | one plain reply, no keyboard, no page | none |
| Cancel from `/cancel` | one plain reply `settings_edit_cancelled` | none |

After a save the old prompt message is edited to `settings_edit_prompt_closed` with no keyboard (best effort; a failed
edit is logged once and changes nothing).

## Text Styling (replaces Typography)

Phase 9 styling stands: `<b>` on "Settings" in the header and on the group title, `<code>` on chat IDs, `<b>` on a
control's current value, no other tags, user text escaped and spliced in after translation, button labels plain text.
Additions:

| Role | Telegram markup | Used for |
|------|-----------------|----------|
| Text to copy and paste | `<code>` | the placeholders, the button syntax examples, `:same`, and `/rules` in the Rules hint, so a tap copies them. They are never translated and never wrapped in `<b>` |
| Command to send | plain text | `/cancel` in the wait footer: in a private chat a tap sends it, which is what the owner wants |
| Owner's stored text | never shown on a page | a page shows state words and a length only. The text itself is shown by Preview, as the message members will see. A page is readable by every member of a group when opened in the group, and the stored HTML must not be echoed into another message's markup |

The prompt bodies contain literal placeholders (`{first}`, `{rules}`). The translator leaves unknown `{name}` tokens
alone when it interpolates (`interpolateParams` returns the match unchanged), so only the real parameters
(`{max}`, `{time}`, `{n}`, `{state}`) are replaced. A test asserts every placeholder token appears untranslated and
unaltered in all 8 locales (see "Rendered-size and content checks").

## Interaction Contract

### Where Set and Remove work (D-01)

| Control | Private menu | Menu opened in the group |
|---------|--------------|--------------------------|
| Set text, Set media, Set buttons | writes the wait and turns the message into the waiting prompt | writes nothing and awaits nothing: the page is redrawn with the notice `settings_edit_group_note` and the always-present Open in private row |
| Remove text, Remove media, Remove buttons | removes the part at once (D-09), redraws with a notice | same refusal as Set: the notice `settings_edit_group_note`, nothing removed |
| Preview text, Preview media, Preview buttons, Full preview | sends into the same private chat | sends into the presser's own private chat, never into the group (D-10); the press is answered with the toast `settings_edit_preview_sent` |
| Welcome, Goodbye and Delete-last switches | work, redraw from the apply function's value | work, redraw from the apply function's value |
| Open in private | not drawn (already private) | a URL button row above the navigation row, `settings_btn_open_private`, the existing `/start settings_<chat id>` deep link (`settingsPrivateURL`). It lands on the group's Main page and the owner opens the page again; the deep link is not edited. Left out, and logged, when the bot has no username (as `settingsChoiceScreen` does) |

In a group menu the Set and Remove buttons stay drawn so the page looks the same in both places; their press is the
refusal above. No typed reply is ever awaited inside a group.

### Rights (press pipeline step 5)

Each control declares one right, and the menu refuses what the matching command refuses. `/setwelcome`,
`/resetwelcome`, `/setgoodbye`, `/resetgoodbye`, `/cleanwelcome` and `/cleangoodbye` need the user right "change group
info" (`chat_status.CanUserChangeInfo`); `/welcome on|off` and `/goodbye on|off` need only an admin; `/setrules` and
`/clearrules` need an admin and the bot to be an admin (`IsUserConnected(..., true, true)`).

| Page, control or action | Right | Refusal |
|-------------------------|-------|---------|
| Welcome and Goodbye: `ws` `wr` / `gs` `gr` (Set, Remove) | new `settingsRightChangeInfo`: live creator, or administrator whose same member record has `can_change_info` (no extra Telegram call) | alert `settings_no_change_info`, nothing edited, nothing written |
| Welcome and Goodbye: switch `tg` control `e` | `settingsRightAdmin` (the live admin check every press makes) | none beyond the pipeline's |
| Welcome and Goodbye: Delete last `tg` control `d` | `settingsRightChangeInfo` | alert `settings_no_change_info` |
| Rules: `rs` `rr` (Set, Remove) | `settingsRightAdminBotAdmin` (the command's own predicate `chat_status.IsBotAdmin`) | notice `chat_status_bot_not_admin`: the page is redrawn with the warning line |
| Every Preview, Full preview and Cancel | `settingsRightAdmin` | none beyond the pipeline's |

Authority-parity tests (`TestSettingsAuthorityParity*`) cover the five rows. A control the presser lacks the right for is
still drawn and its press refused (Phase 9 rule).

### The wait (D-03, D-04, D-05)

One wait per person, whichever group or page. It lives in Redis under `fuku:settings:input:<user>` for 10 minutes, so
whichever replica receives the reply sees it. Its value names the group, the page, the part, the prompt message and a
claim nonce; it never holds the message text.

| Event | Result |
|-------|--------|
| Set pressed, private menu, Redis writes | all pipeline checks pass, the wait is written (replacing any earlier one, TTL 10 minutes from now), the message is edited into the prompt. If an earlier wait for a different group, page or part was replaced, the prompt adds `settings_edit_replaced_note` |
| Set pressed again on the same part | the wait is refreshed to a new 10 minutes and the prompt is redrawn with the new time; no replaced note |
| Set pressed with no Redis, or the write fails | alert `settings_edit_unavailable`; the page stays as it was; Remove, Preview and the switches still work |
| Owner sends a valid message | the typed-reply door below accepts it, the wait is claimed once, the part is written, the page is sent as a new message with the ✅ notice, the old prompt becomes `settings_edit_prompt_closed` |
| Owner sends something the editor refuses | the reason as a reply with `[ ❌ Cancel ]`; **the wait stays open** and its 10 minutes are not extended |
| Cancel pressed on the live prompt or refusal message | the wait is deleted and that message is edited into the page with the notice `settings_edit_cancelled`; nothing is stored |
| `/cancel` typed in private | the wait is deleted, one reply `settings_edit_cancelled`; with no wait, one reply `settings_edit_cancel_nothing`. `/cancel` in a group is ignored |
| Cancel pressed on a prompt whose wait was replaced or already used | alert `settings_edit_prompt_stale`, that message is edited into the page (no notice), **the live wait is left untouched** (a Cancel compares group, page and part with the wait before deleting anything) |
| Cancel or any press on a prompt after the 10 minutes | alert `settings_edit_wait_expired`, the message is edited into the page. Expiry is lazy: no timer, no new drain (the wait key's own TTL ends it) |
| Owner sends a message after the 10 minutes | no wait exists, so the update passes through untouched and nothing is said (accepted, see Assumptions A3). The prompt stated the end time to make this unsurprising |
| Owner sends a command other than `/cancel` while waiting | the command runs as usual; it is never taken as content and the wait stays open |
| Owner presses `/settings`, `/start` deep link, Back on another message | all work; the wait stays until its TTL |

Wait claim order (so a double delivery, or the second item of an album, acts once): the typed-reply door reads the wait
without deleting it, runs every check and the dry run, and only when everything passed claims it with one atomic
compare-and-delete on the nonce, immediately before the write. A refusal therefore never consumes the wait. A claim that
loses (another delivery won) says nothing. If the write fails after the claim, the wait is put back with its remaining
time and the owner is told `common_settings_save_failed` plus `settings_edit_still_waiting`.

### The typed-reply door (D-05)

A message is a candidate only when it is a new (not edited) message in a private chat from a user who is not the bot and
not a Telegram service identity (`staffServiceUserIDs`: they never start or answer a wait) and is not a command. Anything
else returns `ext.ContinueGroups` with no reply, no write and no Telegram call, so no other handler is affected; with no
wait for the sender it does the same. Every check then refuses before the next runs:

| Step | Check | A failure answers | The wait |
|------|-------|-------------------|----------|
| 1 | read the wait (Redis error: treated as no wait, nothing said) | nothing | unchanged |
| 2 | live `getChatMember` of the sender in the wait's group (never the admin cache); a status other than creator or administrator, or a Telegram client error (`isTelegramClientError`, any 4xx other than 429, by class) | `settings_edit_refuse_access_lost` (one text for both, it names no group) | ended |
| 2 | the same lookup fails without a client error (429, 5xx, transport, timeout) | `settings_check_failed` | stays |
| 3 | the owner gate `settingsGate` on that member record (the same function as every door) refuses an administrator | `settings_gate_owner_only` (reached only after step 2 proved an admin, rule R1) | ended |
| 3 | the gate cannot decide | `settings_check_failed` | stays |
| 4 | the right of the part (the rights table): a lost `can_change_info`, or (Rules) a bot that is no longer an admin | `settings_no_change_info`, or `chat_status_bot_not_admin` | ended |
| 5 | the input type and the dry run (below) | the refusal reason plus `settings_edit_still_waiting` | stays |
| 6 | atomic claim, then the write through the part's apply function | success page, or `common_settings_save_failed` | ended on success, put back on a failed write |

Replies are in the sender's own language (the private chat's). The messages of a refusal never carry the group's title,
a chat ID or the words "Staff Group".

### What each part accepts, and every refusal (D-06, D-07, D-08; EDIT-03, EDIT-04, EDIT-05, EDIT-11)

Only `settings_edit_still_waiting` and a Cancel button are added to every refusal; the table gives the reason line.

| Part | Accepts | Refusal and key | Notes |
|------|---------|-----------------|-------|
| Text (Welcome, Goodbye) | a text message; entities are kept and converted to the stored form exactly as `/setwelcome` and `/setgoodbye` convert them (the same code, settled by the spike) | not text: `settings_edit_refuse_need_text`. The text contains `buttonurl://` button lines: `settings_edit_refuse_text_buttons` (nothing is silently moved to the buttons part). Stored form over the limit, counted the way the commands count it (code points of the stored HTML): `content_text_too_long` (limit 4096) or, when the group already has media, `content_caption_too_long` (limit 1024). With the placeholders filled in (the dry run, below): `settings_edit_refuse_too_long_filled` | the existing `content_*` keys are reused, so the wording equals the commands' |
| Text (Rules) | a text message; stored as `/setrules` stores it (`MD2HTMLV2` of the original markdown) | not text: `settings_edit_refuse_need_text`. Over the limit once the `/rules` heading is added: `settings_edit_refuse_too_long_filled` | placeholders do not work in rules (`/rules` does not fill them), and the prompt says so |
| Media (Welcome, Goodbye) | one photo, video, GIF, file (document), sticker, audio or voice message. A GIF is stored as a document, as the commands store it | any other kind (video note, contact, location, venue, poll, dice, game, story, plain text) or a message with no media: `settings_edit_refuse_need_media`. Existing text over 1024 characters: `settings_edit_refuse_media_text_long` (set the media after shortening the text, because the text becomes its caption) | the caption of the media message is not used; when one was present the saved page adds `settings_edit_caption_ignored` |
| Media, an album | the album's items arrive as separate messages with one `media_group_id`: one item is kept, the saved page adds `settings_edit_album_cut`, and the other items of that album are ignored with no reply for 30 seconds (a remembered group id). An album sent where it is refused gets one refusal, not one per item | | which item is kept is whichever arrives first (Assumptions A8) |
| Buttons (Welcome, Goodbye) | text lines in the bot's existing syntax, quoted from `RevertButtons` and `tgmd2html`: `[Name](buttonurl://https://example.com)`, and `:same` after the link to put the button in the row of the one before: `[Name](buttonurl://https://example.com:same)`. Text that is not a button line is ignored. Valid buttons **replace** the current set | not text: `settings_edit_refuse_need_text`. No readable button, or a `buttonurl://` that did not parse: `settings_edit_refuse_buttons_syntax`. A link that is not `http` or `https` with a host: `settings_edit_refuse_button_url` naming the button's number only (no user text is echoed). More than 100 buttons, or more than 8 in one row: `settings_edit_refuse_buttons_limit` | the commands drop a bad link silently (`buttonUrlFixer`); the editor refuses instead (EDIT-05). A button with an empty name keeps the commands' default label, `Greeting` |

Other rules for every part:

- **One part is written per reply, column-targeted.** Text keeps the stored media and buttons, media keeps text and
  buttons, buttons keep text and media. The stored row afterwards equals what one `/setwelcome` carrying the same
  content would store (EDIT-11, checked by a parity test per part).
- **The dry run (D-07)** builds the message the way a real join, leave or `/rules` builds it and refuses it with the
  reason, **before** saving: placeholders are filled with the owner's own name and again with a worst-case name (64
  characters for first and last name, the longest `{fullname}`, `{mention}` and `{username}`, a nine-digit `{count}`),
  the group's real title fills `{chatname}`, and the visible length (after tags are dropped and entities decoded, in
  UTF-16 units) is held to 4096, or 1024 when the group has media. A text that passes with a short name but not with a
  worst-case name is refused with `settings_edit_refuse_too_long_filled` and the number is the worst case. The dry run
  is local: it sends nothing. Telegram can still refuse at Full preview (media whose `file_id` is stale, a link
  Telegram dislikes); that is reported by `settings_edit_preview_failed` and the cause goes to the log only.
- Media and text of a sticker: Telegram sends a sticker without text, so a Welcome with a sticker never shows its text.
  Setting a sticker, or text over a sticker, is allowed; the page shows `settings_edit_note_no_caption` while it applies.
- A wrong-type message is refused with the reason and the wait stays open once per update; it is not "re-prompted" with
  the long prompt body again (Pitfall 10).

### Remove (D-09)

| Remove on | Result | Notice |
|-----------|--------|--------|
| Welcome or Goodbye text | back to the default text, the same default `/resetwelcome` and `/resetgoodbye` store. Those commands reset text, media and buttons together; the page's Remove text resets the text only, and Remove media and Remove buttons reset their own parts, so the three Remove buttons together equal the command | `settings_edit_removed_text_default` |
| Welcome or Goodbye media | the stored media is cleared and the type goes back to text | `settings_edit_removed_media` |
| Welcome or Goodbye buttons | the buttons are cleared | `settings_edit_removed_buttons` |
| Rules text | cleared, as `/clearrules` | `settings_edit_removed_text_rules` |

One tap, no confirmation card (the owner's choice: same as the commands). The Remove button of a part is drawn only
while the part is set (Welcome and Goodbye text: only while it differs from the default). A stale Remove press for a
part that is already empty redraws the page with the warning notice `settings_edit_nothing_to_remove` and writes
nothing. A write failure redraws the page unchanged with `⚠️ common_settings_save_failed`.

Remove media on a row whose text is the only content leaves the text; Remove text on a row with media leaves the media
with the default text as its caption (the default text is at most 1024 characters, so this is always sendable).

### Preview and Full preview (D-10, EDIT-06)

Every preview is sent to the pressing person's **private chat** with the bot, filled in with that person's own name and
the group's title, through the same send function the group uses (`media.SendGreeting` after `FormattingReplacer`; for
Rules, the `/rules` text built by the same code as `sendRules`). A preview never writes: it does not change
`LastMsgId`, does not delete the previous welcome, does not set the last-message bookkeeping of "Delete last welcome", and
never posts into the group or any other chat.

| Button | What is sent (in this order) |
|--------|------------------------------|
| Preview text | the header `settings_edit_preview_header` (Rules: `settings_edit_preview_header_rules`), then the stored text alone as a plain message with the placeholders filled in |
| Preview media | the header, then the media alone with no caption and no buttons |
| Preview buttons | the header, then a message `settings_edit_preview_buttons_body` carrying the buttons as a keyboard (a tap opens the link) |
| Full preview | the header, then the exact message (media with caption, or text, plus buttons) as a member would see it |

Rules page: Preview text sends the stored text alone; Full preview sends the `/rules` message, the heading
(`rules_for_chat_header` with the group's title) and the text, even when private rules is on (the click-to-read message
is not what is previewed). With no rules set, Full preview sends `rules_no_rules_set`, exactly what `/rules` says.

Preview buttons are drawn only for parts that are set (the text preview is always drawn on Welcome and Goodbye, because
the default text is a message too; on Rules only while rules are set). Full preview is always drawn.

| Preview outcome | Answer |
|-----------------|--------|
| sent in a private menu | the press is answered empty (the preview is the answer) |
| sent from a group menu | toast `settings_edit_preview_sent`, no edit |
| a part that is not set (a stale press) | alert `settings_edit_nothing_to_preview`, no edit |
| the group menu's presser never started the bot (Telegram 403 on the send) | alert `settings_edit_preview_need_start` |
| Telegram refuses the send for any other reason, or it fails | alert `settings_edit_preview_failed`; Telegram's own wording goes to the log only; nothing is stored or changed |

### Switches on Welcome and Goodbye (D-11, EDIT-10)

| Control | Label (shows the current state) | Press | Apply function and command |
|---------|---------------------------------|-------|----------------------------|
| Welcome on/off | `Welcome: ✅ On` / `Welcome: ❌ Off` | `tg`, page `w`, control `e`, `v=0` or `1` | `applyWelcomeEnabled` beside `displayGreeting` (`/welcome on|off`): the same `greetings.SetWelcomeToggle`, the same cache key `greetings:<chat>` invalidated |
| Goodbye on/off | `Goodbye: ✅ On` / `Goodbye: ❌ Off` | `tg`, page `g`, control `e` | `applyGoodbyeEnabled` beside `/goodbye on|off`, `greetings.SetGoodbyeToggle` |
| Delete last welcome | `Delete last welcome: ✅ On` | `tg`, page `w`, control `d` | `applyCleanWelcome` beside `cleanWelcomeToggleConfig` (`/cleanwelcome`), `greetings.SetCleanWelcomeSetting` |
| Delete last goodbye | `Delete last goodbye: ✅ On` | `tg`, page `g`, control `d` | `applyCleanGoodbye` (`/cleangoodbye`), `greetings.SetCleanGoodbyeSetting` |

One setting, one code path: each apply function holds the validation, the refusals, the repository write and its
`cache.DeleteCache`, and returns a typed result (outcome, the stored value read back, the repository error); the command
maps it to its unchanged reply and the menu to a redraw. The press sends the absolute target (`v`), so a double tap is
harmless. A successful flip adds no notice (like the Access and Antiflood switches); a failure redraws with
`⚠️ common_settings_save_failed` and the old state. Defaults when there is no row: Welcome On, Goodbye Off, Delete last
Off (what `checkGreetingSettings` returns). The pages read through an error-returning read (see Notes for the planner):
`GetGreetingSettings` and `GetChatRulesInfo` hide read errors, and a getter that hides read errors is never used by a
page, so a read error is the cannot-open edit (`settings_cannot_open`, with the alert `settings_cannot_open_alert`).

### Parts table (so Phase 12 adds parts without reworking the pages)

The pages are drawn from one table of parts; a part declares its code, its label keys, its state line, its accepted input
and its apply function. Phase 11 registers:

| Page | Parts |
|------|-------|
| Welcome (`w`), Goodbye (`g`) | text `x`, media `m`, buttons `b` |
| Rules (`r`) | text `x` only |

A callback naming a part the page does not have (for example `t=m` on Rules) is an invalid request
(`common_callback_invalid_request`), checked before any I/O. Phase 12 adds `m` and `b` to Rules, and the Media-under-text
and Greet-once controls to Welcome, by adding rows to the table, not by editing the renderer.

### Joining the Main grid (D-02)

The pages register from their own files through `registerSettingsPage` (keys `w`, `g`, `r`), so `settings_pages.go` is

## Callback data (64-byte cap)

Built only with `encodeCallbackData` / `callbackcodec.Encode`, read only with `decodeCallbackData`. All buttons are in
the `settings|v1|` namespace (12 bytes). Worst case: `c` = `-1001234567890` (14 characters with the sign), `u` =
`1234567890` (10 digits). Exactly one of `c` and `u` is present, as the namespace requires. A test renders every screen
with these IDs and fails on any omitted button (`settingsScreen.Omitted` must stay 0).

New page keys (existing: `s l c f a`): Welcome `w`, Goodbye `g`, Rules `r`. Parts `t`: `x` text, `m` media, `b` buttons.
Toggle controls `t`: `e` enabled, `d` delete last. New action codes, declared by each page through
`registerSettingsPage` (which panics at init on a duplicate code, so each page has its own; none clashes with `oh op bk
cl tg st no pk ls ly ua uy lk pg ay`):

## Copywriting Contract

Rules: plain, short, one fact per line; say what happened and what to do next; reuse a command's or an earlier phase's
words wherever they already say it; user text escaped and spliced after translation; parameters in brace style. Limits
are Unicode code points of the template, placeholders counted as written, tags and emoji counted. "EN" is the English
source; "Other" is each of es, fr, hi, id, pt, ru, uk. Shorten a translation, never truncate in code. Every key below
exists in **all 8 locale files** with no empty value, is written literally (no key built by concatenation), and every new
key begins with `settings_` so the limits table of `fuku/i18n/settings_locale_test.go` (which must cover exactly the
`settings_` keys) gets one row per key.

## Rendered-size and content checks (the planner turns these into tests)

- A grid button (`{icon} {page name}`) and every two-column editor button (Set, Remove, the three Preview buttons, Full
  preview, Cancel) are at most 20 code points rendered, in all 8 languages.
- The four switch buttons rendered with the longest state word of the language are at most 40 code points.
- Every [alert] key is at most 160 characters in every language (Telegram's limit is 200).
- Every rendered page, prompt, refusal and saved message is at most 3800 UTF-16 units in all 8 languages with a 64-rune
  multibyte group title, including the Welcome page with every part set, a sticker note, a notice and the Open in private
  row, and the Main page with the three new status lines.
- Every callback of every screen in a private and a group menu is at most 64 bytes with a 14-character chat ID and a
  10-digit user ID, and `Omitted` is 0.
- The literal tokens listed above are present and byte-identical in the prompt keys of all 8 locales, and
  `{max}`, `{time}`, `{n}`, `{state}` appear where the English has them.
- `fuku/i18n/settings_locale_test.go` has a limits row for each of the 79 new keys and for `settings_help_msg`.
- Required behaviour tests beyond those: (1) a reply handled by a second handler instance sharing one miniredis sees
  the wait set by the first (EDIT-02, cross-replica); (2) two simultaneous deliveries, and an album of three items,
  write once; (3) a refusal never consumes the wait; (4) Set on another part replaces the first and the old prompt's
  Cancel answers `settings_edit_prompt_stale` and leaves the live wait; (5) `/cancel`, Cancel and the 10-minute expiry
  leave every stored row unchanged; (6) the typed-reply door gives the same answer as a press for the same member record
  in the four owner worlds of `TestSettingsGateAllDoors`; (7) per part, the stored row equals what one `/setwelcome`,
  `/setgoodbye` or `/setrules` with the same content stores; (8) Preview and Full preview write nothing and send only to
  the presser's private chat; (9) the switches leave the same row and invalidate the same cache key as the commands.

## Notes for the planner (contract level)

- **Pages and parts.** One renderer for the three pages driven by a table of parts (`x` text, `m` media, `b` buttons);
  three `registerSettingsPage` calls from `settings_welcome.go`, `settings_goodbye.go`, `settings_rules.go` (or one
  shared file plus thin registrations), page keys `w`, `g`, `r`, orders 50, 60, 70. `settings_pages.go` is not edited.
  Each page has its own action codes (the registry panics on a duplicate): `ws wr wv wf wc`, `gs gr gv gf gc`, `rs rr rv rf rc`.
- **Rights.** Add `settingsRightChangeInfo` and its alert `settings_no_change_info`; add a parity test per row of the
  rights table.
- **Reads.** `greetings.GetGreetingSettings` and `rules.GetChatRulesInfo` swallow read errors and return defaults (the
  greetings reader also creates a missing row). A page needs an error-returning read, as `settingsCaptchaRead` and
  `settingsFloodRead` are, so a failed read is the cannot-open edit and never "Default" or "Not set".
- **Writes.** Column-targeted apply functions beside the commands (`applyWelcomeText/Media/Buttons/Enabled/Clean`, the
  Goodbye twins, `applyRulesText`), each with the validation, the write, its `cache.DeleteCache` of `greetings:<chat>` or the
  rules key and a typed result; the commands keep their replies and call them. `SetWelcomeText` writes all four columns
  at once and cannot serve a one-part write.
- **Send path.** One function builds the member-facing message (`FormattingReplacer`, `keyboard.BuildKeyboard`,
  `media.SendGreeting`) for the join, the leave, `/welcome`, previews and the dry run, so the preview cannot drift. A
  preview must not touch `SetCleanWelcomeMsgId` or delete anything.
- **Spike first** (CONTEXT, research flag): a message sent in private stores in the same form as `/setwelcome` (entities
  to stored HTML, UTF-16 offsets, overlapping entities, emoji, RTL), how an album is cut, and a preview sent to the private
  chat through the group's send path. The dry-run numbers and the 1024 caption rule depend on it.
- **Wait store.** One Redis value per user with a nonce, a compare-and-delete claim, a put-back for a failed write, the
  30-second album memory; no new shutdown drain; document `fuku:settings:input:*` and `fuku:settings:inputalbum:*` in
  `AGENTS.md` (Data) and the new handler group (Handlers), and the new callback codes, the three pages and the rights
  (Callbacks, Permissions), in the same commit.
- **Fire-and-forget.** The best-effort edit of the old prompt and any album memory write that runs off the update path
  start with `defer error_handling.RecoverFromPanic(...)`.
- **Locales.** `make check-translations` first; add the 79 keys to all 8 files and the 79 rows to the limits test; change
  `settings_help_msg` in all 8. `TestSettingsStaffPrivacy` gains the new screens; the worst-case callback test gains the
  new buttons.
- **Tests.** The behaviour tests listed under "Rendered-size and content checks"; the Redis-dependent ones use
  miniredis with two handler instances, the Telegram-dependent ones the repo's hand-written `gotgbot.BotClient` fakes. No
  guarantee rests on PostgreSQL, so nothing joins `make test-postgres-integrity`.
