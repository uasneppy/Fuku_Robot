<objective>
Make `TestStaffActionNonStaffUnchanged` robust against the wall-clock second boundary, test-only, without weakening what it proves.

Root cause, confirmed at planning time:
- The test runs the same command update twice: first on a dispatcher without StaffActions, then on one with it. It compares the Telegram calls of the two runs as strings from `normalizedCalls`, and those strings embed the absolute `until_date`.
- For `/tban` and `/tmute`, `until_date` comes from `extraction.ExtractTime`, which reads `time.Now().Unix()` on every call and adds the duration.
- When the wall clock crosses a whole second between the two runs' `ExtractTime` calls, the strings differ by 1 and the test fails even though StaffActions changed nothing.

The fix is to compare everything except `until_date` exactly, as today, and compare `until_date` through each run's measured clock window. The test then asserts the observable property it cares about: both runs asked Telegram for the same duration.

Purpose: an intermittent red `make test` hides real regressions and teaches people to rerun until green. The test guards the promise that StaffActions changes nothing outside a Staff Group (AGENTS.md: outside a Staff Group the interceptors return `ext.ContinueGroups` with no reply, write or Telegram call), so it has to stay strict and become deterministic.

Output: one edited test file, `alita/modules/staff_action_dispatch_test.go`. No production change: there is no clock seam in `ExtractTime`, and adding one would be a production change that this item rules out. Two proof overlays are built in a temp directory at verify time and never committed: one forces the straddle (must pass), the other forces a real mismatch (must fail). Repeated `-race` runs (`-count=20`) are the proof the user asked for.
</objective>
