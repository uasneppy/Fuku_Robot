## Phase Goal

**As a** group owner, **I want to** open my groups' settings from the bot's private chat and decide whether my admins may change them, **so that** I control who configures the bot.

After this plan the bot keeps its own record of who owns and administers each group, from the moment it loads that group's admin list: `/admincache`, a promotion, a demotion or the bot being promoted all write it, and the bot leaving clears it. This is the data the private list (plan 10-09) shows.

<objective>
Feed `chat_admin_index` from the admin-list load path without making `fuku/utils/cache` import the database layer: an observer hook in `loadAdminCacheFromTelegram`, installed by a new `AdminIndex` module, writes or clears the roster; `adminCacheAutoUpdate` clears it when the bot leaves; `refreshChatAdminIndex` is the lean one-group refresh that the sweep and the group `/settings` repair path (both plan 10-08) reuse (D-02, D-06, D-15; research R-05).

Purpose: MENU-10 (the list is built from the bot's own record, refreshed on every admin-list load, promotion and demotion, and cleared when the bot leaves).
Output: the observer in `fuku/utils/cache`, `admin_index_feed.go` with tests, and the bot-left clear in `bot_updates.go`. No AGENTS.md edit in this plan: it adds no handler group, namespace, key family, table or drain and changes no existing rule; the feed's rules are written into AGENTS.md together with the sweep in plan 10-08.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram admin list to roster | Telegram's answer, possibly stale, failed or partial, becomes rows every replica's list reads |
| cache package to database | the observer is the only bridge; it must not let a database failure change the admin cache result |
