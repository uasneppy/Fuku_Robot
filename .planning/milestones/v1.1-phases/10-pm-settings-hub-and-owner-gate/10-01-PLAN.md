How the SQLite run of the concurrency test avoids busy errors (state it in the test's doc comment): internal/testdb.Run opens SQLite with `_busy_timeout=10000&_journal_mode=WAL`, so a writer that finds the write lock held waits up to 10 s instead of failing, and SQLite holds that lock until commit, which serializes the replaces; because the first statement inside the transaction on SQLite is a write (the upsert, or the delete for an empty roster) and no read precedes it, no transaction has to upgrade a read snapshot to a write, the one case where SQLite answers SQLITE_BUSY without waiting. 160 small transactions finish far inside 10 s. The test changes no pool setting of the shared database. If SQLite still reports "database is locked", the fault is a read inside the transaction, fixed in ReplaceChat; never add a retry loop and never loosen the nil assertion. PostgreSQL, where the advisory lock matters, is the real concurrency proof (plan 10-04 adds the test to make test-postgres-integrity).
