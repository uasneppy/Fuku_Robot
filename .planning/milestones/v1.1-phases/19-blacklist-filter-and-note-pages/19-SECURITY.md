| 11 | the menu and the door to the logs | IDs, codes, counts and error text only |

## New Threats Found by the Audit (unregistered, none blocking)

- **SEC-19-01 (low; DoS / resource). Status: FIXED in part in `899ab69` (the sort key is now computed once per entry; measured after the fix with a throwaway probe, race detector off: 5.5 ms against 36 ms at 10,000 entries and 79 ms against 483 ms at 100,000, the order unchanged and held equal to the comparison sort by a new test); the residual (no per-chat cap on Blacklist and Notes words, and a list past 79,992 entries whose last pages are unreachable because the pager's 4-digit `v` is refused in step 1) is ACCEPTED as an owner decision, because a cap would also bind `/addblacklist` and `/save`. The Blacklist and Notes lists have no cap, and every draw reads and sorts the whole list.**
  - *Evidence:* `fuku/db/blacklists/repository.go:119-128` and `fuku/db/notes/repository.go:235-244` select every row of the chat (small columns only, `Order("id")`, no `LIMIT`); `settingsListLoad` (`settings_list.go:379`) sorts it with `settingsListSort`, whose comparator calls `strings.ToLower` twice per comparison (`:179-196`). Only Filters is capped (150). A typed message carries at most about 2,000 words (`settingsBlacklistApplyTimeout` comment), each an `INSERT`, and the page can be re-armed for another message. Measured by the auditor with a throwaway overlay test (no race detector, random 20 to 80 character Latin and Cyrillic entries): `settingsListSort` takes 0.21 s at 10,000 entries, 2.7 s at 100,000 and 15.7 s at 500,000, on the press goroutine, on every pager, ask, Yes, Cancel and Open press. Memory is small (about 5 MB of allocation at 100,000). Separately, by reading `settings_list.go:350-363` and the 4-digit validator (`settingsListPageMaxDigits`): Next on page 9,999 of a list longer than 79,992 entries carries `v=10000`, which step 1 refuses as an invalid request, so the end of such a list cannot be reached.
  - *Failure scenario:* an administrator with the restrict right (the Blacklist's write right) fills the blacklist through about 50 typed messages and then presses the pager repeatedly: each press burns seconds of CPU on the bot. The same administrator can already make the group's matcher heavy with one `/addblacklist` of 2,000 arguments, so the page adds a convenience and a second place the cost lands, not a new capability. A plain member cannot reach it.
  - *Recommendation:* sort with a precomputed key (compute `strings.ToLower` once per entry, then sort), and decide an owner cap for blacklist words per chat in `applyBlacklistAdd` (it would bind the command too, so it is an owner decision, A19-x); optionally read one page with `LIMIT`/`OFFSET` once a list is large.

- **SEC-19-02 (low; Information disclosure, inherited). Status: ACCEPTED (inherited from Phase 9, research Pitfall 7). A forged `c` on a list action tells whether the bot is in that chat.**
  - *Evidence:* `settings_menu.go:461-478`: for every private action except the pick, a live-member error that `chat_status.IsBotMissingError` recognises edits the menu to the cannot-open note (`p.cannotOpen()`), while a chat the bot is in answers `settings_not_admin` or proceeds. The class rule that makes the answer uniform (`isTelegramClientError`) is scoped to the pick and the deep link (`:464-470`). The 17 list codes inherit the older mapping.
  - *Failure scenario:* a user with a modified or MTProto client sends crafted callback data (`c=<chat id>`) on a bot message in their own private chat and learns whether the bot is a member of that chat. Only bot membership leaks, no content, and the attacker needs the chat ID. It also costs the bot one `getChatMember` per crafted press, throttled by Telegram.
  - *Disposition:* accepted as documented (AGENTS.md "known note"). Closing it means applying the pick's class mapping to every private action, a framework change outside this phase.

- **SEC-19-03 (low; Availability of legitimate admin work). Status: ACCEPTED (provisional owner confirmation A19-2 and A19-A11). The one-code-point rule is a heuristic.**
  - *Evidence:* `list_validation.go:19-31` refuses a word of exactly one code point that is not category So. Probe: `赌`, `博`, `я`, `1`, `$` are refused; `😀`, `©`, `°` and two-letter words (`ee`, `ab`, `a` plus a zero-width space) are allowed.
  - *Impact:* a single Han character is a whole word in a Chinese-language group and cannot be blacklisted by `/addblacklist`, `/filter` or the pages (existing words are kept and still match). In the other direction the rule bounds only the worst case: a two-letter word under action Ban can still delete most messages and ban their senders. The same admin could already set such words before the phase. `19-SPIKE.md` records the rule and its single-commit revert.

- **SEC-19-04 (info; consistency). Status: ACCEPTED. `end()` can report "wait stopped" while a step-2 wait is still live, in a window of a few round trips.**
  - *Evidence:* `end()` and `endWith()` cancel through the Cancel-button script with `r.wait.PromptMsgID` (`settings_input_door.go:402-409`, `settings_input.go:578-583`), which deletes only when it equals the hash's current `m` or a noted refusal. Between the step-1 advance and `settingsInputSetPrompt` (`settings_list_input.go:395-418`) `m` is still the step-1 prompt; a content message that read that value and is then refused with an end reason finds `m` changed, the script answers "stale", the person is told the wait stopped, and the wait lives to its expiry.
  - *Impact:* none on authority: every message is judged live by `authorize`, so a person who lost access still cannot write. It needs a reply inside that window and a refusal that ends the wait.

- **SEC-19-05 (info; log volume). Status: ACCEPTED. A typed message of about 2,000 words can log one error line per word, twice, when the database is down or the 30 s bound passes.**
  - *Evidence:* `applyBlacklistAdd` keeps looping after the context ends (`blacklists.go:186-226`); each failed `blacklistWrites.Add` logs `[Blacklists] Failed to add a blacklist word` (chat ID and error only) and the repository logs `[Database] AddBlacklist` (`repository.go:35`).
  - *Impact:* a bounded burst of about 4,000 lines per message, with no word in any line. It needs an administrator with a wait and a failing database.
