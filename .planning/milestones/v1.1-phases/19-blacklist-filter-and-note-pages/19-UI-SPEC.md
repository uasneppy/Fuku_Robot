# Phase 19 - UI Design Contract

> Visual and interaction contract for the **three list pages of the settings menu**: Blacklist, Filters and Notes. It
> covers their Main cells and state lines, the shared list screen (entries, paging, numbered delete buttons), the delete
> card, the add flows typed in the bot's private chat (one message for blacklist words, two messages for a filter or a
> note), the blacklist action screen, the group-menu note that replaces every list in a menu opened in the group, every
> new callback with its measured worst-case size, every new string with its key and ceiling, and the checks that prove it.
> Generated by gsd-ui-researcher; to be verified by gsd-ui-checker.
> Upstream: 19-CONTEXT.md D-01..D-14 (provisional owner defaults, treated as locked here), 19-RESEARCH.md (its corrections
> C-01..C-16 and settled findings S-01..S-13 are binding and override CONTEXT where they differ), REQUIREMENTS PAGE-07..PAGE-09,
> PAGE-10, PLAT-05, the APPROVED Phase 18 contract (`18-UI-SPEC.md`, whose message anatomy, text styling, status icons, row
> budgets, size budgets, copywriting register and numbered amendments this file reuses and continues: M1 to M37 stay in force
> and this file continues with **M38**; A16-A*, A17-A* and A18-A* stay in force and this file continues with **A19-A1**),
> AGENTS.md (Callbacks `settings|v1`, the Main page, the Locks pager, the shared two-tap card, the message editor and the
> typed-reply door, Permissions, Testing) and the code of `fuku/modules/settings_pages.go`, `settings_menu.go`,
> `settings_card.go`, `settings_locks.go`, `settings_input*.go`, `settings_edit*.go`, `settings_hub.go`, `blacklists.go`,
> `filters.go`, `notes.go`, `fuku/utils/content` and `locales/en.yml`.

This phase has no web screen. Everything is a Telegram message in HTML parse mode plus an inline keyboard: the menu message
(private or opened in the group, edited in place), the typed-reply prompts and the refusal and saved replies of the door
in the bot's private chat. There is **no group-side text**: no page posts into the group, and the effect of a page write
is only what the group's existing watchers do with the stored row (the blacklist watcher at group 7, the filters watcher
at group 9, `#name` and `/get` at group 0). Anything not restated here is unchanged and applies to the new pages: the
message anatomy, the press pipeline (`settingsPress.verify`, owner gate at step 4b, one answer per press), the rights
model, the cannot-open edit, "never name the Staff Group" (D-21, D-32 of the menu) and the Phase 11 to 18 limit tables.

The three pages are **one list engine and three tables** (`settings_list.go` plus `settings_blacklist.go`,
`settings_filters.go`, `settings_notes.go`, each registering from its own `init`), because three hand-written page files
would be near copies (research "one list engine"). Unlike Phase 18 this phase **does** make framework edits, each named
as an amendment: `PrivateOnly` on `settingsPage` (M39), `settingsCardRowsTo` (M40), the bounded `w` field of the wait
(M41), one composite right (M42) and the door's list branch (M43).

**What a member of the group can see.** Nothing of any list. In a menu opened in the group the three cells are on Main
with the fixed state word `In private`, and opening one draws only a note and the Open in private button (D-01, M39).
No screen of a group menu shows an entry, a count of entries, a word, a keyword, a note name or the blacklist action.

## Message Layout (replaces Spacing Scale)

The Phase 9 anatomy stands: a header line (`settings_header` with the page name), the group line (`<b>title</b>
<code>id</code>`), one blank line, the body lines, and one blank line plus the foot notice when a press just ran (`⚠️`
for a refusal or a failure, `✅` for a success, code-side prefixes). This phase adds one changed screen (Main), the list
screen in three variants, the blacklist action screen, the delete card, the add prompts, the door's replies and the group
note. Mock values: group "Fuku Test Group" `-1001234567890`, English, `[ a | b ]` is one keyboard row.

admin and 19 for the owner, about 1.2k units of 3800 (check C19-4).

## Text Styling (replaces Typography)

Phase 11 to 18 styling stands: `<b>` only on "Settings", the group title and the value of a `…: <b>{value}</b>` line
(`settings_bl_action_line`), `<code>` on the chat ID and on **every piece of user text** (an entry, the keyword or name
line of a step-2 prompt, the entry in a delete card, the keyword or name in a refusal or a saved notice), plain text for
intros, hints and notices, button labels plain text. Command and syntax examples inside a string (`#name`, `/get name`,
`[Name](buttonurl://https://example.com)`, `{admin}`, `{private}`) are wrapped in `<code>` in the English template and
are not translated.

**User text rules** (D-11, research Pitfall 1). Every user text is: bidirectional controls stripped, line breaks and runs of
whitespace collapsed to one space, cut by code points (32 in a list line, 100 in a card, a refusal or a notice) with `…`
appended when cut, **then** HTML-escaped (escaping after the cut, so an entity is never split), then spliced into the
translated string. User text never appears in a button label, callback data or a log line; a log line of the list engine,
the door's list branch and the seven apply functions carries the chat ID, the user ID, the page and the part only (C-14).

**No string of this phase carries a Staff Group, a member's name, a user ID or a count of members.** The group's own title
appears only in the group line. Numbers: entry numbers and page numbers (digits, code-side), the counts of the count lines
and saved notices, `{max}`, `{text}`, `{caption}` limits.

### 2. The list: read, order, page, stale entries

- **Read** (research C-01, S-05): every draw reads the list fresh, chat-scoped and error-returning, through a seam per page
  (`settingsBlacklistRead`, `settingsFiltersRead`, `settingsNotesRead`): `SELECT id, word, action FROM blacklists WHERE
  chat_id = ?`, `SELECT id, keyword FROM filters WHERE chat_id = ?`, `SELECT id, note_name, admin_only FROM notes WHERE
  chat_id = ?`. Nothing is created and nothing is cached. A failed read is the cannot-open edit (`settings_cannot_open`
  with the alert `settings_cannot_open_alert`) on the page and `❔` on Main. The commands' list getters, which hide their
  read errors or create rows (`GetBlacklistSettingsContext`, `GetFiltersListContext`, `GetNotesListContext`, `notes.GetNotes`),
  are never called by a page.
- **Order**: the lower-cased text in code point order, ties by row ID. **Page size 8.** The number of an entry is its
  position in that order (1-based), shown in the body line and on its delete button.
- **Cursor**: the absolute page `v`. Opening the page (`op`) draws page 1; Prev is drawn only after page 1 and Next only
  before the last page, each carrying the absolute page; a `v` past the end draws the last page (`0` draws page 1). There is
  no dead button and no `·`.
- **Stale entries.** A page drawn before another admin (or the command) changed the list shows the old entries until the next
  press; every press reads fresh. A delete ask for an entry that is gone, or whose `r` names a row of another chat, redraws
  page `v` with the notice `⚠️ settings_entries_already_removed` and draws no card (the same answer for gone and foreign, so
  no oracle). Numbers shift by the entries added or removed since; a delete button always carries the row ID, never the
  number, so a stale button can only ever reach the row it was drawn for.

### 3. Deleting an entry (D-05, D-06)

| Step | What happens |
|------|--------------|
| Ask (`bx&r&v`) | the whole press pipeline with the page's delete right (section 4), so a presser without it never sees the card; then the entry is read fresh by `(id, chat_id)`; gone → page `v` with `settings_entries_already_removed`; else Screen 4, Yes `{a: by, r}` plus a fresh `e` (now + 5 minutes, `settingsCardLifetime`), No `{a: bp, v}` (M40) |
| Yes (`by&r&e`) | the whole pipeline again with the same right on a fresh member record (a demotion between the taps is refused); then `settingsCardExpired` (an expired minute: the list redrawn at the page holding entry `r`, or page 1 when it is gone, with `⚠️ settings_card_expired`, nothing deleted); then one `DELETE … WHERE id = ? AND chat_id = ? RETURNING` with the command's own cache drops (section 7) |
| Deleted | the press is answered empty and the list is redrawn at the page where the removed entry stood (the count of remaining entries that sort before its returned text, divided by 8, plus 1, clamped), with `✅ settings_bl_removed` / `settings_flt_removed` / `settings_notes_removed` naming the returned text (escaped, cut at 100) |
| Zero rows | another admin deleted it, a stale card, or a forged ID of another chat: page 1 with `⚠️ settings_entries_already_removed` |
| No (`bp&v`) | an ordinary pager press: page `v`, no notice |
| Write error | page holding entry `r` (or page 1) with `⚠️ common_settings_save_failed`, nothing reported as deleted |

A delete never matches by text: a card drawn for one row cannot delete a row re-added later with the same text (the D-33 rule
"a card binds the object it was drawn for"). The card is used for all three pages (D-06, research A19-9). After a delete
the word is no longer acted on, the filter no longer answers and `/get name` answers `notes_does_not_exist`, at the next group
message on the replica that took the press (section 7).

### 4. Rights (D-03, research S-10, C-05)

Opening any page, paging, the action screen and Cancel need `settingsRightAdmin` (the live admin check every press makes,
plus the owner gate at step 4b). Viewing a list is looser than `/blacklists` and `/filters`, which also ask for the bot as an
administrator; accepted because viewing writes nothing (the Phase 18 precedent for `/anonadmin`'s status view, A19-A6). Every
write declares the right of its command and the door judges a typed reply with the same right (`settingsRightRefusalFor` for
the member part, the shared bot half for the bot part).

| Control | Command's checks (read from the code) | `settingsRight` | Refusals, in order (notice unless marked alert) |
|---------|---------------------------------------|-----------------|--------------------------------------------------|
| Blacklist `bn`, `bx`, `by`, `bs`; typed part `w` | `IsUserConnected(true, true)` (user admin, bot admin by `IsUserAdmin(b, chat, b.Id)`), `IsUserAdmin` (silent), `IsBotAdmin` (silent), `CanUserRestrict`, `CanBotRestrict`; `/blacklistaction` the same without the silent pair | **`settingsRightRestrictBotRestrict`** (M42) | `connections_is_user_connected_bot_not_admin`; `chat_status_bot_not_admin` (the command is silent here, the menu must say something); **alert** `settings_no_restrict`; `chat_status_bot_restrict_error` for a press, `chat_status_bot_restrict_group_error` for a typed reply (U-9) |
| Filters `ia`, `ix`, `iy`; typed parts `k`, `y` | `IsUserConnected(true, false)` (no bot check), `CanUserChangeInfo` | `settingsRightChangeInfo` | **alert** `settings_no_change_info` |
| Notes `ea`, `ex`, `ey`; typed parts `n`, `c` | `IsUserConnected(true, true)`, `CanUserChangeInfo` | `settingsRightChangeInfoBotAdmin` | `connections_is_user_connected_bot_not_admin`; **alert** `settings_no_change_info` |
| `op`, `bp ig eg`, `bo`, `bc ic ec`, Back, Close | none beyond the pipeline | `settingsRightAdmin` | none |

**A notice refusal answers empty and redraws with the warning line** (the list page at `v` for an ask, page 1 for Add, the
page holding `r` for a Yes, the action screen for `bs`); **an alert refusal edits nothing** (Phase 9, unchanged). A control
the presser lacks the right for is still drawn. The bot parts use the commands' own cached predicates, never a live bot
lookup, on a press (the Phase 18 rule); **in the door** a cached `false` of a bot part is classified by one live
`getChatMember` of the bot (the Phase 11 `botAdmin()` pattern, generalised): a definite non-administrator, or a bot without
`can_restrict_members` for the blacklist, ends the wait with the refusal and `settings_edit_wait_stopped`; a 429, a 5xx, a
timeout or an answer that says the bot can keeps the wait with `settings_check_failed`. A lost member right in the door ends the
wait with `settings_no_restrict` or `settings_no_change_info` and `settings_edit_wait_stopped` (the Phase 11 mapping). The owner
gate's carve-out applies everywhere (a non-owner administrator with the switch off is refused at step 4b, stricter than the
commands).

### 5. The blacklist action (D-08, research C-02, C-15, S-11)

- **What the page claims.** The action is stored on every word (a column), the watcher acts per word, and the command's
  "current mode" is whichever row the database returns first. The page therefore draws `Action: <value>` **only when every
  word has the same action**; otherwise `Action: Mixed` with one `settings_bl_action_count` line per stored value (most words
  first, ties by value) and the mixed hint. The column allows **eight** values (`warn mute kick ban none tban tmute delete`,
  migration 20260412000000), so a mixed list can have up to eight count lines: the five the command writes are worded by their
  option words (`none` as `Delete only`, `settings_bl_opt_none`) and the three inert ones (`tban`, `tmute`, `delete`) by their
  stored word, escaped and capped at 16 code points, so no stored value is ever hidden or mislabelled (checker F-5). It never draws a single action that is not true of every word.
- **The choices** are exactly the command's five, labelled for what they do: Warn, Mute, Kick, Ban, **Delete only** (value
  `none`: the watcher deletes the message and does nothing else, research C-15; research A19-11). A uniform stored `tban`,
  `tmute` or `delete` is drawn as stored with the inert line and marks nothing; a choice replaces it.
- **A press of `bs`** runs the pipeline with `settingsRightRestrictBotRestrict`, then `applyBlacklistAction(ctx, chat, v)`, which
  updates every word of the chat and drops `blacklist:<chat>`, and redraws the action screen from a fresh read with no notice.
  A press of the action every word already has writes the same rows again and shows no notice. Outcomes: `noWords` (zero rows:
  the list is empty, reached only by a stale screen) redraws with `⚠️ settings_bl_action_no_words`; `saveFailed` redraws the
  stored state with `⚠️ common_settings_save_failed` (this is also what a PostgreSQL database still carrying the old CHECK
  without `none` answers to Delete only until the research C-16 migration lands).
- **Words added later** (research A19-3, recommended YES): `applyBlacklistAdd` gives a new word the action every existing word
  shares, and `warn` when they differ or the list is empty, so a page that "sets the blacklist action" stays true for words
  added afterwards, from the page or by `/addblacklist`. The hint `settings_bl_action_hint` says exactly this. If the owner
  declines A19-3, the hint's English becomes "The action is stored with each word, and a word added later starts with Warn."
  (same key, same ceilings), and nothing else on the screen changes.
- **Empty list**: no Action button (U-10); the empty line says the action is chosen once there is a word.

### 6. Adding: the door's list branch (D-04, D-07, research S-03, S-04, S-08, C-06, C-09, C-11)

**Common rules.** Add is private-only (section 1). An Add press runs the pipeline with the page's write right, then (Filters
only) a fresh count: at 150 the list page 1 is redrawn with `⚠️ settings_flt_refuse_cap` and **no wait is created**. Then
`settingsInputSet` writes the wait (`c` the group, `p` the page, `t` the first part, `m` the menu message, a fresh nonce,
ten minutes) and the menu message is edited into the prompt (Screen 5). With no Redis, or when the write fails, Add answers
the **alert** `settings_entries_add_unavailable` and edits nothing; the list, the delete card and the action keep working
(fresh database reads, a stateless card). A wait it replaced for another group, page or part adds `settings_edit_replaced_note`;
the same page and the same first part only refreshes the ten minutes. Each typed message is judged like a press: live
`getChatMember` of the sender, the owner gate, the part's right (section 4), live `getChat` of the group, then the part's check,
then the claim (or the advance), then the write. A typed message that looks like a command (`/` and a non-space) is not a
candidate and passes on with no reply, so a word, keyword or reply starting with a command cannot be added from the page (the
command can); the wait stays (Phase 11 accepted behaviour).

**Blacklist, one step (part `w`).** The words are the text or the caption, split like `ctx.Args()` (`strings.Fields`) and
lower-cased; a repeated word counts once. Each word is one of: **too long** (over 100 code points), **too broad** (exactly one
code point that is not in Unicode category So, research C-03, A19-2), **already on the list** (against a fresh read), or
**addable**. A message with no word at all (a sticker, a photo without caption) is refused with `settings_edit_refuse_need_text`.
No addable word: the refusal reply (Screen 6), the wait kept. At least one: claim, `applyBlacklistAdd`, finish, then the saved
page with the count lines (Added, Already on the list, Too long, Too broad, and `settings_bl_saved_failed` for words whose write
failed); when every addable word's write failed, the claim is released and the reply is `common_settings_save_failed` with
`settings_edit_still_waiting` and Cancel (Phase 11).

**Filters and Notes, two steps.** Step 1 (`k` keyword, `n` name) needs a text message (a media message is refused with
`settings_edit_refuse_need_text`). The keyword is `strings.Fields` joined by one space and lower-cased; the name is the text
trimmed and lower-cased. Checks, each refusing before the next:

| Check | Filters keyword (`k`) | Notes name (`n`) |
|-------|-----------------------|------------------|
| blank | `settings_entries_refuse_blank` | `settings_entries_refuse_blank` |
| over 100 code points | `filters_keyword_too_long` (the command's text) | `notes_name_invalid` |
| shape | too broad: `filters_keyword_too_broad` (A19-2) | whitespace inside, or a leading `#`: `notes_name_invalid` (A19-4) |
| already exists (fresh read) | `settings_flt_refuse_exists` with the keyword | `settings_notes_refuse_exists` with the name |
| cap (fresh count) | 150 reached: `settings_flt_refuse_cap` | none (notes are uncapped) |

A refusal is the Phase 11 refusal reply: the reason, a blank line, `settings_edit_still_waiting`, one Cancel button noted on the
wait; the wait stays at step 1 and is not extended, so the owner can type another keyword or name (R-8: a refused first step
never strands the user). An existing keyword or name is refused, not overwritten: overwriting is editing content, which is out of
scope (research C-09, A19-7); the refusal tells the owner to delete it from the list first.

Accepted step 1 → the **advance script** (one Lua call: holder of the current nonce, no claim held; sets `t` to the step-2 part,
`w` to the normalised keyword or name, `q` to the step-1 message's ID, a new nonce, a fresh ten-minute expiry, the marker
`c|p|t` rewritten). The step-2 prompt is sent as a reply to the step-1 message and its message ID recorded as `m`; the step-1
prompt is edited to `settings_entries_step_done` (best effort). A second delivery of the step-1 message, a Cancel or `/cancel`
racing it, or an Add that replaced the wait meanwhile all see a stale nonce and do nothing.

Step 2 (`y` reply, `c` content): a candidate whose message ID is not greater than `q` is ignored with no reply (U-11). The
message goes through `content.ExtractTypedNoteOrFilter(msg, w, isFilter, language)`, so the stored row equals what `/filter <w>`
(or `/save <w>`) **replying to that message** stores, formatting, buttons, media kinds and note directives included (research
S-04; the two-word reply quirk of the command is not copied). Refusals keep the wait at step 2 with `w` kept: the extraction's
own texts `content_need_filter_content` / `content_need_note_content` (no text and no supported media: a poll, a location, a
contact, a dice, a story) and `content_text_too_long` / `content_caption_too_long` (filled with the count, as the command does).
There is no button-count check (the commands have none, research S-04). Then the keyword or name is checked again against a
fresh read: taken meanwhile by another admin, or (Filters) the cap reached meanwhile, **ends the wait** with the reason, a blank
line and `settings_edit_wait_stopped`. Otherwise claim, `applyFilterAdd` / `applyNoteAdd`, finish, the saved page (Screen 6) at
the page holding the new entry with `✅ settings_flt_saved` / `settings_notes_saved`; an apply outcome `exists` (a lost insert
race) is answered like the re-check; a failed write releases the claim and answers `common_settings_save_failed` with
`settings_edit_still_waiting` and Cancel. An album's first item is the content and the notice adds `settings_edit_album_cut`

## Callback data (64-byte cap)

Built only with `encodeCallbackData`. Worst case: `c` = `-1001234567890` (14 characters), `u` = `1234567890`, `r` = a
17-digit row ID, `v` = a 4-digit page, `e` = an 8-digit unix minute (8 digits until about the year 2160). Byte counts include
`settings|v1|` (12 bytes) and were **measured** with `callbackcodec.Encode` (keys sorted, URL-encoded) in a throwaway test on
2026-11-13. The page shown is Blacklist; Filters and Notes have the same shapes with `i…` and `e…` codes and the same sizes.

| Button | Data (private) | Bytes private | Bytes group |
|--------|----------------|---------------|-------------|
| Main cell of a list page | `settings\|v1\|a=op&c=-1001234567890&p=b` | 37 | 33 |
| Pager (Prev, Next), card No | `settings\|v1\|a=bp&c=-1001234567890&v=9999` | 40 | private only |
| Delete ask `🗑 n` | `settings\|v1\|a=bx&c=-1001234567890&r=12345678901234567&v=9999` | 60 | private only |
| **Delete Yes** | `settings\|v1\|a=by&c=-1001234567890&e=29412345&r=12345678901234567` | **64** | private only |
| Delete Yes with an 18-digit ID (never drawn, U-5) | `…&r=123456789012345678` | 65, **over the cap** | — |
| Add | `settings\|v1\|a=bn&c=-1001234567890` | 33 | private only |
| Cancel the wait | `settings\|v1\|a=ic&c=-1001234567890&t=y` | 37 | private only |
| Action screen | `settings\|v1\|a=bo&c=-1001234567890` | 33 | private only |
| Action choice (`warn`, `mute`, `kick`, `none`; `ban` is 39) | `settings\|v1\|a=bs&c=-1001234567890&v=none` | 40 | private only |
| Back, Close | unchanged | 33 | 29 |
| Open in private (group note) | a URL button, no callback data | — | — |

The **largest new button is the delete Yes at exactly 64 bytes**, which is why row IDs are bounded at 17 digits (U-5, research
C-04) and why the Yes carries no page (with `v` it would be 71). Every other new button has at least 4 bytes to spare. A
row whose ID has more than 17 digits is drawn without its delete button and counted in `settingsScreen.Omitted`; the bytes test
holds `Omitted` at 0 for 17-digit IDs on every screen and fails on any button over 64
(`TestSettingsList{Blacklist,Filters,Notes}CallbackBytes`). No callback carries a word, keyword, name or any user text.

## Accessibility and phone-width notes

- **Numbers bind buttons to lines.** A delete button carries only `🗑` and the entry's number, and the same number starts the
  entry's body line, so a screen reader reads the list as text and the button by its number; the card then names the entry in
  full before anything is deleted.
- **Readable entries.** Each line is cut at 32 code points, so a long entry never wraps into several lines on a phone; bidi
  controls are stripped so a right-to-left word cannot reorder the line, the number or the next line (research Pitfall 1). A
  right-to-left word still renders right to left inside its `<code>`: checked on a phone (A19-A10).
- **Widest rows.** The delete rows have four cells of at most 7 code points (`🗑 79992`, the widest global number); the action rows three and two cells of at
  most 17 (`✅ Delete only`); Main's cells at most 20. The Add row is one full-width button (Filters, Notes) or two half cells.
- **State is never icon alone**: counts are words (`Words: 20`), the action is a word, the marked choice has `✅` and the action
  line repeats it.
- **No colour, no image, no URL** except the Open in private URL button of the group note.
- **Privacy at a glance.** A group menu shows only `In private` and the note; everything else is in the private chat of an
  admin the pipeline has just checked live.
- hi, ru, uk and id cells and buttons are checked on a phone (A19-A10).
