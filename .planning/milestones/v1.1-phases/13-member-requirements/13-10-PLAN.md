## Planner assumptions (flagged)

- The cap numbers (10 a minute, a 10-minute pause) are the research's (Claude's discretion, D-21); they keep a chat well under Telegram's group limit of about 20 messages a minute (research assumption A1, an owner live check in 13-SPIKE.md).
- Revision of research Open Question 13 (orchestrator decision): during a pause a new violator's message is still deleted when Delete messages is on, because a delete is not a punishment and posts no notice; only punishments and notices pause. The paused path deletes before it returns, with no hold, no live lookup and no notice. Second revision: the paused path, which runs before the job's live lookup, deletes only when the cached admin list is known and the sender is not in it. An unknown status means no delete and no Telegram call during a pause, so a pause never spends a call to decide a delete and never deletes an admin's message.
- Why the cache is trusted: the watcher already skips a known admin, and a promotion or demotion invalidates and reloads the chat's admin list. That is `adminCacheAutoUpdate`, registered for chat_member admin changes at group 0 by the BotUpdates module (priority -10, so it is the first group-0 handler of such an update), and it returns `ext.ContinueGroups`. A known list therefore misses a new admin only for a message handled at the same moment as the promotion's own update, before that update's invalidation. That window is the one the watcher's known-admin skip already has; the plan does not close it with a live call, which a pause forbids.
- The held path outside a pause asks one live getChatMember when the cache cannot say (at most one read per held message of an unknown-status member, paced fleet-wide), so a held member promoted while the cache is cold is never deleted. The tests prime the admin cache with `cache.LoadAdminCache` against the fake's `getChatAdministrators` and simulate a promotion with the fake's `listAdministrator` plus `cache.InvalidateAdminCache`.
- The cap counts punishment attempts, not successes, so a bot that keeps being refused still reaches the pause instead of retrying forever.
- The runner's shedding under overload stays best effort (13-09, AGENTS.md, D-14 as amended): a shed job deletes nothing until the member's next message.
- Test hygiene: `memberReqEnv` and `memberReqCleanup` as 13-07 (the cleanup already deletes the `fuku:memberreq:*` keys of its chats); every test turns enforcement on through `withMemberReqLive` (`newMemberReqEnv` does it); the no-Redis test removes the client through the test seam and restores it in `t.Cleanup`.
