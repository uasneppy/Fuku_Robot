## Phase Goal

**As a** group owner, **I want** accounts whose names look like spam flagged by AI, **so that** advertising accounts are screened when they join, with no message text leaving the server.

After this plan the provider call is capped per account, per group and per fleet per hour, at four at a time per replica, paused by its own breaker when it fails, and an outage or an exhausted hour leaves members alone without ever suspending the other rules.

## Planner assumptions (flagged)

- Execution rules are `executor-brief-15.md`'s; read "of NN" as "of 11".
- Plan 15-05 (the baseline, the new-member marker, the watcher's cached read and the held release) runs before this plan, so every test here is written against the final rule: a test that needs the rule to judge a member either passes `memberReqLookupMode{Joining: true}` to a direct call or runs the join entry, and a job-path test first records the member as new with the helper plan 15-05 added (`mreqAIMarkNew`), because an established member without a marker is only baselined and costs no call. The research ran the cost-guard plan first; the order is swapped because the baseline changes what the rule does for a first sighting, and tests written before it would all have to be edited after it.
- Order inside the flight (D-24, research S-04), after the cache re-read the tracer already does: breaker paused, then the gate, then the budget, then the call, then the breaker record, then the cache write. A paused breaker is a sticky unknown and spends nothing; a gate that cannot be had within `memberReqAIGateWait` is a sticky unknown when the flight's own context is still live (a cancelled one is a plain unknown: shutdown is not a state) and spends nothing, because the gate is taken before the budget; a budget refusal is a sticky unknown and the gate slot is given back by the `defer`; a Redis error on a budget key is a plain unknown (a fault of the moment, not a state). The unit is reserved before the call and a failed call still spends it (the conservative side, as for images).
- The budget keys are fleet-wide per account (no chat in `aib:u:`): a name belongs to the account, not to a group, and renaming is the attack (D-25). Each key is used in single-key commands only, so no hash tag is needed. They sit in the `fuku:memberreq:*` family, outside the cache prefix, so `CLEAR_CACHE_ON_STARTUP` keeps them.
- dupl: the budget reservation does not copy `raidAIReserveBudget`. It uses the stateless `raidAIBudgetTake`, `raidAIHourStamp` and `raidAIScrub` and nothing else of the image code, and it is shaped differently (it returns a three-way result, ok, capped or error, which the caller turns into a sticky or plain unknown, where the image function returns a bool and bumps its own counters). The breaker is a type with methods and its own struct, with the map bound and the prune in their own small methods and the failure count in another, so no run of 100 tokens equals `raid_ai_breaker.go`'s package-level functions. `raid_ai_breaker.go` and `raid_ai_image.go` are not edited. If the lint stand-in still names a clone after one restructure, restructure the breaker further (smaller methods, a different split); only if two restructures leave a finding, record a deviation, extract the shared logic into a generic type in a new file used by both breakers with `raid_ai_breaker.go`'s names and behaviour unchanged (the existing `TestRaidAIBreaker` and `TestRaidAIImageBreakerCap` must pass unedited), and say so in the SUMMARY.
- The sticky bit reaches the executor without the executor naming the rule: `memberReqLookupMasks` stamps each row's bit into the context it hands to that row's `Lookup`, `memberReqNoteSticky(ctx)` reads it and sets it in the run's `memberReqLookupTouch.sticky` (an `atomic.Int64` or-ed with the bit), and `memberReqLiveViolation` clears `touch.sticky` from `unknownMask`. A caller that got a sticky answer from a flight it only followed notes it too (the answer carries the flag). Without a touch in the context (a press, the held release) the note is a no-op.
- The stale-names guard (D-29) uses a table field, not a literal bit: `memberReqRule.NamesBound` is true only on the AI row, and `memberReqNamesBoundMask()` ORs the bits of those rows. The guard compares the canonical names hash (`namecanon.Of`, the empty string when not judgeable) of the record the lookups judged with the hash of the re-read record, so an invisible-character change does not count as a change and a change from judgeable to not does.
- `memberReqAICall` exists because the recovered-panic shape of the log sweep (plan 15-10) and the gate's release on a panic cannot be provoked through the HTTP client; its default is the real call and production code never reassigns it.
- Counters (checked, passed, breached, cached, capped, shed, failed, blocked) are in-memory atomics for tuning (D-32); this plan adds no `/stats` section (D-32 marks it optional; the owner can ask for it later), and `memberReqAIStatsSnapshot()` is read by the tests of this plan to assert which outcome happened.
- Test hygiene as in plans 15-04 and 15-05: fresh IDs from `uniqueLinkOwnerID()` and `uniqueModuleChatID()`, names carrying the unique user ID, `mreqAICleanup` extended to delete every `fuku:memberreq:aib:*` key (it already deletes the verdict, baseline and marker keys), every swapped package variable (the gate, its wait, the three budgets, the breaker instance, `raidNow`, the seams) restored in `t.Cleanup`, the breaker reset by a helper at the start and end of every test that can trip it (its state is process-wide), no skipped test, no parallel test with the enforcement switch, no real provider. Concurrency tests use Mute or Kick, never Warn (the warn module's SQLite transaction).
