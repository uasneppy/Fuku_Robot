## Phase Goal

**As a** group owner, **I want** accounts whose names look like spam flagged by AI, **so that** advertising accounts are screened when they join, with no message text leaving the server.

After this plan an established member's names are first recorded without a call, a new joiner is judged at join or at their first message, a renamed member is judged again, the watcher decides from three cached reads without calling anyone, and switching the rule on in a large group costs no provider call.

<objective>
Complete the rule's order (baseline, new-member marker, joining), write the marker in the join entry, extend the watcher's one cached read with the three AI keys, and pass the sender's names to the held release, with their tests (D-02, D-04, D-21; research S-03, S-02 "Held release").

Purpose: without this plan an established member is judged by the provider at every first message (a burst on switch-on) and a joiner whose call fails is never judged. The rule's safety for a real group rests on it.
Output: edits to six production files, two new test files, three edited test files, AGENTS.md.
</objective>

## Planner assumptions (flagged)

- Execution rules are `executor-brief-15.md`'s; read "of NN" as "of 11". This plan runs before the cost-guard plan (15-06); the research ran them the other way round, but the baseline changes what the rule does for a first sighting, so every test written before it would have to be edited after it. The three tracer tests it changes are named above and edited only for that reason.
- The rule's order is exactly research S-03 / D-21: names nil is unknown; not configured is inert; not judgeable is inert; no Redis is unknown; one pipelined round of `GET nv`, `GET nm`, `GET nu` (any error other than a miss is unknown); a readable verdict decides (below the bar records a pass and passes; at or above the bar sets the marker and breaches); otherwise, when not joining and the marker is absent, a baseline equal to the current hash passes with no write and an absent baseline is written with `SET NX` and passes with no call; otherwise (a joiner, a marker present, a baseline that differs) the flight judges, and its answer is recorded by the caller (pass: `nm = h` and delete `nu`; breach: set `nu`; unknown, sticky or not: nothing). A flight is shared by callers with different user IDs and the same string, so it does only the call and the verdict write; each caller records its own `nm` and `nu` (D-24). `mode.Fresh` and `mode.Classify` stay ignored (D-23).
- "New" means "recorded as joining while the rule is on": the join entry sets the marker for every joiner it reaches while `memberReqAILive(settings)` holds, whatever the raid join and flood settings are (the raid `:joined` set is not used: it records nothing when those triggers are off). The accepted limit, written into AGENTS.md and `15-SPIKE.md`: with no Redis, a failed marker write or a join the entry never saw, a real new member is baselined and unjudged until they rename (the safe direction). A joiner who never reaches the entry (a captcha failure, a lockdown ban) gets no marker. A member who renames and never writes costs nothing: no update arrives.
- The watcher's satisfied rule is D-21's literally: the verdict value when it parses and is below the bar, or the marker absent and the baseline equal to the current names hash. One consequence the plan records for the owner rather than changes: a member whose baseline equals their current names and who has no marker stays satisfied even when another account's judgement of the same string has since cached a breach, because the baseline is the bot's record that these names were accepted for this member; if a job runs for that member for another reason, the rule's own order (the verdict first) breaches them. The gap errs toward not punishing. `TestMemberReqWatcherAI` has a subtest that pins it so the behaviour is deliberate.
- The AI part of the watcher's read is live only while the rule's action is not Off and the process is configured (`memberReqAILive`): an unconfigured stored value must be treated as Off there, or every message of every member would start a job for ever (research Pitfall 6). Names that are not judgeable (`namecanon.Of` false) are satisfied with no GET. The canonical names and the verdict key are computed in the watcher by pure Go, with the model of `config.AppConfig.AnthropicModel`.
- The held release passes `Names` from `c.User` (the message sender's current names, which Telegram stamps on every message); it runs the same rule, so it records pass and marker exactly as a job does. A hold whose bit is 128 is the only one that makes the call.
- The join entry's marker write is one Redis `SET` under `raidRedisTimeout` through the existing helpers, its error only logged at debug by IDs, after the punished-mute branch and before `if !settings.CheckOnJoin` (a member whose hold read failed returns to the plain welcome before it and gets no marker, the safe direction).
- The Redis key families `nm` and `nu` never hold a name: `nm` holds a 32-hex hash, `nu` the digit 1; both live under `fuku:memberreq:*`, outside the `fuku:cache:` prefix, so `CLEAR_CACHE_ON_STARTUP` keeps them. `nm` is per user (a name belongs to the account), `nu` per chat and user (a membership belongs to a group), and `memberReqCleanup` finds `nu` by its chat ID while `mreqAICleanup` deletes `nm` by user ID.
- Test hygiene as in plan 15-04: fresh IDs from `uniqueLinkOwnerID()` and `uniqueModuleChatID()`, names carrying the unique user ID, dates taken before the message and at least 2 s apart for join and rejoin tests (`mreqSendAt`), every swapped variable restored in `t.Cleanup`, no skipped test, no parallel test with the enforcement switch, no real provider; multi-goroutine tests use Mute or Kick.
