- **The control key of a lock (D-18 against D-09 and the UI-SPEC).** D-18 notes the lock's own name fits the callback "so it can be the control key"; D-09 says a button carries "the table code ... never the lock's name", and the approved UI-SPEC's table gives two-letter codes (`sk gf ph vd vn vo au dc ct lc gm ur fw rt ac bt ms cm md ot pv al`). D-18 permits the name but does not require it, and the UI-SPEC wins on discretion items, so the codes are used; nothing conflicts. The kind (the command's lock name) lives only in the table.
- The table has no production reader until 18-12 registers the page; this plan's tests use it, and the SUMMARY says so (the brief's rule for a table a later plan of this phase is the only production user of).
- C-04: neither command refuses a single type (a bad name refuses the whole call before any write), so `applyLock`'s `lockUnknownType` is reached by the commands' pre-check only as a guard and by a forged page press; the `bots` lock's bot right is checked when a bot joins, not at the write (the page's live right line, 18-12, covers it).
- `locks.UpdateLock` relies on the `locked` column default being false for an unlock (A7, Pitfall 8); neither the model tag nor the column default changes.
