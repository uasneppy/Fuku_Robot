## Phase Goal

**As a** group owner, **I want** members' commands, late edits and, when I choose, every message removed automatically, **so that** the group stays clean and an edited message cannot slip spam in later.

After this plan the third rule works end to end: with "Self-destruct" on, every member message is deleted N minutes after it was sent, admins', approved users' and pinned messages stay, a busy group keeps pace, and a Staff Group is never touched by any of the three rules.

The tracer comes first: one member message queued and deleted on time through the real dispatcher.
Purpose: the producer of the self-destruct rows; everything durable and bounded is plan 17-06's.
Output: watcher code, one hook in pins.go, two test files, toolkit additions, AGENTS.md.
</objective>

## Planner assumptions and deviation notes (flagged)

- Execution rules are `handoff/executor-brief-17.md`'s; "of NN" reads "of 12". Invariant gates use `42c48c4`.
- **Deviation note 3 (D-11 and the bot's own pins).** D-11 drops a row when a `pinned_message` service message names a message. When the bot itself pins a member's message (`/pin` in `pins.go`, near line 324), the service message's sender is the bot, and a `NewMessage` handler without `SetAllowBot` never sees it (gotgbot's `Message.CheckUpdate` drops bot senders; D-10 forbids any `SetAllow*` on the watcher). Without a hook, a member's message pinned with `/pin` would still self-destruct. Recommended handling: after `/pin`'s successful `PinChatMessage` of the replied-to message, call `memberDeletePinned(chat.Id, messageID)`, which runs `deletion.DropPendingMessage(ctx, chat, message, deletion.KindMemberSelfDestruct)` on its own bounded context and logs a failure by chat ID only. A pin by another bot is not seen either: a stated limit in AGENTS.md and a live check in `17-SPIKE.md`. The permanent pin (`/permapin`) pins a message the bot sent itself, which is never queued, so it needs no hook.
- The watcher order is research S-03's, cheapest first: (1) `msg.PinnedMessage != nil`: in a group or supergroup with a negative chat ID, `memberDeletePinned(msg.Chat.Id, msg.PinnedMessage.GetMessageId())` (the chat from the service message, never the nested object) and return; (2) chat type; (3) sender shape through `raidFloodSenderCounts` (a `via_bot` message is queued: D-10 exempts it only for edits); (4) `memberContentMessage` (false for every message `deletionServiceKindOf` recognises and for the creation and migrate fields); (5) the rule through `deletionRulesLookup` (present and accepted by `deletion.ValidateRuleDelay`, else Off); (6) and (7) `memberDeletionExempt` (plan 17-05, D-33: approvals through the tri-state `approvals.IsUserApprovedContext`, then `memberDeletionAdminStatus`; approved, an approvals read error, an administrator and an unknown admin status are all exempt, so a read that fails keeps the message); (8) `memberDeleteOffer(deletion.Entry{ChatID, MessageID, Kind: deletion.KindMemberSelfDestruct, SentAt: deletionSentAt(msg.Date), DelaySecs: delay})`. No captcha lookup: group -10 ends a pending member's update (research C-08). The result is a named value preset to `ext.ContinueGroups`, with `defer error_handling.RecoverFromPanic`.
- The watcher is registered only in the commit that also has every exemption, the pin drop and the `/pin` hook (Task 1), so no committed state can self-destruct an admin's, an approved member's or a pinned message (the advisory of the plan check); Task 2 holds the exhaustive tests.
- The busy-group test asserts call counts and row states, never wall-clock sleeps, except one lower bound on the elapsed time of the real pacer (at least the number of calls minus one times 100 ms). It drives the worker with `pass`/`cycle` and the clock with `deletionNow`. A 3000-message burst fits the 4096-entry channel, so `shed == 0` is asserted.
- Accepted limits (stated in AGENTS.md by this plan, not tested as wanted behaviour): a pin that lands while the message is still in the batcher buffer (about 300 ms) or after the worker claimed its row; a pin by another bot; exemptions judged at send time (a member approved or promoted later still loses queued messages, research open question 4); a command deleted by command deletion leaves a self-destruct row whose later delete is refused quietly.
- Test hygiene: fresh chat and user IDs (`uniqueModuleChatID()`, `uniqueLinkOwnerID()`), cleanups of users rows and cache keys, approvals, captcha attempt rows and the `captcha_pending` key, rule rows and `delete_rules:<chat>`, queue rows, the admin cache entry, the `fuku:delete:*` keys (the pacer keys included after the busy test), `drainMemberDeleteQueue` before row cleanup, swapped variables restored through `mreqSwap`, `deletionInline.wait` registered last; no case is skipped.
