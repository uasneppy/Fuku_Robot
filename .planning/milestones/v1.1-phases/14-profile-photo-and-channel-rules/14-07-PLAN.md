## Phase Goal

**As a** group owner, **I want to** require a profile photo and, in a channel's comment group, a subscription to that channel, **so that** throwaway accounts and outsiders are screened too, without anyone punished because a lookup failed.

After this plan every member is checked against the two rules at their next message with no Telegram call from the watcher, a member who fixes their photo or subscription is released from a warn hold without the owner doing anything, and an exempt member without a photo costs nothing.

<objective>
Extend the message watcher with the cached-positive read and the job hand-off for the lookup rules, skip jobs for known admins and approved members on a miss, and add the held release to the enforcement job, with the named tests that prove each branch and the Phase 13 guarantees that share the code (D-10, D-21, D-24, D-25, D-12; research S-02 held release, S-03, Pitfall 8; UI-SPEC planner note R2).
Purpose: without the watcher branch the rules never fire on a message from a member whose names are clean (the common case), and without the held release a warn hold with a lookup bit could never be cleared once the member fixes the photo.
Output: watcher and executor changes, a new held file, two test files, AGENTS.md.
</objective>

## Planner assumptions (flagged)

- D-21 (the orchestrator's amendment of D-10) is implemented as research S-02 recommended: the hold is still read first and nothing on the held path punishes or claims; the release re-check is limited to the hold's own lookup bits, runs only when the names are clean, and ends in the Phase 13 predicate. It only deletes the hold row: for a punished mute the SQL deletes the row only when `punished_at` is more than 2 s before the message, and a member the bot muted cannot send, so that message proves an admin lifted the mute; the release never calls `restrictChatMember` (a mute hold is only ever freed by "I fixed it" or an admin).
- A member held for a lookup rule and now clean for it, whose hold also carries a name bit that is no longer broken, is released too (the hold's name bits do not need a lookup). A hold whose lookup-bit rule is now Off counts that bit as released.
- The released message is not deleted (the member is clean now); a kept hold deletes it exactly as Phase 13's held path does, using the watcher's snapshot for the Delete messages switch (the deferred SEC-NEW-06 of the Phase 13 disposition stays accepted).
- The watcher reads `lc` only to learn "none" (0) or a channel ID for the `sub` read; a missing `lc` is "not satisfied" and the job resolves the link. The watcher never classifies and never calls the classifier (R2).
- The pass key and the lookup positives are read in one pipelined round for groups with a lookup rule on, so the common path costs at most two round trips (one with only the photo rule) against one today (research S-03); a group with only name rules on keeps its single GET exactly as in Phase 13.
- Redis down handing a job per message to the runner is the documented D-12 cost: bounded by 32 jobs, the pacer's local fallback interval and shedding, never a punishment.
- Multi-goroutine tests use Mute or Kick, never Warn (SQLite "database is locked" with concurrent warn writers); any test that sends and joins takes dates before the message, at least 2 s apart (`mreqSendAt`).
- Execution rules are `executor-brief-13.md`'s; read "of 14" in its STATE.md rule as "of 12". Test hygiene is plan 14-03's.
